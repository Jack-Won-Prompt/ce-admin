# CEAdmin ↔ 위드웍스 연동 규격

작성 2026-08-31 · 콜로플라스트코리아 CEAdmin

이 문서 하나로 양쪽 방향을 다 설명합니다.

| 방향 | 무엇을 | 어떻게 |
|---|---|---|
| **CEAdmin → 위드웍스** | 판매주문 등록·수정·삭제, 반품·교환·취소, 샘플, 제품·재고 조회 | 위드웍스가 열어 준 REST API 를 CEAdmin 이 호출 |
| **위드웍스 → CEAdmin** | 창고 안에서 벌어진 일(확정·할당·피킹·송장·출고·취소, 반품 접수·입고) | 위드웍스가 CEAdmin 의 웹훅 주소로 POST |

두 방향은 **서로를 기다리지 않습니다.** CEAdmin 이 주문을 넘기면 그 응답으로 끝이고,
그 뒤에 벌어지는 일은 웹훅으로 옵니다.

---

# 1. CEAdmin → 위드웍스 (우리가 부릅니다)

## 1.1 공통

| 항목 | 값 |
|---|---|
| 기본 주소 | 위드웍스가 알려 준 API 주소 (CEAdmin 설정에 보관) |
| 경로 앞머리 | `/api/v1/ce-admin/` |
| 인증 | `Authorization: Bearer <토큰>` |
| 형식 | 요청·응답 모두 JSON (UTF-8) |
| 시간 제한 | 조회 8초 · 등록/수정 12~15초 |

**응답은 이 모양이면 됩니다.**

```json
{ "success": true, "result": { ... } }
```

```json
{ "success": false, "message": "무엇이 잘못됐는지 사람이 읽을 수 있는 한 줄" }
```

CEAdmin 은 `success` 를 먼저 보고, 실패면 `message` 를 담당자 화면에 그대로 보여 줍니다.
**HTTP 상태만 200 이고 `success:false` 인 경우도 실패로 다룹니다.**

## 1.2 판매주문

### `POST /api/v1/ce-admin/so_store` — 판매주문 등록

담당자가 주문 등록 화면에서 「주문 생성 및 연계」를 누를 때 한 번 갑니다.

```json
{
  "ce_order_number": "ORD-0028",
  "rx_number": "RX-20260828-010",

  "patient_name": "홍길동",
  "patient_mobile": "010-1234-5678",
  "patient_zipcode": "13595",
  "shipping_address": "경기 성남시 분당구 서판교로 32",
  "shipping_address_detail": "101동 1001호",
  "recipient_name": "홍길동",

  "delivery_date": "2026-09-02",
  "ho_account_id": 1234,
  "remark": "담당자 메모",
  "so_type": "5001",
  "billing_strategy": 25,
  "qty_unit": "EA",
  "confirm": false,

  "items": [
    { "item_code": "SC-12F-3040", "qty": 540, "unit_price": 1200 }
  ]
}
```

**꼭 지켜 주셔야 하는 두 가지**

1. **`qty_unit: "EA"` — 수량은 낱개입니다.** CEAdmin 의 수량은 총계(1일 처방개수 × 총
   처방기간)입니다. 이것을 밝히지 않아 위드웍스가 RB(박스)로 읽고 `r_box` 를 곱한 적이
   있습니다 — 540개가 5,400개로 등록됐습니다.
2. **`confirm: false` — 확정은 창고에서 합니다.** 올리자마자 확정되면 수량·배송지를
   고칠 자리가 없고 재고가 그 자리에서 묶입니다.

**`so_type` 은 `5001`(End User Direct) 로만 주고받습니다.** 다른 유형으로 넘기면 그쪽
콜백 대상에서 빠져 진행 상태를 영영 받지 못합니다.

`patient_name` · `patient_mobile` · `patient_zipcode` 는 거래처·배송지 자동 등록에 씁니다.

**응답**

```json
{ "success": true, "result": { "so_no": "S2608280001", "so_id": 98765,
                               "patient_account_new": true, "patient_address_new": false } }
```

`so_no` 는 CEAdmin 이 주문에 저장하고, 이후 모든 대화의 열쇠가 됩니다.

### `PUT /api/v1/ce-admin/so_update` — 판매주문 수정

몸은 `so_store` 와 같습니다(`ce_order_number` 로 찾습니다). 수량·배송지·품목이 바뀔 때 갑니다.

### `DELETE /api/v1/ce-admin/so_delete` — 판매주문 삭제

```json
{ "ce_order_number": "ORD-0028" }
```

### `GET /api/v1/ce-admin/so_show` — 판매주문 조회

```
GET /api/v1/ce-admin/so_show?ce_order_number=ORD-0028
```

```json
{ "success": true, "result": {
    "status": "95", "status_label": "확정",
    "ship": { "ship_no": "SH2608280001", "ship_status": "95",
              "ship_status_label": "출고완료", "tracking_no": "1234567890" } } }
```

**이 조회는 「그 순간의 전체 상태」로 다룹니다.** 응답에 없는 값은 지워진 것으로 보고
CEAdmin 이 비웁니다 — 취소된 배송 정보가 남지 않게 하기 위해서입니다. (웹훅은 반대로
「온 것만」 덮습니다. 1.6 참고)

CEAdmin 은 이 조회를 **10분마다** 진행 중인 주문에 대해 돕니다. 웹훅이 몇 번 실패해도
결국 맞춰지는 그물입니다.

### `GET /api/v1/ce-admin/sso_link` — 위드웍스 화면 바로 열기

```
GET /api/v1/ce-admin/sso_link?so_no=S2608280001
```

담당자가 위드웍스 화면을 직접 보러 갈 때 씁니다.

## 1.3 반품 · 교환 · 취소

CEAdmin 의 「교환/반품/취소」 접수는 **창고에 이미 넘긴 건**에 대해서만 만들어집니다.

### `POST /api/v1/ce-admin/so_cancel` — 원 판매주문 취소

아직 나가지 않은 건(송장 없음)의 취소입니다. 반품 주문을 따로 만들지 않습니다.

```json
{ "ce_order_number": "ORD-0028", "so_no": "S2608280001" }
```

### `POST /api/v1/ce-admin/return_store` — 반품 판매주문 등록

이미 나간 건의 반품·교환·출고 후 취소입니다.

```json
{
  "ce_return_number": "RT-20260831-001",
  "ce_order_number": "ORD-0028",
  "so_no": "S2608280001",
  "return_type": "return",
  "reason": "환자 요청 — 규격 불일치",
  "items": [ { "item_code": "SC-12F-3040", "qty": 30 } ]
}
```

`return_type` 은 `cancel` · `return` · `exchange` 셋입니다.

`items` 는 **되돌리는 수량**입니다. 부분 반품이면 그만큼만 옵니다 — 원 주문 수량을
그대로 보내지 않습니다.

**응답에는 `so_no` 와 `so_type` 이 함께 와야 합니다.** CEAdmin 은 그 둘이 있어야 이후
상태를 이어 받습니다.

```json
{ "success": true, "result": { "so_no": "R2608310001", "so_id": 99001,
                               "so_type": "5011", "status": "02", "status_label": "등록" } }
```

### `POST /api/v1/ce-admin/return_status` — 우리 쪽 진행 단계 알림

CEAdmin 담당자가 접수 건의 단계를 옮기면 알려 드립니다(참고용).

```json
{ "ce_return_number": "RT-20260831-001", "status": "inspecting", "status_label": "검수 중" }
```

### `GET /api/v1/ce-admin/return_show` — 반품 조회

```
GET /api/v1/ce-admin/return_show?ce_return_number=RT-20260831-001
```

## 1.5 제품 · 재고

### `GET /api/v1/ce-admin/items` — 제품 조회

담당자가 주문 제품 칸에서 이름·코드로 찾을 때 부릅니다.

### `GET /api/v1/ce-admin/stock?item_codes=SC-12F-3040` — 재고 조회

**한 건씩만 묻습니다.** 목록을 만들 때 전부 물으면 한 건에 7초씩 걸려 검색 자체가
끊겼습니다 — 담당자가 제품을 고른 뒤 그 한 건만 따로 묻습니다.

## 1.6 실패했을 때

CEAdmin 은 **되돌리지 않습니다.** 주문은 우리 쪽에 이미 서 있고, 위드웍스로 넘기지
못한 것은 화면에 그렇게 적힙니다. 담당자가 원인을 보고 다시 누릅니다.

그러니 **실패 응답의 `message` 를 사람이 읽을 수 있게 적어 주십시오.** 그 문장이 담당자
화면에 그대로 뜹니다. 「Validation error」보다 「item_code SC-99 를 찾을 수 없습니다」가
백 배 낫습니다.

# 2. 위드웍스 → CEAdmin (그쪽이 부릅니다)

## 2.1 보내는 곳

| 항목 | 값 |
|---|---|
| 주소 | `POST https://<CEAdmin 주소>/api/webhook/withworks` |
| 인증 | 헤더 `X-Withworks-Secret: <미리 나눈 비밀>` |
| 형식 | `Content-Type: application/json` (UTF-8) |

## 2.2 몸

```json
{
  "event_id": "WW-20260831-000123",
  "event": "so.shipped",
  "ce_order_number": "ORD-0028",
  "so_no": "S2608280001",
  "occurred_at": "2026-08-31T14:05:00+09:00",

  "status": "95",
  "status_label": "확정",

  "ship": {
    "ship_no": "SH2608280001",
    "ship_status": "95",
    "ship_status_label": "출고완료",
    "tracking_no": "1234567890",

    "shipped_at": "2026-08-31",
    "items": [
      { "product_code": "28512", "lot_no": "L2608A", "expiry_date": "2028-05-31", "quantity": 30 },
      { "product_code": "28512", "lot_no": "L2609B", "expiry_date": "2029-01-15", "quantity": 10 }
    ]
  }
}
```

| 필드 | 필수 | 설명 |
|---|---|---|
| `event_id` | ✅ | 사건마다 하나. **재전송해도 같은 값을 유지**해 주십시오 |
| `event` | ✅ | 아래 목록 |
| `ce_order_number` | 판매 사건에 ✅ | CEAdmin 주문번호 |
| `ce_return_number` | 반품 사건에 ✅ | CEAdmin 접수번호 |
| `occurred_at` | 권장 | 창고에서 그 일이 벌어진 시각 |
| `status` · `status_label` | 선택 | 판매주문 상태 |
| `ship` | 선택 | **배송 정보가 생겼거나 바뀐 사건에만** 넣어 주십시오 |
| `ship.shipped_at` | **요청 (신규)** | 출고를 확정한 **날짜**(`YYYY-MM-DD`) |
| `ship.items[]` | **요청 (신규)** | 무엇이 어느 **Lot** 으로 나갔는가 |

### `ship.shipped_at` · `ship.items[]` — 2026-08-31 새로 요청드립니다

콜로플라스트 요청서 2쪽입니다. 두 가지를 **`so.shipped` 에 함께** 실어 주십시오.

**① `shipped_at` — 출고일자**

CEAdmin 은 지금 출고일을 「우리가 받아 적은 시각」으로 갈음하고 있습니다. 웹훅이 몇 번
실패해 열 분 뒤 훑기(`so_show`)가 채우면 그만큼 늦은 날이 적힙니다. **청구 기한이
출고일 + 2주**라 하루가 어긋나면 기한도 어긋납니다. 창고가 확정한 날짜를 주십시오.

**② `items[]` — Lot 과 유효기간**

| 필드 | 필수 | 설명 |
|---|---|---|
| `product_code` | ✅ | 제품코드. CEAdmin 주문 줄과 **이 값으로 짝짓습니다** |
| `lot_no` | ✅ | Lot 번호 |
| `expiry_date` | 권장 | 그 Lot 의 유효기간 (`YYYY-MM-DD`) |
| `quantity` | 선택 | 그 Lot 으로 나간 수량 |

- **한 제품이 두 Lot 으로 나뉘어 나가면 줄을 둘로 주십시오.** 유효기간이 Lot 마다
  다르므로 한 줄에 담을 수 없습니다.
- `product_code` 가 CEAdmin 주문에 없으면 그 줄은 **적지 않고 기록만 남깁니다.**
  짐작으로 다른 줄에 붙이면 그 물건의 유효기간이 딴 제품의 것이 됩니다.
- 같은 사건이 다시 와도 **Lot 번호로 갱신**하므로 줄이 겹치지 않습니다.

**`ship` 을 매번 넣지 마십시오.** CEAdmin 은 웹훅을 「온 것만 덮는다」로 다룹니다.
빈 `ship` 을 넣으면 앞서 받아 둔 송장이 지워집니다. 「값이 없다」와 「이번에 안 왔다」는
다릅니다.

## 2.3 판매 사건

| `event` | 시점 | CEAdmin 주문 상태 |
|---|---|---|
| `so.created` | 판매주문 등록 | 안 바뀜 |
| `so.confirmed` | 판매주문 확정 | 안 바뀜 |
| `so.allocated` | 재고 할당 | 안 바뀜 |
| `so.picked` | 피킹 완료 | 안 바뀜 |
| `so.invoiced` | 송장 발행 | 안 바뀜 (송장번호는 저장) |
| **`so.shipped`** | **출고 완료** | **`shipping`** |
| `so.cancelled` | 취소 | `cancelled` |

상태를 바꾸지 않는 사건도 **보내 주십시오.** 사건 기록으로 남아 담당자가 진행 상황을
봅니다.

**`so.shipped` 가 두 가지의 시작점입니다.**

- **청구** — CEAdmin 은 이 사건을 받는 순간 청구 준비 여부를 다시 따집니다.
- **환자 안내** — 이 사건을 받으면 환자에게 「제품이 발송되었습니다 · 운송장 번호」
  문자를 보냅니다. 그러니 **송장이 있으면 `ship.tracking_no` 를 함께 실어 주십시오.**

**`so.delivered` 는 보내지 않습니다**(2026-08-15 확정). 위드웍스가 배송 상태를 관리하지
않아 — 택배사 조회 연동이 없고 `trackings` 에 배송상태 컬럼도 없다 — 보낼 값이 없습니다.
그래서 CEAdmin 도 배송완료를 기다리지 않고 **출고완료를 마지막 기준**으로 삼습니다.

## 2.4 반품 사건

| `event` | 시점 | CEAdmin 접수 단계 |
|---|---|---|
| `ro.created` | 반품주문 등록 | 안 바뀜 |
| `ro.rcpt_completed` | 실물이 창고에 들어옴 (`schedule_by_receivings.status` 95·98) | `inspecting` (검수) |
| `ro.confirmed` | 반품주문 확정 (`status` 95) | `inspecting` (검수) |
| `ro.cancelled` | 반품 취소 | `cancelled` |

`ro.rcpt_completed` 는 2026-08-31 위드웍스가 더한 사건입니다. 반품주문의 확정은 창고
담당자가 따로 누르는 일이라 늦게 올 수 있어, 그것만 보면 **물건이 이미 들어왔는데도
CEAdmin 은 「수거중」에 멈춰 있습니다.** 둘 중 먼저 오는 것이 단계를 옮기고, 뒤에 오는
것은 제자리에 멈춥니다.

이 사건에는 `receiving` 블록을 함께 실어 주십시오. CEAdmin 은 `received_date` 를 접수 건의
「입고일」로 적습니다 — 이미 적혀 있으면 건드리지 않습니다.

```json
"receiving": {
  "rcpt_no": "RC2608310001",
  "rcpt_status": "95",
  "rcpt_status_label": "입고완료",
  "received_date": "2026-08-30T12:25:00+09:00"
}
```

### `pl3` — 3PL 진행 상태 · 2026-08-31 새로 요청드립니다

콜로플라스트 요청서 4쪽입니다. **반품 사건마다** 창고가 지금 어디까지 했는지를 실어
주십시오. CEAdmin 의 접수 단계(`status`)와 **따로** 적습니다 — 그것은 「우리가 어디까지
했는가」이고 이것은 「창고가 어디까지 했는가」라, 한 칸에 섞으면 담당자가 승인을 눌러야
할 차례인지 창고를 기다릴 차례인지 갈리지 않습니다.

```json
"pl3": {
  "status": "95",
  "status_label": "입고완료",
  "occurred_at": "2026-08-30T12:25:00+09:00"
}
```

| 필드 | 필수 | 설명 |
|---|---|---|
| `status` | 권장 | 창고가 쓰는 코드 그대로 |
| `status_label` | ✅ | 화면에 그대로 섭니다 |
| `occurred_at` | 권장 | 창고에서 그 일이 벌어진 시각 |

요청서가 적어 온 값은 이렇습니다 — **창고가 쓰는 이름 그대로** 주시면 됩니다.
CEAdmin 은 목록을 정해 두지 않고 받은 글자를 그대로 세웁니다.

> 도착완료 · 검수중 · 검수완료 · 승인대기 · 승인완료 · 입고중 · 입고완료 · 출고중 · 출고완료

`pl3` 가 없으면 CEAdmin 은 `receiving.rcpt_status_label` 로 갈음합니다. 그때는
입고완료 한 걸음만 보입니다.

**반품에는 `ro.*` 를 쓰고 `so.*` 를 쓰지 마십시오.** 반품 사건에 `so.*` 를 쓰면 같은
`ce_order_number` 를 싣기 때문에 **원 주문이 다시 배송중으로 되돌아갑니다.**

창고에서 직접 만든 반품(우리가 보내지 않은 것)은 `ce_return_number` 가 없어도 됩니다.
CEAdmin 은 사건만 기록하고 `200` 으로 답합니다.

## 2.5 출고 상태값

`ship.ship_status` 는 창고 화면의 고르는 칸과 같은 코드입니다.

| 코드 | 뜻 | | 코드 | 뜻 |
|---|---|---|---|---|
| `02` | 신규 | | `55` | 피킹완료 |
| `9` | 취소 | | `57` | 피킹완료/부분출고 |
| `14` | 부분할당 | | `92` | 부분출고 |
| `15` | 부분할당/부분피킹 | | `93` | 출고확정대기 |
| `16` | 부분할당/부분출고 | | **`95`** | **출고완료** |
| `17` | 할당완료 | | `98` | 오더종결 |
| `51` | 피킹중 | | | |
| `52` | 부분피킹 | | | |
| `53` | 부분피킹/부분출고 | | | |

CEAdmin 이 환자에게 「보냈습니다」라고 말하는 것은 **`95` 출고완료**와 **`98` 오더종결**
뿐입니다. 부분출고(`16` · `53` · `57` · `92`)에는 보내지 않습니다 — 나머지가 남아 있는데
발송 안내를 보내면 환자는 전량이 온 줄 알고 기다리다 다시 묻습니다.

**판매주문 상태(`status`)는 다른 체계입니다.** 그쪽은 `02` 등록 · `03` 확정 · `95` 확정 ·
`99` 취소입니다. 같은 `95` 라도 `status` 면 판매 확정이고 `ship.ship_status` 면
출고완료라 뜻이 다릅니다 — 섞지 말아 주십시오.

## 2.6 CEAdmin 이 돌려주는 값

| 상황 | 코드 | 몸 |
|---|---|---|
| 정상 처리 | `200` | `{"success":true}` |
| 같은 `event_id` 가 다시 옴 | `200` | `{"success":true,"message":"Already processed"}` |
| 우리 표에 없는 주문/반품 | `200` | `{"success":true,"message":"Order not found — event recorded"}` |
| 비밀 불일치 | `401` | `{"success":false,"message":"Unauthorized"}` |
| 형식 오류 | `422` | `{"success":false,"message":"Validation failed","errors":{...}}` |
| 우리 쪽 비밀 미설정 | `503` | `{"success":false,"message":"Webhook not configured"}` |

**모르는 주문에도 `200` 을 줍니다.** 다시 보낸다고 우리에게 그 주문이 생기지는 않고,
사건은 이미 우리 표에 남아 나중에 볼 수 있습니다.

## 2.7 지켜 주셔야 할 것

1. **재시도** — 응답이 `2xx` 가 아니거나 시간이 초과되면 다시 보내 주십시오. 간격을
   늘려 가며(1분 → 5분 → 30분 → 2시간) 몇 차례 시도하고, 그래도 안 되면 로그에 남기고
   포기하십시오.
2. **재전송할 때 `event_id` 유지** — 새로 매기면 중복으로 쌓입니다. 같은 값이면 CEAdmin
   이 `200 {"message":"Already processed"}` 로 답하고 아무것도 두 번 하지 않습니다.
3. **`4xx` 는 재시도하지 마십시오** — 형식이 틀린 것이라 다시 보내도 같습니다.
4. **동기 호출 금지** — 출고 처리 트랜잭션 안에서 보내지 마십시오. CEAdmin 이 느리면
   위드웍스 업무가 멈춥니다. 큐에 넣어 뒤에서 보내 주십시오.
5. **순서는 보장하지 않아도 됩니다** — CEAdmin 은 온 것만 덮으므로 `so.picked` 가
   `so.shipped` 뒤에 도착해도 송장이 지워지지 않습니다.
6. **보낸 기록을 남겨 주십시오** — 사건, 주문번호, 응답 코드, 시도 횟수. 안 갔을 때
   무엇이 빠졌는지 그것으로 찾습니다.

# 3. 시험해 보기

## 3.1 위드웍스 → CEAdmin

```bash
curl -X POST https://<CEAdmin 주소>/api/webhook/withworks \
  -H "Content-Type: application/json" \
  -H "X-Withworks-Secret: <비밀>" \
  -d '{
    "event_id": "TEST-0001",
    "event": "so.shipped",
    "ce_order_number": "ORD-0028",
    "so_no": "S2608280001",
    "occurred_at": "2026-08-31T14:05:00+09:00",
    "ship": { "ship_status": "95", "ship_status_label": "출고완료",
              "tracking_no": "1234567890" }
  }'
```

**보실 것**

1. `200 {"success":true}` 가 오는가
2. **같은 요청을 한 번 더** 보내면 `{"message":"Already processed"}` 가 오는가
3. 비밀을 틀리게 보내면 `401` 이 오는가

## 3.2 단계별로

`so.created` → `so.confirmed` → `so.allocated` → `so.picked` → `so.invoiced` →
`so.shipped` 순서로 하나씩 보내며 매번 `200` 이 오는지 보십시오. CEAdmin 주문 상세의
「창고 이력」에 여섯 줄이 차례로 쌓이면 제대로 붙은 것입니다.
