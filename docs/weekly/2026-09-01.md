## 2. 개발 — 적용한 업무

### 2.1 입금 내역 *(신규 화면)*

돈이 들어왔는지는 통장을 봐야 아는데, 그 통장이 화면 밖에 있었습니다. 토스 가상계좌로
받은 건만 저절로 확인되고, 무통장입금과 기관 환급금은 담당자가 인터넷뱅킹과 화면을
번갈아 보며 맞췄습니다.

| 무엇이 가능해졌나 | 지금 상태 |
|---|---|
| **통장 내역 받아 오기** | 팝빌 계좌조회로 긁어 옵니다. 서른 분마다 저절로 돌고, 「지금 가져오기」로 곧바로 받을 수도 있습니다 |
| **주문에 잇기** | 목록에서 주문번호를 적으면 그 줄에서 걸립니다. 비우고 저장하면 풀립니다 |
| **환자별 분리** | 지자체가 여러 환자 건을 통으로 보낸 입금을 갈라 각 주문에 겁니다. 원본 줄은 통장이 준 그대로 남습니다 |
| **한 번에 마감** | 갈라 놓은 건들을 한 번에 닫습니다. 무엇으로 닫았는지(통장 줄·입금자·금액)를 각 건에 남깁니다 |
| **세 갈래로 보기** | 환자 본인부담금 · 기관 환급 · 미정산 |

정산/회계와 따로 둔 까닭이 있습니다. 그쪽은 「얼마를 받아야 하는가」를 세고 이쪽은
「무엇이 들어왔는가」를 봅니다. 맞추는 일이 그 사이에 있습니다.

**아직 비어 있습니다.** 팝빌에 계좌를 등록하고 정액제를 신청해 주셔야 내역이 들어옵니다
(3장 참조).

### 2.2 Finance — 재무가 보는 여섯 목록 *(신규 화면)*

담당자가 일하는 화면에서는 「이 달에 얼마가 오갔나」를 알 수 없었습니다. 주문 관리는
건별 처리를 위한 자리이고, 정산/회계는 입금을 맞추는 자리입니다.

여섯을 한 화면의 탭으로 두었습니다 — 묻는 것이 같고(기간), 여는 사람이 같고, 무엇보다
여섯을 오가며 견주어 보기 때문입니다.

| 탭 | 무엇을 보나 |
|---|---|
| 통합주문내역 | 전체 주문 현황 및 매출 |
| 정산내역 · 환자결제(10%) | 본인부담금 입금 확인 |
| 정산내역 · 공단ㆍ지자체(90%) | 기관 지급금 관리 |
| 미정산내역 | 미수금 — 누가 안 냈는지, 며칠 지났는지 |
| 반품환불내역 | 매출 차감 및 환불 |
| 부가세신고내역 | 신고자료 생성 및 검증 |

모든 탭이 엑셀로 나가고, 주문번호가 첫 칸이라 탭끼리 이어집니다. 기간은 「이번 달」·
「지난 달」 단추로도 고릅니다.

**PG 정산 정보는 세우지 않았습니다.** PG 정산일·정산금액·수수료·회사계좌 입금은 토스
정산을 받아 와야 아는 값인데 그 연동이 없습니다. 모르는 것을 0으로 적으면 「수수료가
없다」로 읽힙니다.

### 2.3 PG 결제 *(신규 화면)*

토스 결제는 정산/회계의 「가상계좌 매칭」 탭에만 있었습니다. 거기는 발급하고 입금을
기다리는 자리라, 이미 끝난 결제나 카드 결제를 되짚어 볼 곳이 없었습니다.

상태별 건수를 먼저 보여 주고, 발급일시·결제수단·상태·금액·가상계좌 정보·입금기한·
입금일시·토스 주문번호를 세웁니다.

입금 내역과 다른 것을 봅니다. 그쪽은 통장에 찍힌 줄이고 이쪽은 PG가 확인해 준 결제입니다.
가상계좌로 받은 돈은 둘 다에 나타나는데, **어긋나면 그것이 곧 봐야 할 일**이라 한 화면에
합치지 않았습니다.

### 2.4 되돌리는 건 — 사유가 정하는 것 *(확장)*

「단순변심이 아닌 교환·반품은 금액 조정 없고 발행 내역에도 넣지 말 것」이라는 요청을
글자 그대로 옮기면 자격 변경까지 걸립니다. 그것은 이미 받은 돈을 돌려주는 건이라 조정이
반드시 있어야 합니다. 그래서 한 줄로 가르지 않고 **사유마다 하나씩** 정하도록 표로
옮겼습니다.

| 사유 | 배송비 | 금액조정 | 발행포함 |
|---|---|---|---|
| 단순 변심 | 고객 | 있음 | 포함 |
| 사이즈 교환 | 고객 | 없음 | 불포함 |
| 상품 불량 | 판매자 | 없음 | 불포함 |
| 오배송 | 판매자 | 없음 | 불포함 |
| 배송 지연 | 판매자 | 없음 | 불포함 |
| 자격 변경 | 접수 때 고름 | 있음 | 포함 |
| 기타 | 접수 때 고름 | 있음 | 포함 |

가른 잣대는 **「돈이 오갔는가」**입니다. 물건만 바꿔 주는 교환은 돈이 그대로라 조정할
것도 되돌릴 발행도 없습니다.

규칙이 실제로 뭅니다 — 금액조정을 끈 사유는 금액조정 주문을 세우지 않고, 발행포함을 끈
사유는 세금계산서·현금영수증을 되돌리지 않습니다. **이게 특히 중요합니다**: 처음부터
발행에 들지 않은 건을 취소하면 멀쩡한 발행이 국세청까지 취소되어 갑니다.

**이 값은 화면에서 고칩니다**(마스터 관리 › 반품 사유). 앞으로도 바뀔 규칙이라, 바뀔
때마다 배포를 기다리게 두면 결국 아무도 안 고칩니다.

### 2.5 교환·반품·취소 — 환불의 자취와 알림 *(확장)*

지금까지는 「얼마를 어느 계좌로 돌려줬는가」까지만 남았습니다. 카드 취소가 승인됐는지,
통장을 언제 물렸는지, 환불분 현금영수증 번호가 무엇인지를 알려면 팝빌과 토스 화면을
따로 열어 맞춰 봐야 했습니다.

| 무엇이 가능해졌나 | 지금 상태 |
|---|---|
| **환불 처리 자취** | 카드사·유효기간·승인번호·카드결제 취소·무통장결제 취소·취급점·환불기관정보·환불 현금영수증번호와 구분·적요·담당자메모 |
| **반품 Lot** | 되돌아온 물건의 Lot을 주문 줄에 적습니다 |
| **3PL 진행 상태** | 창고가 알려 주는 그대로 적습니다. 우리 접수 단계와 따로 둡니다 — 그것은 「우리가 어디까지 했는가」이고 이것은 「창고가 어디까지 했는가」입니다 |
| **접수자 알림** | 창고가 움직이면 알람과 채팅이 함께 갑니다. 토스트는 보고 있을 때만 눈에 들어, 자리를 비운 사이 지나간 것은 채팅에 남습니다 |
| **팀장 승인 요청** | 단계가 승인 차례에 닿으면 저절로 나갑니다. 접수자가 따로 부탁하게 두면 잊습니다 |
| **환자 안내** | 상세 화면에서 접수자가 눌러 보냅니다. 알림톡 틀이 있으면 알림톡, 없으면 문자입니다 |

이름도 요청대로 고쳤습니다 — 「갈래」→「사유」, 「종류」→「유형」, 「전부」→「전체」.

### 2.6 청구 관리 — 상태 일곱과 기한 *(확장)*

「청구완료」와 「승인」이 한 칸을 두고 다투고 있었습니다. 화면은 둘을 따로 세는데
상태값은 하나였고, **「보류」가 아예 없어 「우리가 아직 안 낸 것」과 「내고 기다리는 것」이
한 숫자**였습니다.

청구 전 → 청구중 → 청구완료 → 승인 / 반려 / 보류 / 취소, 일곱으로 세웠습니다.
반려 뒤의 걸음(관할 지사 검토결과 반려 → 재신청(승인대기) → 재신청완료)은 **상태가 아니라
별도 칸**입니다. 재신청 중에도 그 건은 여전히 반려된 건인데, 상태를 옮기면 「반려 몇 건」이
갑자기 줄어 다시 내야 할 일이 눈에서 사라집니다.

**청구 기한을 셉니다** — 출고일 + 2주. 아직 청구하지 않은 건에만 남은 날이 서고, 사흘
안이면 노랗게, 넘겼으면 「6일 초과」로 붉게 섭니다. 이미 낸 건에 적어 두면 무엇이 급한지가
묻힙니다.

이름도 「공단청구」에서 **「청구」**로 바꿨습니다. 지자체 청구도 이 자리에서 하는데
공단이라 적어 두면 지자체 건을 여기서 찾을 생각을 못 합니다.

### 2.7 정산 상태 — 마감과 확정 *(신규)*

「마감」은 셈을 닫은 것이고 「확정」은 그 뒤 되돌릴 수 없게 잠근 것입니다. 둘을 가른
까닭은, 닫고 나서도 며칠은 고칠 일이 생기기 때문입니다. 잠그는 것을 따로 두지 않으면
담당자가 닫기를 미루게 되고, 그러면 어디까지 봤는지가 영영 안 남습니다.

**못 받은 돈이 있어도 닫을 수 있습니다.** 요청서가 그렇게 적었고(「3PL 샘플로 입고 잡고
마감 확정」) 실제로 그런 건이 있습니다. 다만 말없이 닫히면 나중에 아무도 못 찾으므로
**남은 돈이 있으면 까닭을 묻습니다 — 막지는 않습니다.**

**배송비는 받을 돈에서 뺐습니다.** 08-24부터 받지 않기로 했는데 그 전 26건에 3,000원이
적혀 있어, 그것까지 받을 돈으로 세면 이미 끝난 건이 영영 「3,000원 모자람」으로 남습니다.
정산/회계의 칸과 합계, 입금 예정액, 안내 문자의 금액에서 모두 걷었습니다.

### 2.8 현금영수증·전자세금계산서 — 팝빌 항목 전부 *(확장)*

팝빌이 주는 스물몇 칸 가운데 여덟만 세우고 있었습니다. 전송 결과나 취소 사유를 보려면
팝빌 사이트를 따로 열어야 했습니다.

작성일자·발행일자·품목명·신분확인번호·휴대폰번호·이메일·공급가액·세액·봉사료·과세형태·
승인번호·원본 승인번호와 거래일자·상태·취소 사유·전송결과·전송일시·전송결과일시·
연동관리번호·가맹점을 모두 세웠습니다. 전자세금계산서도 같습니다.

**팝빌 발행 건을 우리 주문에 이었습니다.** 이을 열쇠는 이미 있었는데(현금영수증은
주문번호, 세금계산서는 관리번호에 심긴 주문 id) 읽어 둔 자리가 없었습니다.
쌓인 것도 이었습니다 — 현금영수증 13건 전부, 세금계산서 6건 중 5건(하나는 옛 형식).

찾는 칸도 늘렸습니다 — 휴대폰번호와 신분확인번호. 취소 건은 금액이 마이너스로 서서,
이 표만 보고도 이 기간에 얼마가 남았는지 읽힙니다.

### 2.9 발행에 필요한 값이 쌓이게 *(개선)*

세금계산서 상호·대표가 주문 37건 가운데 **3건**에만, 거래처 현금영수증번호는 10명 가운데
**0명**에게 적혀 있었습니다. 칸이 없어서가 아니라 **발행 창이 늘 빈칸으로 열려**, 담당자가
매번 같은 값을 다시 치고 그 값이 그 주문에만 남았기 때문입니다.

- **열 때** — 거래처가 적어 둔 현금영수증번호·소득공제 구분으로 엽니다. 세금계산서는
  같은 사람의 지난 발행에서 상호·대표·이메일을 가져옵니다.
- **닫을 때** — 발행하며 쓴 값을 거래처에 남깁니다. 이미 적혀 있으면 덮지 않습니다.

### 2.10 서식 둘 *(신규)*

**의료용품 구입 확인서** — 거래처 한 사람이 지금까지 무엇을 얼마에 샀는지를 한 장에
모읍니다. 거래처 목록에서 내려받고, 상세에서 문자나 메일로 보냅니다(메일은 주소가 있을
때만). 보내는 링크는 **이레가 지나면 죽습니다** — 사람에게 보내는 주소가 영영 살아 있으면
그 주소를 받은 누구든 남의 구입내역을 볼 수 있습니다.

**청구 자료 묶음** — 지자체는 서류를 등기로 보내므로 다섯을 한 번에 뽑아야 하는데,
하나씩 눌러 내려받으면 다섯 번 누르는 동안 한둘을 빠뜨립니다. 처방전·개인정보 동의서·
거래명세서·전자세금계산서를 한 PDF로 엮고, **첫 쪽에 무엇이 들었고 무엇이 빠졌는지**를
적습니다. 빠진 채로 부치면 반려되어 돌아오고, 그때는 이미 우편 값이 나간 뒤입니다.

### 2.11 목록이 함께 쓰는 칸 *(확장)*

「모든 화면의 항목이 최종으로 보이게」라는 요청에 따라, 목록이 함께 쓰는 칸을 63개에서
**72개**로 늘리고 쓰는 화면을 4곳에서 **10곳**으로 넓혔습니다. 새로 든 칸은 판매번호·
출고일자·Lot·유효기간·Operation 담당자·마감 체크·참고사항입니다.

칸의 이름과 차례가 어디서나 같습니다 — 화면을 옮길 때마다 다시 읽는 법을 배우지
않게 하려는 것입니다.

### 2.12 요청서 이전 — 화면과 절차 *(08-26 ~ 08-30)*

| 무엇이 달라졌나 | |
|---|---|
| **거래처 관리가 환자 정보의 정본** | 여러 화면에서 고치던 환자 정보를 한 곳으로 모았습니다. 고치면 열려 있는 화면들이 따라옵니다 |
| **개인정보 동의를 한 자리에서** | 위임동의 서명 화면에서 함께 받습니다. 한 번 받은 사람에게 다시 묻지 않고, 물을 때는 다 묻습니다 |
| **주문 등록 화면 재편** | 주문 연계 탭을 걷어 주문 제품 아래로 내리고, 「주문 목록」 탭에서 다음에 손댈 건을 고릅니다 |
| **처방전이 곧 주문 관리에** | 올리면 그 자리에서 주문 관리에도 섭니다. 그림이 없어도, 제품을 안 골랐어도 |
| **되돌리는 건이 절차서대로** | 교환·반품·취소가 절차서의 다섯 갈래를 그대로 밟습니다 |
| **출고 안내 문자** | 창고가 출고하면 운송장 번호와 함께 나갑니다 |
| **검수와 동의 없이 주문이 나가지 않습니다** | |

## 3. 확인·결정이 필요한 사항

| 구분 | 내용 |
|---|---|
| **운영 확인** *(신규 · 중요)* | **출고 전에 국세청 신고가 나가고 있었습니다.** 자동 발행이 켜져 있는데 조건이 「입금 확인」 하나뿐이라, 물건이 창고에 있는 채로 세금계산서·현금영수증이 먼저 나갔습니다. 요청서 8·9쪽의 「입금 **및 출고**」 조건을 넣어 막았습니다. **적용 뒤에는 출고돼야 발행됩니다** — 「입금은 됐는데 계산서가 안 나온다」는 문의가 오면 그 건은 출고 전 상태입니다 |
| **데이터 확인** *(신규)* | **총 주문금액이 총액이 아닙니다.** `total_amount` 은 「환자가 낼 돈」(본인부담＋배송비)이라, 37건 가운데 **30건**이 부담금 합과 어긋납니다(예: 총액 84,000 / 환자 81,000＋기관 729,000). Finance는 환자 몫＋기관 몫으로 세도록 했지만, 이 칸의 뜻을 그대로 둘지 정해 주십시오 |
| **승인 필요** *(신규)* | **팝빌 계좌 등록 + 정액제 신청.** 끝나야 입금 내역에 통장 거래가 들어옵니다. 그전까지는 화면이 안내만 띄웁니다 |
| **정보 필요** *(신규)* | **콜로 모 계좌** — 은행 코드·계좌번호·예금주 |
| **창고 요청** *(신규)* | 위드웍스에 세 가지를 요청드렸습니다 — `ship.shipped_at`(출고일자) · `ship.items[]`(Lot·유효기간) · `pl3`(3PL 진행 상태). 저쪽이 실어 보내야 그 칸들이 찹니다 |
| **정책 확인** *(신규)* | **거래명세서의 발행일**이 「만드는 그날」로 찍히고 있습니다. 같은 명세서를 다음 달에 다시 뽑으면 날짜가 달라집니다. 요청서에 「출고일 → 결제일로 변경 요청 예정」이라 적혀 있어 손대지 않았습니다 |
| **정책 확인** *(신규)* | **자동 테스트 32건이 실패**하고 있습니다. 이번 주 작업 전후가 같아 기존 실패이지만, 그대로 두면 새로 생긴 고장을 가려 주지 못합니다. 언제 손볼지 정해 두시는 편이 좋겠습니다 |
| 승인 필요 *(이어짐)* | **알림톡 템플릿**. 교환·반품 진행 안내 틀(`return_progress`)을 팝빌에 올려 주시면 문자 대신 알림톡으로 나갑니다 |
| 확인 예정 *(이어짐)* | **NICE 본인확인** 운영 연결 테스트 |
| 데이터 오류 *(이어짐)* | 회사 정보의 **상호** 자리에 사업자번호가 들어 있음 |
