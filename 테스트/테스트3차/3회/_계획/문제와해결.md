# 테스트 3차 · 3회 — 문제와 해결

> 진행하다 막힌 자리와 그 해결을 그때그때 적습니다.
> 2회까지의 것은 `테스트3차/2회/_계획/고친것과에러.md`.

## ⓪ 팩스가 시늉 없이 진짜 나간다 · 고침 `cd516c7` (3회 시작 전)

**증상** 문자에는 `POPBILL_SMS_SIMULATE` 가 있는데 **팩스에는 없었다.**
화면을 처음부터 끝까지 훑어 보는 시험에서 ［팩스 발송］을 누르면 팝빌로 진짜 나간다 —
2회에서는 접수번호가 모두 진짜였다(`026090415402900003` 등).

**왜 나쁜가** 종이가 나가고 포인트가 깎인다. 받는 번호를 시험 번호로 돌려 두어도
나가는 것은 나가는 것이다. 그리고 「보냈다는 가정으로 진행」하고 싶어도 길이 없어,
팩스 화면만 통째로 건너뛰게 된다 — 그러면 서류 세기ㆍ합본ㆍ받는 곳이 시험에서 빠진다.

**고침** `POPBILL_FAX_SIMULATE` 를 만들었다(`config/popbill.php` · `FaxService::sendFax`).
켜 두면 **합본 만들기ㆍ서류 세기ㆍ받는 곳 고르기까지 그대로 하고 마지막 한 걸음만**
막는다. 접수번호 자리에는 `SIMFAX-…` 가 선다. **기본값은 꺼짐** — 운영에서 조용히
안 나가는 일이 없어야 한다.

## ① 거래처 창에서 주민등록번호를 넣어도 생년월일이 빈 채다 · 고침 `9551cff`

**어디** 거래처 관리 → ［거래처 등록］ 창 (주문 등록 화면도 같은 창을 쓴다)
**증상** 주민등록번호를 적어도 바로 옆 「생년월일」 칸이 채워지지 않는다.
주문 등록 화면은 진작 자동으로 채우고 있었다(`rnRecalc`).

**왜 나쁜가** 같은 번호를 보고도 사람이 앞 여섯 자리를 손으로 옮겨 적어야 한다.
적지 않으면 빈 채로 남는데, **나이는 성년과 미성년을 가르는 값**이다. 미성년이면
보호자 서명과 법정대리인 신분증이 더 필요하다. 두 화면이 같은 번호를 보고 다른 일을
할 까닭이 없다.

**고침** 창에도 같은 수를 두었다(`peBirthFromRrn`). 사람이 손으로 고쳐 둔 값은 덮지
않는다 — 이 수가 채워 둔 값만 다시 적는다.

**확인** 1번 김지훈에서 `850216-1038514` 를 넣자 그 자리에서 `1985-02-16`.

## ② 업로드 화면의 담당자 목록에 관리자가 없다 · 고침 `9551cff`

**어디** 처방자료 업로드 → 처방전 설정 → 담당자
**증상** 「원동희」를 쳐도 **「그런 담당자가 없습니다」**. 지금 로그인한 사람인데도.

**까닭** 그 화면만 `User::where('role','manager')` 를 보았다. 처방전 목록 화면은
`whereIn('role',['admin','manager'])` 를 본다. 지금 열 사람 가운데 **다섯이 관리자**라,
절반은 담당자로 고를 수 없었다.

**왜 나쁜가** 담당자를 비운 채 올리게 된다. 그러면 **창고 소식이 갈 곳이 없다** —
`OrderNotice` 는 주문의 담당자를 먼저 보고, 없으면 처방전에 배정된 사람을 본다.
둘 다 비면 예전처럼 모두에게 띄우기만 하고 채팅에는 남지 않는다.

**고침** 두 화면이 같은 잣대를 보게 맞췄다.

## ③ 결과지가 여러 장이면 팩스가 500 으로 끝난다 · 고침 `12d4a81`

**어디** 주문 등록 → ［팩스 발송］ → ［팩스 전송］
**증상** 화면에 **「❌ Server Error」** 만 뜬다. 무엇이 잘못됐는지 알 길이 없다.

**까닭** 팩스 제목에 첨부마다 「갈래: 파일이름」을 그대로 이어 붙였다.

```
[CE] RX-20260905-004 요양비위임장·등록신청서: 02_자가도뇨소모성_재료_등록신청서_TEST.png
·결과지: 등록처리_결과지_01of18_TEST.png·결과지: 등록처리_결과지_02of18_TEST.png· … (18번)
```

이 건은 제목이 **천 자를 넘어** `fax_histories.title`(varchar 200)에 들어가지 못했다.

```
SQLSTATE[22001]: Data too long for column 'title' at row 1
```

**무엇이 더 나쁜가** 그 자리는 **팩스를 이미 보낸 뒤**다. 팝빌로 나가고 나서 자취를
남기다 죽는다 — 화면은 실패로 보이는데 팩스는 갔다. 담당자는 다시 보내고, **같은
팩스가 두 번 간다.**

**고침 둘**
① 제목을 갈래로 묶는다 — 「요양비위임장·등록신청서·**결과지 18장**·신분증」(45자).
   읽는 사람에게 필요한 것은 「무엇을 몇 장 보냈나」지 파일 이름 열여덟 개가 아니다.
   그래도 넘칠 수 있어 200자에서 자른다.
② 자취 남기는 자리를 감쌌다. 못 남겼으면 **「팩스는 나갔으나 전송 자취를 남기지
   못했습니다 — 다시 보내지 마시고 관리자에게 알려 주십시오」** 로 알린다.

**확인** 결과지 18장 건이 접수번호 `SIMFAX-20260905115426-1477` 로 나가고,
합본 21장이 묶이고, 자취가 제목 45자로 남았다.

## ④ 수량을 고쳐도 표 아래 합계가 옛 값 그대로다 · 고침 `37dff3d`

**어디** 주문 등록 → 주문 제품 → 수량
**증상** 수량을 120 → 180 으로 고치면 **그 줄은 405,000 으로 바뀌는데 아래 합계는
270,000 그대로**다.

**왜 나쁜가** 담당자가 합계를 읽어 환자에게 금액을 말하면 틀린 금액이 나간다.
게다가 **두 숫자가 한 화면에 나란히 서서 서로 다른 말을 한다** — 어느 쪽이 맞는지
알 방법이 없다.

**까닭** 합계줄(`tfoot`)은 표를 그릴 때 한 번만 찍었다. 수량을 고치면 `calcItem` 이
그 줄만 다시 적고 합계는 손대지 않았다.

**고침** 합계 칸에 이름을 붙이고 `calcTotals` 가 함께 적게 했다.

**확인** 120 → 180 → 120 으로 오갈 때마다 합계가 따라 움직인다.

## ⑤ 결제전송 창의 「결제 금액」이 0원이다 · 고침 `(아래 커밋)`

**어디** 주문 등록 → ［결제전송］ 창
**증상** 화면을 열어 둔 채 ［주문 생성 및 연계］를 하고 바로 ［결제전송］을 누르면
**「결제 금액 0원」**. 바로 아래 전송 이력에는 「링크페이 **27,000원** · 문자 보냄」이
서 있다. 새로고침하면 27,000원으로 제대로 보인다.

**까닭** `payAmount` 는 서버가 화면을 그릴 때 `order.total_amount` 를 한 번 찍는다.
그때는 아직 주문이 없어 0 이다. 옆 칸들(알림톡ㆍ문자의 금액)은 `calcTotals` 가 그때그때
다시 적고 있었는데 **이 칸만 빠져 있었다.**

**왜 나쁜가** 그 창에서 바로 링크를 보내는 자리다. 0원을 보면 「금액이 안 잡혔다」고
읽어 보내지 못하고, 화면을 새로 고쳐 다시 들어온다. 게다가 **같은 창 안에서 0원과
27,000원이 나란히 서서 서로 다른 말을 한다.**

**고침** `calcTotals` 가 `payAmount` 도 함께 적게 했다.
