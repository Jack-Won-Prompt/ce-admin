## ① 한 번에 올릴 수 있는 수를 넘으면 파일이 조용히 사라진다 · 고침 `83d8d70`

**어디** 처방자료 업로드
**증상** 김가람은 결과지가 **19장**이라 처방전ㆍ신분증ㆍ등록신청서까지 **22장**이다.
올리면 **「업로드 완료」**가 뜨는데 결과지가 **17장만** 저장된다. 두 장이 어디로 갔는지
아무 말이 없다.

**까닭** PHP 의 `max_file_uploads`(기본 20)를 넘는 파일은 **라라벨이 보기 전에 조용히
버려진다.** 검사 규칙의 `max:40` 은 이미 잘린 배열을 보므로 걸리지 않는다.

**무엇이 나빠지는가** 빠진 것을 아무도 모른다. 그대로 두면 **공단 팩스에도 빠진 채
나가고**, 공단이 서류가 모자라다며 돌려보낼 때 무엇이 빠졌는지 되짚을 자리가 없다.

**고침** 브라우저가 몇 장을 보내는지 함께 적어 보내고, 서버가 받은 수와 견준다.
모자라면 **아무것도 저장하지 않고** 무엇이 막았는지ㆍ어떻게 하면 되는지 알린다.

> 보낸 파일 22장 가운데 20장만 서버에 닿았습니다 — 한 번에 올릴 수 있는 파일이
> 20장으로 막혀 있습니다. 나누어 올리시거나 php.ini 의 max_file_uploads 를 늘려
> 주십시오. 빠진 채로 저장하면 공단 팩스에도 빠진 채 나가므로 아무것도 저장하지
> 않았습니다.

**아울러** 운영 `php.ini` 의 `max_file_uploads` 를 **20 → 60** 으로 올렸다.
고친 뒤 22장이 **하나도 빠짐없이** 들어가는 것을 운영에서 확인했다.

## ② 거래처를 고쳐도 요양비위임장이 옛 값 그대로다 · 고침 `2155595`

**증상** 위임장은 **서명하는 그 순간에 한 번 그려** 파일로 남는다. 그 뒤로는 다시
그리지 않아, 이름이나 연락처를 잘못 적은 채 서명을 받으면 거래처를 고쳐도 종이에는
옛 값이 그대로 남는다. **그 종이가 공단 팩스 합본에 실려 나간다.**

**까닭** 값을 **동의 기록에 찍힌 사진**에서 먼저 읽었다
(`$consent->patient_name ?: $patient?->name`). 서명할 때 환자가 보고 확인한 값이라
그것이 옳다고 보았기 때문이다.

**정한 것** (2026-09-05 지시) — **내용을 다시 그리고 서명은 덮어서 그대로 쓴다.**

**고침 셋**
① 읽는 차례를 뒤집었다 — **지금의 거래처를 먼저** 본다.
② 거래처를 저장하면 그 사람의 위임장을 **모두 다시 그린다.** 이름ㆍ연락처가 그대로면
   하지 않는다 — 고치지도 않은 것을 다시 그리면 자취만 늘어난다.
③ **파일 이름도** 종이에 적히는 값을 따른다. 안은 새 번호인데 이름은 옛 번호이면
   파일만 보고 고른 사람이 옛 것을 보낸다.

**서명은 덮지 않는다.** 동의 기록의 서명 이미지를 그대로 다시 얹으므로 사람이 그은
획은 바뀌지 않고 글자만 새로 앉는다. 동의 기록 자체도 손대지 않는다 —
그것은 「그때 무엇을 보고 서명했는가」를 말하는 자취다.

> **남는 물음** — 성명ㆍ주민등록번호까지 다시 그리므로, **환자가 보지 않은 이름으로
> 위임장이 나갈 수 있다.** 서명이 남아 있어 위임 자체가 없어지는 것은 아니나,
> 신원이 바뀌는 수정이라면 다시 서명받는 편이 옳다.

## ③ 같은 초에 두 번 그리면 위임장 파일을 스스로 지운다 · 고침 `14558fc`

**②를 만들고 나서 드러난 것.** 거래처를 고칠 때마다 다시 그리게 하니 잇달아 부르는
일이 흔해졌다.

**까닭** 파일 이름이 `delegations/{rx}_{YmdHis}.pdf` 라 **초 단위**다.

```
① 파일 F 를 쓴다 → 줄 A 를 만든다                       F 있음
② 같은 초에 다시: F 를 덮어 쓴다
   → 옛 줄 A 의 파일을 지운다 = **방금 쓴 F 를 지운다**
   → 줄 B 를 만들어 F 를 가리킨다                        F 없음 · 줄만 남음
```

**무엇이 나빠지는가** 화면에는 위임장이 **있는 것으로 보인다.** 공단 팩스가 그 줄을
믿고 붙이려다 그때서야 없는 것을 안다.

**고침** 이름에 무작위 여섯 자를 더해 겹치지 않게 하고, 지우기 전에 **「방금 쓴 것과
같은 자리인가」**를 한 번 더 본다. 파일을 잃는 것보다 한 장 더 남는 것이 낫다.

**확인** `258_20260905151026_9cPSWw.pdf` — DB 와 서버 파일이 맞는다.

## ⓐ 내가 만든 어긋남 — 로컬 tinker 로 위임장을 그렸다 (고칠 것 아님, 새길 것)

DB 는 운영과 같은데 **storage 는 로컬과 서버가 따로**다. ②를 확인하면서 **로컬
tinker** 로 `saveDelegationDocument()` 를 불렀더니 —

```
DB(운영)   → delegations/258_20260905145217.pdf   ← 로컬 디스크에만 있음
서버 디스크 → delegations/258_20260905144312.pdf   ← DB 에는 없음
```

**운영 화면에서 열면 파일을 못 찾는다.** 운영 화면에서 거래처를 저장해 바로잡았다.

> **파일을 만드는 일은 반드시 운영 화면에서 한다.** 로컬 tinker 로 부르면 DB 는
> 운영에 쓰이고 파일은 로컬에 떨어져 자취가 어긋난다.

## ⓑ 운영과 로컬의 주문 제품 화면이 다르다 (새길 것)

| | 로컬 | **운영** |
|---|---|---|
| 생김새 | 카드형 표 | **표뷰(wwGrid)** |
| 제품 고르는 길 | `pac-input-0` 칸에 치고 `pacSearchBtn(0)` | ［제품 추가] → `openProductSearch(0)` → **`.cg-modal-search`** 칸 |

운영에서 시험할 때는 **`.cg-modal-search`** 에 코드를 넣는다(3자 이상).

**증상으로 보였던 것** 병원 조회 창에서 「순천향」ㆍ「31100767」을 넣어도 목록이 빈다.

**실은** `page.fill('#hpQ', …)` 은 **값만 넣고 검색을 부르지 않는다.**
화면은 사람이 칠 때 `oninput`ㆍ`Enter` 로 `hospitalSearch()` 를 부르게 되어 있다.
`window.hospitalSearch()` 를 곧장 부르니 두 줄이 제대로 떴다.

```
순천향대학교 부속 부천병원  31100767
순천향대학교 부천병원      31100767
```

**새길 것** — 브라우저로 몰 때 **칸에 값만 넣는 것과 사람이 치는 것은 다르다.**
자동완성ㆍ조회가 붙은 칸은 그 화면이 부르는 함수를 함께 불러야 한다.

**곁들여 알게 된 것** — 같은 요양기관기호 `31100767` 로 **병원이 둘** 등록돼 있다.
기호는 공단 청구의 열쇠라 언젠가 하나로 합쳐야 한다. (이번에는 처방전 원본과 같은

## ④ ~~기초(의료급여)인데 재평가 대상자가 N 인 채로 지나간다~~ · **되돌림** `766dc17`

> **이 항목은 틀렸다.** 사용자 정정 — 「**기초는 재평가 없음, 공단만 재평가 있음.**」
> `df108da` 로 세운 것(자동 Y·빨간 테·화면 문·서버 문)을 `766dc17` 에서 남김없이 걷었다.
> 아래는 무엇을 왜 잘못 읽었는지 남겨 두는 기록이다. 이 자리에 정말 필요한 것은
> **공단 재등록 알림**(⑦)이었다.

**물음에서 시작했다** — 「기초(의료급여) 재평가 대상자」가 사람이 넣는 값인가?
**맞다.** `basic_reeval`(Y/N)ㆍ`basic_reeval_due`(기한) 둘 다 담당자가 고르고 적는 칸이고
검사 규칙도 `nullable` 이다. 자동으로 정해지는 곳이 없었다.

**무엇이 나쁜가** 기초 수급자는 자격을 **주기로 다시 확인**받는다. 기한을 놓치면
자격이 끊긴다 — 그러면 **공단 청구가 통째로 반려되고, 이미 나간 물건 값은 우리가
떠안는다.** 그런데 자격을 「기초」로 바꿔도 재평가는 N 인 채였고 화면은 아무 말도
하지 않았다. 사람 기억에 맡길 자리가 아니다.

**고침 셋**
① 자격을 「기초」로 고르면 재평가 대상자가 그 자리에서 **Y** 로 선다.
   사람이 손으로 고쳐 둔 값은 덮지 않는다.
② 기초인데 기한이 비어 있으면 그 칸에 **빨간 테**를 둘러 눈에 띄게 한다.
③ 기초인데 대상자가 Y 가 아니거나 기한이 비면 **창고로 보내지 않는다** —
   화면(`gateBasicReeval`)과 서버 둘 다에서 막는다.

> 기초(의료급여) 건은 재평가 대상자와 기한을 채워야 창고로 보낼 수 있습니다 —
> 기한을 놓치면 자격이 끊겨 공단 청구가 반려됩니다.

거래처 창에는 자격 칸이 없다(자격은 처방전에 붙는 값)라 묶는 자리는 주문 등록 화면 하나다.

**확인할 자리** — **5번 정시우(기초ㆍ지자체)** 에서 이 문이 실제로 걸리는지 본다.

## ⑤ 지자체(시군구청) 건인데 **팩스로 보낼 수 있었다** · 고침 `4e6f679`

**어디** 주문 등록 → ［공단 팩스 전송]

**무엇이 나쁜가** 청구처가 **지자체**면 이 건은 **등기로 부치는 건**이다. 그런데
5번 정시우(기초·용인시 기흥구청)에서 팩스 단추가 그대로 살아 있었다. 누르면

등기를 부치지 않는다. **청구가 통째로 멈춘다.**

**고침** 두 겹으로 막았다.

|---|---|

```php
if ($request->recipient_type === 'nhis'
    && optional($prescription->billingOffice)->kind === 'local') {
    return response()->json(['success' => false,
        'message' => '지자체(시군구청) 건은 팩스로 보내지 않습니다 — 등기로 부치십시오.'], 422);
```
