# 위드웍스에서 할당 → 피킹 → 송장 → 출고 하는 법

소스(`E:\xampp\htdocs\withworks`)를 읽어 알아낸 절차. 화면만 보고는 알 수 없는 자리가 몇 군데 있다.

## 1. 할당 — 통합 출고 관리

`/integrated_ship` → 판매번호로 검색 → 줄을 **더블클릭**해 상세를 연다(URL 에 `#출고id` 가 붙는다)
→ 아래 「**미할당**」 탭 → 줄 체크 → 「**부분 할당**」 → 「실행하시겠습니까?」에 **Yes**

→ 출고 상태가 **「할당완료」**, 로케이션(MJ-07-26-03)에서 PICKTO 로 잡힌다.
→ CE 로 **`so.allocated`** 가 오고 주문이 `allocated` 로 오른다.

> **「지정 할당」은 쓰지 않는다** — 로케이션 재고를 손으로 골라야 하는데 검색이 「No data」로 뜬다.

## 2. 피킹 — **작업 관리** (`/management`, 화면 제목은 「작업 관리」)

> **「피킹」 화면(`/direct_picking`)의 「지정 피킹」은 이미 할당한 건에 쓸 수 없다.**
> 소스가 그대로 말한다 —
> 「해당 건은 이미 할당되어 있습니다. 지정피킹은 할당 없이 사용하는 기능으로,
> **작업관리 화면에서 피킹해 주세요.**」 (`DirectPickingController` 화면 코드)

`/management` → 출고번호로 검색 → 줄을 고르고 아래 **순서를 지켜** 두 칸을 채운다.

| 차례 | 칸 | 값 |
|---|---|---|
| ① | **작업 수량**(`work_qty`) | 잔여 수량 전부 |
| ② | **작업 바코드**(`standard_code`) | 그 줄의 바코드 그대로 |

→ 「**피킹 확정**」 → 「실행하시겠습니까?」에 **Yes**

### 순서를 지켜야 하는 까닭

바코드를 넣으면 화면이 이렇게 셈한다(`get_all_details.blade.php`) —

```
목표수량(target_qty) = 작업수량(work_qty) × 바코드에 적힌 수량(unit_qty)
```

**작업수량이 비어 있으면 1 로 채워 넣는다.** 그래서 바코드만 먼저 넣으면
목표수량이 **1** 이 되어 한 번에 한 개씩만 피킹된다.
(이 시험에서 그렇게 두 번 헛돌아 540 → 538 이 되었다.)

서버는 `target_qty[출고상세id]` 를 그대로 피킹 수량으로 쓴다
(`ManagementController@picking` → `$pickQty = $qtyList[$pick->id]`).

### 바코드를 안 넣으면 — 「전산 피킹」 창

바코드 칸이 비면 「피킹확정 대상 중 작업에 대한 바코드가 없습니다. 그래도 진행하시겠습니까?」
→ Yes → **「전산 피킹」 창**이 뜨고 **아이디ㆍ비밀번호ㆍ사유**를 받는다.

이 창은 로그인 계정이 **창고사(`account_type = 40`)** 일 때만 뜬다.
서버는 **이메일**로 사람을 찾는다 — `User::where('email', $manualUserId)`.
로그인 아이디(JHW)를 넣으면 「이메일 혹은 비밀번호가 일치하지 않습니다」로 막힌다.

**바코드를 채우면 이 확인 자체를 건너뛴다**(`!$manualUserValidation && !$stdCode` 일 때만 막는다).
그래서 이 시험에서는 바코드를 넣는 길로 갔다.

### CE 로 언제 오는가

```
so.picked = 합계 피킹수량 >= 합계 수량      ← 전량 피킹만 「피킹 완료」
```
**부분 피킹은 웹훅을 쏘지 않는다**(`CeAdminController`). 훅 자체는
`schedule_by_ship_details` 의 `alloc_qty`ㆍ`picking_qty`ㆍ`ship_qty` 가 바뀔 때 뛴다.

# 이어서 알아낸 것 (3ㆍ4단계)

## 3. 송장 — 두 갈래가 따로 있다

| 자리 | 무엇을 채우는가 | CE 웹훅 |
|---|---|---|
| 통합 출고 관리 → **3PL 송장출력** | `trackings` 표 | **`so.invoiced`** (`Tracking::created` 훅) |
| 출고 확정/마감 → **송장번호 칸** | `schedule_by_ships.mst_tracking_no` | (없음) |

**출고 확정 화면에 적는 송장번호는 `trackings` 로 가지 않는다.** 그래서
출고 확정만 하면 CE 에는 `so.invoiced` 가 오지 않고 주문의 송장번호도 비어 있다.
`webhookTrackingNo()` 가 `trackings` 표만 보기 때문이다.

「3PL 송장출력」 창은 **배송지가 있어야 뜬다** — 없으면 `3pl_invoice_list/get` 이 500 이다
(`account_addresses` 조인이 깨진다). 다만 그 창은 **목록만 보여 주고 번호를 발급하지 않는다**.
실제 번호는 3PL 이 채워 보낸 것을 「운송장 엑셀업로드」로 올린다.

## 4. 출고 확정ㆍ마감 — `/ship_conf`

목록에서 줄을 고르고 **송장번호 칸**을 채운 뒤 「출고 확정&마감」.
송장번호가 비면 막힌다(`MSG.TRACKING_NUMBER_REQUIRED` — 운송사 지원 유형일 때).

→ 출고 상태 `95` → CE 로 **`so.shipped`**, 주문이 **`shipping`** 으로 오른다.

## 배송지가 없으면 어디서 걸리는가

CE 가 주문을 만들 때 배송 주소를 채우지 않으면 창고 출고에 `to_address_id` 가 비고,
**3PL 송장출력이 500** 으로 죽는다. 뒤늦게 CE 에서 주소를 넣고 「주문 수정」을 눌러도
`so_update` 가 통하지 않는다(아래).

## 위드웍스에서 고친 것 — `24789adaa`

**① 진행된 주문의 수정을 막는다**
`so_update` 는 주문 상세를 통째로 지우고 다시 만든다. 할당ㆍ피킹이 걸린 상세는
그것을 가리키는 줄이 있어 지워지지 않아 예외가 났다. 출고가 「신규」가 아니면
먼저 **422** 로 막는다 — 「이미 창고 작업이 시작된 주문이라 수정할 수 없습니다」.

**② 사유를 감추지 않는다**
거래처ㆍ배송지를 만드는 두 자리가 `try` 밖에 있었다. 거기서 난 예외는 아래 `catch`
가 잡지 못하고 전역 처리기까지 올라가는데, 그 처리기는 API 요청이면 사유를 지우고
**「WITHWORKS Server Error」만** 돌려준다(`app/Exceptions/Handler.php`).
두 자리를 `try` 안으로 옮겼다.

# 송장번호 — 「운송장 엑셀업로드」로만 들어간다

## 출고 확정/마감 화면의 송장 칸은 저장되지 않는다

격자에 「운송장번호」 칸이 있어 채울 수 있지만, `ShipmentController` 는 그 값을
**읽어서 검증만** 한다 — `mst_tracking_no` 에 쓰는 코드가 없다.
세 건에 번호를 넣고 마감했으나 DB 는 모두 빈칸이었다.

그런데도 마감이 통과한 것은 `carrier_code` 가 `USC00010`(운송사 미지원)이라
송장 검증(`MSG.TRACKING_NUMBER_REQUIRED`)을 통째로 건너뛰기 때문이다.

## 실제 경로 — 3PL 이 엑셀로 올린다

통합 출고 관리 → **「운송장 엑셀업로드」** → 파일 선택(그 자리에서 바로 처리된다).
`Tracking` 표에 줄이 서고, `Tracking::created` 훅이 **`so.invoiced`** 를 띄운다.
