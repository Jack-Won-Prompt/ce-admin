## 겪은 것

### ① 카드 매출전표가 500 으로 터진다 — **고침**

결제수단을 고르는 순간 `POST /settlement/orders/247/pay-method` 가 **500** 이었다.
화면에는 아무 말도 없었다.

```
ErrorException: Array to string conversion
  at app/Support/CardSalesSlip.php:173
```

`TossPayment` 모델이 `raw_response` 를 **배열로 풀어 준다.** 그것을 다시
`(string)` 으로 감싸니 PHP 가 경고를 냈고, 라라벨이 경고를 예외로 올려 500 이 됐다.

**가상계좌를 발급한 건에서만 드러난다** — 토스 결제 자취가 있어야 이 길로 들어오기
때문이다. 링크페이만 안내하고 끝난 송예린은 자취가 없어 지나갔고, 본인부담 0이던
박도겸은 발급 자체가 없었다.

두 곳(`data()`ㆍ`payment()`)을 도우미 하나로 모으고, 옛 자료가 문자열로 남아 있을
수 있어 **두 꼴을 모두 받게** 했다.

### ② 반쪽으로 멈춘 건을 화면이 다시 열어 주지 않는다 — **고침**

500 이 났는데도 **입금 기록과 현금영수증은 이미 남았다.** 이 걸음은
「입금 기록 → 증빙 발행 → 창고 확정」을 차례로 밟는데, 가운데서 넘어져
**입금만 남고 주문은 대기**인 채였다.

그런데 화면은 **받은 건의 결제수단 칸을 글자로 굳혀 버린다.** 다시 누를 단추가 없어
담당자가 남은 걸음을 밟을 길이 없었다.

반쪽 상태(받았는데 주문이 대기)에서는 단추를 **붉게** 세우고
「입금은 확인됐지만 주문 확정이 남았습니다 — 다시 고르면 이어서 밟습니다」로 알리게 했다.
끝까지 간 건은 그대로 글자만 선다.

### ③ 서버도 반쪽을 막고 있었다 — **고침**

화면을 열고 다시 눌렀더니 이번엔 **422**,
「이미 입금이 확인된 주문입니다」. 서버 관문도 「받았는가」만 보고 있었다.

가리는 잣대를 **「확정까지 갔는가」**로 바꿨다. 반쪽이면 다시 부를 수 있게 열되
**입금 자취는 새로 쓰지 않는다** — 이미 있는 것이 맞다. 이미 발행된 증빙은 발행 쪽이
스스로 건너뛰므로 두 번 신고되지 않는다(현금영수증 한 건으로 확인).

> **어제 송예린에서 고친 자리와 이어진다.** 그때는 「받기 전에 넘어가면 안 된다」까지
> 좁혔는데, 그것으로도 부족했다. **넘어가는 잣대는 처음부터 「끝났는가」여야 했다.**

### ④ 판매상태 필터 기본값이 「등록」 — 확인 필요

위드웍스 판매 주문 화면은 판매상태가 **「등록」으로 걸린 채** 열린다. 방금 확정한 건을
찾으려면 필터를 바꿔야 하는데, 모르면 「연계가 안 됐다」로 읽는다.
**위드웍스 쪽 화면이라 우리가 고칠 수 없다** — 절차서에 적어 두는 편이 낫다.

### ⑤ 등록신청서와 처방전의 식별번호가 다르다 — 자료 문제

등록신청서 `130205-3XXXXXX` · 처방전 `161207-3XXXXXX`. **시험 자료끼리 어긋난 것**이며
시스템 결함이 아니다. 처방전을 따랐다.

### ⑥ 위드웍스 확정자 빔 — 앞의 넷과 같다

`so_confirm` 으로 확정하면 화면 사용자가 없어 확정자가 남지 않는다. CE Admin 활동
기록에는 남으므로 급하지 않다.
