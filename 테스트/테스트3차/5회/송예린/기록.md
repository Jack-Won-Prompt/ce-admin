## 겪은 것

### ① 생년월일이 하루 앞섰다 — **고침**

거래처 수정 창을 열자 **2017-04-27** 이었다. 주민번호는 170428 이다.

어제 서나윤에서 같은 것을 보고 화면 쪽을 고쳤는데, **뿌리가 두 군데 더 있었다.**

| | |
|---|---|
| 모델 캐스트 | `date` 로만 두면 JSON 에 `2017-04-27T15:00:00.000000Z` 로 나간다 — 우리 시간 04-28 00:00 이 UTC 로는 전날 15:00 이다. `date:Y-m-d` 로 바꾼다 |
| `only([...]) + [...]` | PHP 의 배열 합집합은 **왼쪽이 이긴다.** only() 에 이미 birth_date 가 있어 오른쪽에 다시 적은 값이 통째로 무시됐다 — 고쳐 놓고도 그대로였던 까닭이다. `array_merge` 로 바꾼다 |

**DB 는 처음부터 04-28 로 맞았다.** 화면으로 오는 길에서만 밀렸다.

### ② 같은 요양기관번호를 쓰는 줄이 둘 — **표시를 붙임**

31100767 에 「순천향대학교 **부속** 부천병원」과 「순천향대학교 부천병원」이 함께 있다.
어느 쪽을 골라도 청구가 갈 곳은 같지만, 건마다 다른 줄을 고르면 **목록이 두 병원처럼
갈린다.** 새로 겹치는 것은 등록 때 막고 있는데, 이미 있는 것은 조회 목록이 아무 말도
하지 않아 알 수가 없었다.

**「같은 번호 2줄 — 마스터 정리 필요」**를 띄우게 했다. **정리는 담당자 판단이 필요하다.**

### ③ 잠긴 단추가 까닭을 말하지 않았다 — **고침**

보호자 서명까지 마쳤는데 ［동의 서명］이 잠긴 채였다. 무엇이 남았는지 알려 주는 곳이
없어 위아래를 훑어야 했다 — **법정대리인 신분증**이 비어 있었다. 화면이 길어 그 칸은
스크롤해야 보인다.

남은 것을 단추 위에 그대로 적게 했다(본인확인ㆍ보호자 넷ㆍ서명ㆍ신분증ㆍ신청 유형ㆍ
동의 항목).

### ④ 같은 결제수단을 고르면 아무 일도 일어나지 않았다 — **고침**

정산에서 링크페이를 눌러도 요청조차 나가지 않았다. 화면 코드가 이랬다.

```js
if (method === row.pay_method_key) return;   // 같은 값이면 넘어간다
```

상세 목록의 결제 방식이 링크페이로 기본 잡혀 있어 **주문에 그 값이 미리 적힌다.**
목록에는 확정 전이라 「-」로 보이는데 속값은 이미 `card` 다. 그래서 링크페이를 눌러도
「같은 값」이라 조용히 돌아갔다 — **담당자는 눌렀는데 아무 반응이 없고 까닭도 모른다.**

**이 걸음이 세금계산서ㆍ거래명세서ㆍ창고 확정을 함께 움직이는 자리**라 가볍지 않다.
넘어가는 것을 **이미 받은 건에서 같은 값을 다시 고를 때만**으로 좁혔다.

> 박도겸(가상계좌)ㆍ서나윤(무통장입금)은 기본값과 **다른 값**을 골라 우연히 비껴갔다.
> 링크페이를 고르는 건에서만 드러난다.

### ⑤ 산재에 위임동의를 물었다 — **고쳤다가 되돌림**

산재는 우리가 대신 받을 급여가 없으니 「건강보험 급여 위임동의」를 물을 까닭이 없다고
보아 자격으로 막았다. **그것이 틀렸다** — 처음 오는 거래처는 산재라도 서명을 받는다
(2026-09-08 지시). 서명 화면이 개인정보 동의도 함께 받고, 자격은 나중에 바뀐다.

되돌리고 그 자리에 **왜 자격으로 가르지 않는지**를 적어 두었다. 가르는 잣대는 자격이
아니라 **처음인가**이고, 그 일은 이미 있던 「한 번 물어본 사람에게는 다시 보내지
않는다」가 한다.

### ⑥ 청구가 없는 건인데 「청구 준비」가 미비 — 확인 필요

주문 관리 목록에서 **청구처 = 해당 없음 · 청구 여부 = 해당 없음** 인데 **청구 준비 =
미비** 다. 서나윤(지자체)에서도 같은 것을 보았다 — 청구 준비 판정이 공단 기준이라,
공단 건이 아닌 것은 늘 미비로 읽히는 것으로 보인다. 일은 막히지 않지만 목록만 보면
아직 낼 게 남은 것처럼 보인다. **다음에 살펴본다.**
