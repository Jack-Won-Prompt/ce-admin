## 0. 붙는 곳을 먼저 확인한다 (2026-09-27 12:5x)

시험을 시작하기 전에 토스와 팝빌이 정말 시험 갈래인지 **런타임 값으로** 읽었다.
`.env` 만 보고 판단하지 않는다 — 아래에 적는 까닭 때문이다.

```
popbill.env       = test     IsTest = true
popbill.issue_simulate = false        ← 팝빌 테스트베드로 **실제로 발행**한다
popbill.service_env    = 모두 빈칸     ← 다섯 서비스 모두 전체 갈래(test)를 따른다
popbill.sms_mode  = live     fax_mode = redirect
popbill 계정      = corp 1018634660 · user coloplast

toss.test_mode    = true
toss.client_key   = test_ck_yL0q…
toss.va_selectable = true
```

DB 설정에 담긴 값도 같다 — `popbill.env = test`, `toss.env = test`,
`toss.test_client_key = test_ck_…`, `popbill.issue_simulate = 0`.

**시험 갈래 확인 완료.** 팝빌은 테스트베드(test.popbill.com)로 실제 발행하므로
발행ㆍ취소가 국세청으로 가지 않고, 토스는 시험 키로 붙는다.

### ⚠ 위험한 자리 — `.env` 와 DB 가 서로 반대다

| | `.env` | DB `settings` | 실제로 도는 값 |
| --- | --- | --- | --- |
| `POPBILL_IS_TEST` | **false**(운영) | `is_test=0` · `env=test` | **test** |
| `POPBILL_ISSUE_SIMULATE` | **true**(막음) | `issue_simulate=0` | **false**(발행함) |

부팅할 때 `AppServiceProvider` 가 `ServiceSettings::applyToConfig()` →
`PopbillEnvironment::apply()` 순으로 **DB 값을 config 위에 덮는다**. 그래서 지금은
시험 갈래가 맞다.

그러나 **DB 의 `popbill.env` 줄이 사라지면 곧바로 운영으로 떨어진다** —
`config/popbill.php` 의 `'env' => env('POPBILL_ENV') ?: (IS_TEST ? test : live)` 가
`.env` 의 `false` 를 읽기 때문이다. 설정 표를 비우거나 옮겨 심는 일이 있으면
국세청 실신고로 바뀐다. 10월 1일 전까지는 **DB 의 `popbill.env=test` 를 건드리지 않는다.**

### 소스로 먼저 가린다

`PrescriptionController::store()` 는 올린 파일마다 **늘 새 처방번호를 낸다**.


주석이 아니라 코드가 그렇다 — 기존 건을 찾는 질의가 아예 없다. 2026-09-15 지시

그러므로 **같은 주문에 더 붙이는 길은 업로드 화면이 아니라 주문 화면의
「첨부문서 추가」**다. 두 길을 나누어 확인했다.

## 항목 2 — 재업로드 요청 시 알림이 가는가 · 모바일 웹에서 확인되는가 ✅

### 소스

### 🔴 결함 ⑬ — 한 장만 다시 올렸는데 되물은 요청이 **모두** 닫힌다

두 건을 되물었다.

| 요청 | 대상 | 사유 | 다시 올렸나 |
| --- | --- | --- | --- |
| #36 | 본 그림 | 서류 유형이 다름 | **올렸다** |
| #35 | 첨부 1906 `G03_…png` | 이미지가 잘 안 보임 | **안 올렸다** |

그런데 DB 는 둘 다 같은 시각에 닫혔다.

```
요청#35 서류=처방전 첨부id=1906 닫힘='2026-09-27 13:11:24' 닫은첨부=NULL
요청#36 서류=처방전 첨부id=NULL 닫힘='2026-09-27 13:11:24' 닫은첨부=NULL
```

**까닭은 `ReuploadRequestService::닫기()` 가 서류 **이름**으로만 닫기 때문이다.**

```php
$질의->where('doc_label', $서류이름);
return $질의->update(['resolved_at' => now(), …]);
```

두 요청 모두 `doc_label = '처방전'` 이라, 처방전 한 장이 올라오면 그 이름을 가진
**열린 요청을 전부** 닫는다. 첨부 1906 은 흐린 그대로 남아 있는데 목록의
「요청 여부」는 `—` 가 되어, 검수자는 **되물은 것을 받았다고 읽는다.**

`resolved_attachment_id` 가 `NULL` 인 것도 같은 자리의 자취다 — 어느 파일이 이
요청을 닫았는지 적지 못한다.

고칠 자리는 좁다. 요청이 **첨부를 짚고 있으면**(`attachment_id` 가 있으면) 그
첨부가 갈린 경우에만 닫고, 본 그림 요청(`attachment_id` 가 `NULL`)만 이름으로
닫으면 된다. 지금은 둘을 가리지 않는다.

※ 고치기 전에 확인을 받는다 — 2회차부터 같은 자리를 다시 밟아 재현을 굳힌다.

배지는 앞의 것으로 그리고, **주문을 낼 수 있는가는 뒤의 것으로 가른다.**

없어도 같은 사람의 지난 서명이 위임기간 안이면 참이다.

서버는 쓸 수 있는 지난 서명이 있을 때만 `#prevSignNote` 를 심고, 보일지 말지는
화면이 전략으로 정한다(`renderDelegationNeed`) — 거래처가 있고, 위임이 필요하고,
이 건에 직접 받은 서명이 없을 때만 뜬다.

## 항목 7 — 주문 제품에서 필수값을 안 넣으면 걸러지는가 ✅

관문이 여럿이고 층이 둘(화면ㆍ서버)이다. 차례로 밟았다.

### ㉮ 수량은 빈 채로 둘 수 없다 (격자가 막는다)

제품을 고르면 수량이 **1 로 자동으로 선다**. 일부러 지우고(Ctrl+A → Delete → Enter)
확인하니 `items[0].quantity` 가 다시 `1` 이었다 — wwGrid 가 빈 값을 받지 않고
되돌린다. 「수량을 입력해 주십시오」 관문(`order.blade.php:9731`)은 그 뒤에 선
두 번째 그물이다.

### ㉯ 박스 단위가 맞아야 한다

수량 1 로 ［주문 생성 및 연계］를 눌렀다.

```
[알림] 박스 수량이 맞지 않습니다
       박스 단위의 수량이 아닙니다. 「박스」 항목을 확인하고 수량을 수정해 주십시오.
```

이 제품은 `R-Box 30` 이라 30 의 배수여야 한다. 수량을 **30** 으로 고치니 통과했고,
금액이 그 자리에서 다시 섰다.

```
수량 30 · RB 단위 30 EA · 박스 1.0 BOX
총 67,500 = 공단 60,750 (90%) + 본인 6,750 (10%)     ← 처방전·일반 전략 그대로
```

### ㉰ 재구매 가능일은 **서버가** 막는다

박스 수량을 맞추자 확인 창이 떴고, ［생성합니다］를 눌렀더니 서버가 되돌렸다.

```
[토스트] ❌ 재구매 가능일 2주 이상 남아 진행불가합니다
         (재구매 가능일 2026-10-28 · 31일 남음)
```

막힌 것이 맞는지 DB 로 확인했다.

```
EUD202609271315541  status=pending  so_no=NULL      ← 위드웍스로 나가지 않았다
copay=6750  nhis=60750
```

`so_no` 가 비어 있으니 **연계는 서지 않았다.** 주문 줄 자체는 13:15:54 에 이미
서 있었는데, 그것은 ［주문 생성 및 연계］가 아니라 **유형을 고르는 순간 서는 줄**이다
(2026-09-22 에 확인된 설계). 상태가 `pending` 에 머물러 있는 것이 그 증거다.

**판정 — 걸러진다.** 화면과 서버 두 층이 같은 것을 막고, 서버가 마지막 문이다.

### 곁들여 — 화면이 한 걸음 늦게 막는 자리 (작은 틈)

［주문 생성 및 연계］를 누르면 **먼저 확인 창이 열리고, ［생성합니다］를 누른 뒤에야**
재구매 막힘이 알려진다. 그런데 그 막힘은 화면이 이미 알고 있었다 —
바로 아래 붉은 띠에 같은 글이 떠 있었다.

```
⚠ 재구매 가능일 2주 이상 남아 진행불가합니다 (재구매 가능일 2026-10-28 · 31일 남음)
```

`gate박스수량()` 은 창을 열기 전에 막는데(위 ㉯ 는 창이 안 떴다), 재구매는 그렇지
않다. 담당자는 「진행합니다」를 눌러 놓고 되돌려받는다. 막을 수 있는 것을 창 앞에서
막으면 걸음이 하나 준다. **일을 그르치지는 않으므로 결함이 아니라 다듬을 자리로
적어 둔다.**

## 항목 8ㆍ9 — 주문 생성 및 연계 → 결제 링크 발송 · 위드웍스 판매주문 등록 ✅

### 앞선 걸음에서 드러난 것 — 오지혜로는 갈 수 없었다

항목 7 에서 재구매 막힘이 걸려, 이 사람으로는 처방전 건을 더 진행할 수 없었다.
「신구매」로 고쳐도 소용이 없다 — `RepurchaseWindow::block()` 은 **처방외(유형 20)만**
면제한다.

```php
if ((string) ($rx->counsel_acc_add_type ?? '') === '20') { return null; }
```

**이것은 결함이 아니다.** 신구매/재구매 칸은 *공단 등록 구분*(신규 등록ㆍ재등록)이고,
재구매 주기는 *같은 사람의 지난 구매일*이 정한다. 지난달에 산 사람이 오늘 또 사면
공단 등록이 신규든 아니든 주기는 아직 안 찬다. 두 값이 재는 것이 서로 다르다.

※ 중간에 「신구매로 바꾸니 띠가 사라졌다」고 읽었는데 **내 측정이 틀렸다.** 띠는
주문 제품 탭 안에 있어 그 탭이 숨어 있을 때 `offsetHeight` 가 0 이다.
`재구매띠가리기()` 는 처방외만 보고 여닫는다 — 신구매로는 애초에 숨지 않는다.

막히지 않은 거래처를 골라 이어 갔다.


**367 (E)김도빈**으로 갔다 — 위임 서명이 이미 있어 항목 5 를 한 번 더 확인하게 된다.

### ㉰ 청구 관리 — 🔴 결함 ⑭ 를 찾아 그 자리에서 고쳤다

원천은 결제 링크다. `CashbillController::cardReceipts` 가 그렇게 적어 두었다 —
`toss_payments` 는 한 주문에 한 줄이라 재결제가 앞 줄을 덮어써서, 걸음마다 한 줄이

같은 파일의 주석이 의도를 밝혀 둔다: 「취소는 뺀 금액으로 적는다 — 승인과 나란히

까닭은 링크를 해지하는 자리가 **아직 안 받은 것만** 거두기 때문이다.

```php

PaymentLink::where('order_id', $order->id)
    ->whereIn('status', ['sent', 'failed'])      // ← 'paid' 는 손대지 않는다
    ->update(['status' => 'cancelled']);
```

그 자리에서는 맞는 잣대다 — 「취소한 건의 링크가 살아 있으면 환자가 그 사이에 결제해
버린다」를 막는 일이라, 이미 받은 줄을 건드릴 까닭이 없다. 빠진 것은 **환불했다는
표시**다.

**고치지 않고 적어 둔다.** 받은 줄을 `cancelled` 로 바꾸면 「받았던 사실」이 지워지고,
합계를 다른 표에서 다시 세면 이 화면만 또 갈린다. 돈을 어떻게 읽을지 정하는 일이라
확인을 받고 간다. 두 갈래가 보인다:

* ㉠ 결제 링크에 **`refunded`** 상태를 더해 화면이 「환불 −6,750」으로 적는다
* ㉡ 링크 상태는 그대로 두고, `cardReceipts` 가 `order_amendments` 의 환불액을 보고
  그 줄을 음수로 그린다

※ 화면에는 `(E)김도빈` 으로 나오는데 **맞다** — 내부 화면이다. 밖으로 나가는 글
(문자ㆍ증빙 PDFㆍ팝빌ㆍ토스)에서만 뗀다.
