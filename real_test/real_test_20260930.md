## 0. 먼저 — 순서 검증 결과

지시하신 순서를 **소스 로직으로 확인**했다. 주석이 아니라 실제로 도는 코드와
운영 서버의 설정값을 읽었다. **그대로 진행하면 멈추는 자리가 넷 있다.**

### ✗ (가) 공단 팩스 자동 전송이 **꺼져 있다**

```
order.nhis_fax_on_consent = false
order.nhis_fax_on_id_card = false
```

[NhisFaxAuto.php:51](app/Services/NhisFaxAuto.php#L51) 이 이 값을 맨 먼저 보고
**아무 말 없이 물러난다** — 알림도 남지 않는다. 지금 상태로는 「운영 팝빌로 팩스
자동 전송 확인」 단계에서 아무 일도 일어나지 않고, 그것이 실패인지 아닌지조차
화면에 뜨지 않는다.

**시험 전에 둘 다 켜야 한다.**

### ✗ (나) 팩스가 **0504-134-1393 으로 가지 않는다**

받는 번호는 [NhisFaxAuto.php:203](app/Services/NhisFaxAuto.php#L203) 이
**관할 청구처(`billing_offices.fax`)** 에서 읽는다. 지시하신 번호는 그 표에 없다.

운영 설정은 —

```
popbill.fax_mode          live      ← 적힌 곳으로 실제로 나간다
popbill.test.receiver_fax ''        ← 시험 수신처가 비어 있다
```

`fax_mode` 를 **`redirect`** 로 두고 **시험 팩스 번호에 0504-134-1393** 을 넣으면,
관할 청구처를 건드리지 않고 그 번호로만 간다([FaxService.php:67](app/Services/Popbill/FaxService.php#L67)).
**운영 청구처의 팩스번호를 고쳐 시험하면 안 된다** — 되돌리기를 잊으면 공단으로
갈 팩스가 엉뚱한 곳으로 간다(2026-09-07 에 그 일이 있었다).

### ✗✗ (다) 세금계산서·현금영수증이 **국세청 실신고로 나간다**

```
billing.auto_issue        true
billing.auto_issue_start  '2026-09-01'   ← 오늘(9-30)은 이미 지났다
popbill.issue_simulate    false
팝빌 갈래                 live
enabled(taxinvoice)       true
enabled(cashbill)         true
```

즉 결제가 확인되면 [DepositAutoIssue](app/Services/DepositAutoIssue.php) 가
**실제로 국세청에 신고**한다. 시험 환자 「최연아」 이름으로 세금계산서와
현금영수증이 콜로플라스트 명의로 발행된다.

**팝빌은 한 번 발행하면 API 로 지우지 못한다.** 되돌리려면 취소 신고를 또 해야
하고 그것도 기록에 남는다(2026-09-27 에 취소현금영수증 셋을 만들어 남긴 적이 있다).

**고를 수 있는 길 둘** —

1. `popbill.issue_simulate = true` 로 두고 시험한다. 조회는 그대로 팝빌에 묻고
   **쓰는 일(발행ㆍ취소)만 막는다.** 화면에는 발행된 것처럼 보이고 서류도 만들어진다.
   국세청에는 가지 않는다.
2. 실신고를 감수하고 그대로 진행한 뒤, 시험이 끝나면 **취소 신고**를 낸다.

### ✗ (라) 「처방전 업로드 분리」는 사용자별로 갈리지 않는다

업로드 화면은 담당자를 **고르는 칸**일 뿐, 로그인한 사람에 따라 올릴 수 있는 서류가
달라지지 않는다. 관리자가 처방전·결과지를, stella 가 등록신청서를 올리는 것은
**같은 화면에서 각자 로그인해 올리면 그대로 된다** — 막는 것도 나누는 것도 없다.
다만 그렇게 하면 두 사람이 **같은 처방전에** 올려야 하므로, 관리자가 먼저 올려
처방전을 세운 뒤 stella 가 그 처방전을 열어 등록신청서를 더해야 한다.

### 지시하신 순서와 다른 점 — 셋

**① 팩스는 「신분증 링크 발송」 다음 걸음이 아니다.**
서명이 끝나는 그 순간(8)과 신분증이 닿는 그 순간(11), **두 번** 저절로 재어진다.
사람이 누르는 걸음이 아니다. 둘 중 **나중에 갖춰지는 쪽**에서 나간다.

**② 「유형·자격 선택」이 빠져 있다.**
주문 줄은 **유형을 고를 때 선다**. 이것을 안 하면 주문 제품 탭이 비고, 청구전략이
서지 않아 금액도 서명 안내도 서지 않는다.

**③ 증빙 생성ㆍ위드웍스 확정ㆍ거래명세서 작성일은 한 덩어리다.**
셋을 따로 부르는 자리가 없다. `DepositAutoIssue` 안에서 차례로 일어난다 —
발행 → 거래명세서 → `WithworksConfirm`(작성일 함께). 그래서 발행이 막히면
**확정도 함께 멈춘다.**

### 증빙 넷은 결제 갈래로 갈린다

### 오류 — 설정을 엉뚱한 묶음에 담았다

처음에 `fax_mode`ㆍ`test_receiver_fax` 를 **`test` 묶음**에 담았다. 화면의 탭 이름이
「테스트 설정」이라 그것이 묶음 이름인 줄 알았는데, `config/settings-schema.php` 의
최상위 묶음은 **`web`** 이다(`test` 라는 묶음은 없다).

`ServiceSettings::applyToConfig()` 는 **스키마에 있는 묶음만** 훑으므로, 담긴 값은
어느 코드도 읽지 않는 채로 누워 있었다 — 담았는데 `config()` 는 그대로 `live` 였다.
**담은 것만 보고 됐다고 읽으면 안 된다.** 반드시 `config()` 를 다시 읽어 확인한다.

**고침** — `test` 묶음의 두 줄을 걷고 `web` 묶음에 다시 담았다. 확인한 값 —

```
order.nhis_fax_on_consent true
order.nhis_fax_on_id_card true
popbill.fax_mode          redirect
popbill.test.receiver_fax '0504-134-1393'
popbill.issue_simulate    false
```

### 1-1. 앱 로그인 (관리자)

| | |

**앱이 운영 서버에 붙은 것을 확인했다** — nginx 로그에 `Dart/3.12 (dart:io)` 요청이

탓에 **같은 이메일 칸**이 다시 눌렸다 — 비밀번호가 이메일 뒤에 붙어
`admin@ce-admin.co.kr12345678` 이 되었다. 지우고, 칸을 누르는 대신 **키보드의 「다음」**
으로 옮겨 해결했다. 사람이 손으로 할 때도 같은 일이 난다.

### 1-2. 앱 업로드 — **시험이 엉뚱한 서버로 가고 있었다**

관리자로 로그인해 처방전·결과지 두 장을 담고 「처방전 업로드(2건)」을 눌렀는데
**운영 서버에 아무것도 닿지 않았다.** 처방전도 환자도 늘지 않았다.

까닭을 찾으려 nginx 로그를 보니 **오늘 앱(Dart) 요청이 한 건도 없었다** — 마지막
자취가 09:45(다른 사람 폰)였다. 로그인조차 우리 서버를 지나지 않았다는 뜻이다.

## 7. 앱을 고치고 다시 — 새 판 1.3.4

지시 「이 둘(단추 안내ㆍSMS 문구)도 고치고 새 APK로 1단계부터 다시」.

### 고친 것 둘 (커밋 `38be6938`)

**① 업로드 단추가 왜 안 눌리는지 말한다.**
여태 `onPressed: (_queue.isEmpty || _selectedPatient == null) ? null : _uploadAll`
이라, 조건이 안 맞으면 눌러도 아무 일이 없었다. 단추는 활성처럼 보이고 안내도 없어
사람은 「고장났나」로 읽는다. 이제 —

- 단추는 늘 눌린다. 누르면 무엇이 모자란지 말한다.
- 모자란 것을 **단추 바로 위에** 붉게 적는다(토스트는 스쳐 간다).
- 안내와 실제로 막는 잣대가 `_blockedReason()` **한 곳**을 본다.

**② 인증번호 안내를 실제로 올 때만 적는다.**
로그인 화면이 「로그인 후 SMS 인증번호가 발송됩니다」를 늘 적어 두었는데
`auth.otp_enabled` 가 꺼진 서버에서는 오지 않는다. `/api/auth/options` 에
`otp_login` 을 더하고 화면이 그때만 적게 했다. 못 물어보면 **없는 것으로 본다** —
기다리게 하는 쪽이 더 나쁘다.

**확인** — 새 판 로그인 화면에서 그 문구가 **사라졌다**. 서버에 물어 받았다는 뜻이다.

### 겪은 어려움 — 한글 입력 (내 쪽 연장 문제)

`adb shell input text` 로는 한글이 들어가지 않는다. `input keyevent` 도 자판이 영문
모드면 ASCII 가 나온다. **키보드를 한글로 바꾼 뒤 자판 위치를 직접 눌러야** 한다 —

```
         ㅇ(329,1823) ㅕ(697,1672) ㄴ(223,1823)
         ㅇ(329,1823) ㅏ(855,1823)
```

globe 는 **한 번 눌러서는 안 바뀔 때가 있다**(영문↔한글이 아니라 자판을 도는 듯하다).
한 글자 찍어 보고 아니면 한 번 더 누른다.

이것은 **사람에게는 없는 어려움**이다 — 손으로는 그냥 친다. 기록만 남긴다.

### 1-3(다시). 처방전ㆍ결과지 업로드 — **공통 코드가 통째로 비어 있었다**

#### ✗✗ 뿌리 — 운영의 `common_codes` 가 0줄이었다

```
common_codes 표 있음
모두 0줄
```

[PrescriptionApiController.php:63](app/Http/Controllers/Api/PrescriptionApiController.php#L63) 이
`Rule::in(UploadDocTypes::codes())` 로 가리는데, 그 목록이 **공통 코드에서 온다.**
표가 비어 있으니 **어떤 유형을 보내도 거절**된다 — 앱이든 웹이든 **처방자료를
한 장도 올릴 수 없는 상태**였다.

이 코드는 `2026_08_19_000003_create_common_codes_table` 이 심는 것이다. **표는 서
있는데 줄만 없다** — 그 마이그레이션은 이미 돌아간 것으로 적혀 있어 다시 돌지 않는다.
언제 비었는지는 알 수 없다(그 표를 지우는 코드는 `ResetForRetest` 뿐인데 거기서
`common_codes` 는 **남길표**에 있다).

**고침** — `common-codes:ensure` 명령을 두어 **없는 것만** 채웠다(커밋 `4300e9fb`).
이미 있는 줄은 이름도 차례도 건드리지 않는다. 다시 돌려도 탈이 없다.

```
13개를 넣었습니다. doc_type 이 지금 13개입니다.
업로드가 받는 유형 : registration_form, prescription, test_result, id_card, privacy_consent, other
```

#### 그 뒤 업로드 성공

```

처방전 #50972 RX-20260930-002 · 상태 review_needed · 만든이 1(관리자) · 15:10:29
```

처방전은 **본문 그림**으로, 결과지는 **첨부**로 들어갔다.

#### 그 밖에 드러난 것

**서류 유형 목록이 고른 값 기준으로 재배치된다.** 「처방전」을 고른 뒤 다시 열면
목록 순서가 바뀌어, 같은 자리를 누르면 **다른 유형**이 잡힌다(결과지를 누르려다
신분증이 잡혔다). 사람도 똑같이 헛짚을 수 있는 자리다.

**고침이 동작하는 것을 확인했다** — 서류를 담기 전에는 단추 아래에
「올릴 서류를 먼저 담아 주십시오 — 「카메라」 또는 「갤러리」를 누릅니다.」,
