## 0. 먼저 — 순서 검증 결과

지시하신 순서를 **소스 로직으로 확인**했다. 주석이 아니라 실제로 도는 코드와
운영 서버의 설정값을 읽었다. **그대로 진행하면 멈추는 자리가 넷 있다.**

### ✗ (가) 공단 팩스 자동 전송이 **꺼져 있다**

```
order.nhis_fax_on_consent = false
order.nhis_fax_on_id_card = false
```

[NhisFaxAuto.php:51](app/Services/NhisFaxAuto.php#L51) 이 이 값을 맨 먼저 보고
**아무 말 없이 물러난다** — 알림도 남지 않는다. 지금 상태로는 「운영 팝빌로 팩스
자동 전송 확인」 단계에서 아무 일도 일어나지 않고, 그것이 실패인지 아닌지조차
화면에 뜨지 않는다.

**시험 전에 둘 다 켜야 한다.**

### ✗ (나) 팩스가 **0504-134-1393 으로 가지 않는다**

받는 번호는 [NhisFaxAuto.php:203](app/Services/NhisFaxAuto.php#L203) 이
**관할 청구처(`billing_offices.fax`)** 에서 읽는다. 지시하신 번호는 그 표에 없다.

운영 설정은 —

```
popbill.fax_mode          live      ← 적힌 곳으로 실제로 나간다
popbill.test.receiver_fax ''        ← 시험 수신처가 비어 있다
```

`fax_mode` 를 **`redirect`** 로 두고 **시험 팩스 번호에 0504-134-1393** 을 넣으면,
관할 청구처를 건드리지 않고 그 번호로만 간다([FaxService.php:67](app/Services/Popbill/FaxService.php#L67)).
**운영 청구처의 팩스번호를 고쳐 시험하면 안 된다** — 되돌리기를 잊으면 공단으로
갈 팩스가 엉뚱한 곳으로 간다(2026-09-07 에 그 일이 있었다).

### ✗✗ (다) 세금계산서·현금영수증이 **국세청 실신고로 나간다**

```
billing.auto_issue        true
billing.auto_issue_start  '2026-09-01'   ← 오늘(9-30)은 이미 지났다
popbill.issue_simulate    false
팝빌 갈래                 live
enabled(taxinvoice)       true
enabled(cashbill)         true
```

즉 결제가 확인되면 [DepositAutoIssue](app/Services/DepositAutoIssue.php) 가
**실제로 국세청에 신고**한다. 시험 환자 「최연아」 이름으로 세금계산서와
현금영수증이 콜로플라스트 명의로 발행된다.

**팝빌은 한 번 발행하면 API 로 지우지 못한다.** 되돌리려면 취소 신고를 또 해야
하고 그것도 기록에 남는다(2026-09-27 에 취소현금영수증 셋을 만들어 남긴 적이 있다).

**고를 수 있는 길 둘** —

1. `popbill.issue_simulate = true` 로 두고 시험한다. 조회는 그대로 팝빌에 묻고
   **쓰는 일(발행ㆍ취소)만 막는다.** 화면에는 발행된 것처럼 보이고 서류도 만들어진다.
   국세청에는 가지 않는다.
2. 실신고를 감수하고 그대로 진행한 뒤, 시험이 끝나면 **취소 신고**를 낸다.

### ✗ (라) 「처방전 업로드 분리」는 사용자별로 갈리지 않는다

업로드 화면은 담당자를 **고르는 칸**일 뿐, 로그인한 사람에 따라 올릴 수 있는 서류가
달라지지 않는다. 관리자가 처방전·결과지를, stella 가 등록신청서를 올리는 것은
**같은 화면에서 각자 로그인해 올리면 그대로 된다** — 막는 것도 나누는 것도 없다.
다만 그렇게 하면 두 사람이 **같은 처방전에** 올려야 하므로, 관리자가 먼저 올려
처방전을 세운 뒤 stella 가 그 처방전을 열어 등록신청서를 더해야 한다.

### 지시하신 순서와 다른 점 — 셋

**① 팩스는 「신분증 링크 발송」 다음 걸음이 아니다.**
서명이 끝나는 그 순간(8)과 신분증이 닿는 그 순간(11), **두 번** 저절로 재어진다.
사람이 누르는 걸음이 아니다. 둘 중 **나중에 갖춰지는 쪽**에서 나간다.

**② 「유형·자격 선택」이 빠져 있다.**
주문 줄은 **유형을 고를 때 선다**. 이것을 안 하면 주문 제품 탭이 비고, 청구전략이
서지 않아 금액도 서명 안내도 서지 않는다.

**③ 증빙 생성ㆍ위드웍스 확정ㆍ거래명세서 작성일은 한 덩어리다.**
셋을 따로 부르는 자리가 없다. `DepositAutoIssue` 안에서 차례로 일어난다 —
발행 → 거래명세서 → `WithworksConfirm`(작성일 함께). 그래서 발행이 막히면
**확정도 함께 멈춘다.**

### 오류 — 설정을 엉뚱한 묶음에 담았다

처음에 `fax_mode`ㆍ`test_receiver_fax` 를 **`test` 묶음**에 담았다. 화면의 탭 이름이
「테스트 설정」이라 그것이 묶음 이름인 줄 알았는데, `config/settings-schema.php` 의
최상위 묶음은 **`web`** 이다(`test` 라는 묶음은 없다).

`ServiceSettings::applyToConfig()` 는 **스키마에 있는 묶음만** 훑으므로, 담긴 값은
어느 코드도 읽지 않는 채로 누워 있었다 — 담았는데 `config()` 는 그대로 `live` 였다.
**담은 것만 보고 됐다고 읽으면 안 된다.** 반드시 `config()` 를 다시 읽어 확인한다.

**고침** — `test` 묶음의 두 줄을 걷고 `web` 묶음에 다시 담았다. 확인한 값 —

```
order.nhis_fax_on_consent true
order.nhis_fax_on_id_card true

popbill.test.receiver_fax '0504-134-1393'
```

### 1-1. 앱 로그인 (관리자)

| | |

`admin@ce-admin.co.kr12345678` 이 되었다. 지우고, 칸을 누르는 대신 **키보드의 「다음」**
으로 옮겨 해결했다. 사람이 손으로 할 때도 같은 일이 난다.

### 1-2. 앱 업로드 — **시험이 엉뚱한 서버로 가고 있었다**

관리자로 로그인해 처방전·결과지 두 장을 담고 「처방전 업로드(2건)」을 눌렀는데
**운영 서버에 아무것도 닿지 않았다.** 처방전도 환자도 늘지 않았다.

까닭을 찾으려 nginx 로그를 보니 **오늘 앱(Dart) 요청이 한 건도 없었다** — 마지막
자취가 09:45(다른 사람 폰)였다. 로그인조차 우리 서버를 지나지 않았다는 뜻이다.

## 7. 앱을 고치고 다시 — 새 판 1.3.4

지시 「이 둘(단추 안내ㆍSMS 문구)도 고치고 새 APK로 1단계부터 다시」.

### 고친 것 둘 (커밋 `38be6938`)

**① 업로드 단추가 왜 안 눌리는지 말한다.**
여태 `onPressed: (_queue.isEmpty || _selectedPatient == null) ? null : _uploadAll`
이라, 조건이 안 맞으면 눌러도 아무 일이 없었다. 단추는 활성처럼 보이고 안내도 없어
사람은 「고장났나」로 읽는다. 이제 —

- 단추는 늘 눌린다. 누르면 무엇이 모자란지 말한다.
- 모자란 것을 **단추 바로 위에** 붉게 적는다(토스트는 스쳐 간다).

**② 인증번호 안내를 실제로 올 때만 적는다.**

`common_codes` 는 **남길표**에 있다).

**고침** — `common-codes:ensure` 명령을 두어 **없는 것만** 채웠다(커밋 `4300e9fb`).

**서류 유형 목록이 고른 값 기준으로 재배치된다.** 「처방전」을 고른 뒤 다시 열면

## 10. ✗ 「업로드 분리」는 앱에서 지시하신 대로 되지 않는다

지시 — 「관리자 : 처방전ㆍ결과지 업로드 / stella : 등록신청서 업로드」.

### 소스로 확인한 것

**앱의 처방전 목록은 본인이 올린 것만 보인다.**

```php
// PrescriptionApiController::index — 내 처방전 목록 (모바일 앱 — 로그인 사용자 본인 업로드만)
$query = Prescription::where('created_by', auth()->id())
```

화면 머리에도 「**본인이 등록한 처방전**」이라 적혀 있다.

앱에서 **이미 있는 처방전에 서류를 더하는 길**은 상세 화면의 [서류 추가]뿐인데
([prescription_detail_screen.dart:188](ce_app/lib/screens/prescription_detail_screen.dart#L188)),
그 화면에 닿으려면 목록에 그 건이 보여야 한다.

`RX-20260930-002` 는 **관리자**가 만들었다(`created_by = 1`). 그러므로 —

> **stella 는 앱에서 그 처방전을 볼 수 없고, 등록신청서를 더할 수도 없다.**

stella 가 앱 업로드 화면에서 최연아를 골라 등록신청서를 올리면 **새 처방전**
(`RX-20260930-003`)이 하나 더 선다. 같은 환자에게 처방전이 둘이 되고, 서류는 갈린다.

### 고를 수 있는 길 셋

| | 어떻게 | 무엇이 걸리나 |
|---|---|---|
| ① | **한 사람이 세 장을 다 올린다** | 지시하신 「분리」가 아니다 |
| ② | stella 가 **웹**에서 그 처방전을 열어 등록신청서를 더한다 | 웹 처방전 상세는 남의 건도 보인다. 다만 「앱으로」가 아니다 |
| ③ | 앱 목록에 **남의 건도 보이게** 고친다 | 앱의 잣대를 바꾸는 일이다 — 지금 「본인 것만」은 뜻이 있어 둔 자리다 |

**③ 을 하려면 어디까지 보일지 정해야 한다** — 모두인가, 같은 환자만인가,
검색으로만 찾게 할 것인가.

어느 길로 갈지 정해 주시면 그대로 진행한다. 짐작해 고치지 않는다.

## 11. 업로드 분리 성공 — 앱에 이미 있던 「처방전 조회」로

### 내가 잘못 짚은 것

앞 절에서 「앱에서는 안 된다」고 적었으나 **틀렸다.** 앱에는 **「처방전 조회」**가
이미 있다(2026-09-23 지시) — 이름과 생년월일로 **남이 올린 건**을 찾아 들어가는
자리다. 목록(`index`)만 본인 것이고, 그 조회는 `/api/prescriptions/lookup` 이라는
**따로 난 길**을 쓴다.

나는 그것을 보지 못하고 `index()` 를 넓히는 코드를 넣었다가(`2b12a9d4`) —
같은 일을 하는 길이 둘이 되므로 — **되돌렸다**(`db646a9b`).

> **소스를 끝까지 훑기 전에 「없다」고 적지 않는다.**

### 지시하신 요건은 이미 들어 있었다

「이름과 생년월일(8자리) 같이 검색 필수」 · 「이름은 포함(like) 조건」 —
`lookup()` 이 그대로 그렇게 한다. 이름은 `(E)`ㆍ붙임표ㆍ빈칸을 뗀 뒤 **무르게**
견주고(2026-09-26), 생년월일은 여덟 자리ㆍ주민번호 앞자리 둘 다 받는다(2026-09-29).

## 13. 3단계 — 주문 등록 (상세정보 입력까지)

### 연락처를 먼저 채웠다

앱의 환자 등록에는 연락처 칸이 없어 최연아의 전화번호가 비어 있었다. 주문 등록
화면의 환자 칸은 **「거래처관리에서 수정합니다」**로 잠겨 있어, 거래처 관리에서 넣었다.

```
#12614 최연아 · 주민번호 940406-2****** · 연락처 010-4206-1393
```

> **적어 둘 것** — 앱으로 등록하면 연락처가 비어 있다. 서명ㆍ신분증 링크가 그
> 번호로 나가므로 **그 전에 반드시 채워야 한다.** 앱 등록 대화상자에 연락처 칸을
> 더할지는 결정이 필요하다.

### 유형ㆍ신구매ㆍ자격

「병원ㆍ처방 정보」 탭에 있다(상담ㆍ환자 정보가 아니다).

| 칸 | 고른 값 |
|---|---|
| 유형 * | **처방전** (`10`) |
| 신구매/재구매 * | **신구매** |
| 자격 * | **일반** |

**유형을 고르는 순간 주문 줄이 섰다** — 앞서 소스로 짚은 그대로다.

```
POST /prescriptions/RX-20260930-002/order-line  200
→ 주문 1건
```

신구매ㆍ자격은 [저장]을 눌러야 담긴다. 저장 뒤 —

```
유형 '10' · 신구매 '신구매' · 자격 '일반'
```

### 막은 것 — 「동의 확인」이 먼저다

[저장]을 누르려는데 **모달이 가로막았다**.

```
동의 확인
동의를 확인한 뒤 구매를 진행해 주십시오.
아직 받지 못한 동의
  · 요양비 위임 서명
  · 개인정보 수집·이용 동의
화면 위쪽의 「서명 동의」 버튼으로 받으십시오.
```

**순서를 지키라는 안내다.** 시험 계획의 다음 걸음(서명 동의 링크)을 화면이 먼저
일러 준다. [확인]을 눌러 닫고 저장을 마쳤다 — 저장 자체는 막지 않는다.

**자동화에서 겪은 것** — 이 모달이 떠 있는 동안 저장 단추가 `modal-overlay` 에
가려 눌리지 않는다. 사람은 모달을 보고 닫지만, 자동화는 「단추가 안 눌린다」로만
보인다. 모달을 먼저 닫아야 한다.

한쪽만 재승인되는 날이 온다. 커밋 `fb912169`.

```

```

**서명 직후 서류 둘이 저절로 만들어졌다** (16:06:40) —

```
생성 서류 #1 consent      (개인정보 수집·이용 동의서)
생성 서류 #2 delegation   (요양비 위임장)
```

주문 등록 화면의 배지도 「**서명 동의 완료**」로 바뀌었다.

### 공단 팩스는 아직 나가지 않았다 — 맞는 동작이다

```
attempt() → 보냄 false · 까닭  신분증 이(가) 아직 없습니다
```

`NhisFaxAuto` 가 **네 가지를 다 갖췄는지** 보고 멈춰 섰다 —

| 서류 | 지금 |
|---|---|
| 등록신청서 | ○ (Stella 가 올림) |
| 결과지 | ○ (관리자가 올림) |
| 요양비위임장 | ○ (서명 직후 자동 생성) |

## 15. ✗✗ 공단 지사 167곳 가운데 164곳에 관할 지역이 없다

「관할 청구처 자동 찾기」는 `billing_office_areas` 를 보고 찾는다. 그 표가 —

```
공단 지사 167곳 · 관할 지역이 있는 곳  3곳 · 없는 곳 164곳
                                   (서대문ㆍ노원ㆍ성동지사뿐)
지자체    4곳 · 관할 있는 곳 4곳
```

**서대문ㆍ노원ㆍ성동을 뺀 모든 지역에서 청구처를 찾지 못한다.** 중구지사(#340)는
팩스(02-3275-8350)까지 갖춰 있는데도 걸리지 않았다.

청구처가 없으면 `billing_office_id` 가 비고, 그러면 **공단 팩스가 못 나간다**
(`NhisFaxAuto::faxNumber()` 가 `billingOffice->fax` 를 읽는다).

### 엑셀 확인 — 관할 자료는 없다

`기능 추가 및 수정/20260927/건강공단보험 지사 리스트.xlsx` (172줄) 을 열어 보았다.

| 있는 칸 | 공단(지사명) · 주소 · 부서 · TEL · **FAX** · 비고 |
|---|---|
| **없는 칸** | **관할 시군구** |

지사 주소에서 시군구를 뽑아 관할로 삼는 것은 **쓸 수 없다** —

| 문제 | 보기 |
|---|---|
| 지사가 있는 구 ≠ 관할 구역 | 부산남부지사 주소는 **수영구** |
| 한 지사가 여러 시군구 | 남양주가평지사 = 남양주시 + **가평군**(주소엔 남양주시만) |
| 한 구에 지사 둘 | 영등포북부ㆍ남부 |
| 주소 표기가 제각각 | 「서울시 영등포구」에서 **서울시**가 시군구로 읽힘 |
| 못 읽는 줄 | 안성지사(`안성시석정동`) · 세종지사(구가 없음) |

**짐작해 채우지 않았다.** 관할을 잘못 넣으면 환자 서류가 엉뚱한 지사로 가고,
팩스는 한 번 나가면 되돌릴 수 없다.

### 오늘은 중구지사만 넣었다 (지시 「2」)

```
중구지사 #340 · 관할 시군구 「중구」 · 시도는 비워 둔다
```

**시도를 「서울」로 적었더니 못 찾았다** — 서버는 주소에서 「**서울특별시**」로 읽어
견준다(`ClaimAgency::sidoFromAddress`). 기존 세 줄(서대문ㆍ노원ㆍ성동)처럼 **비워
두어야** 시도로 가리지 않는다. 비운 뒤 곧바로 찾아졌다.

```
lookup → 1곳 · 중구지사 #340 · FAX 02-3275-8350
청구 기관 'nhis' · 청구처 중구지사 · 팩스 02-3275-8350
```

### 남은 일 (별도)

**지사 167곳의 관할 시군구를 채워야 한다.** 「지사명 ↔ 관할 시군구」 목록만 있으면
엑셀 일괄 올리기(`billing-offices/upload`)로 한 번에 넣을 수 있다.
엑셀의 팩스ㆍ전화ㆍ부서 갱신(172줄)도 함께 할 수 있다.

### 그 사이 환자 주소도 채웠다

관할 찾기는 **환자 주소**에서 시군구를 읽는다. 앱으로 등록한 환자는 주소가 비어
있어(연락처와 같다) 자동 찾기가 「주소에서 읍ㆍ면ㆍ동과 시ㆍ군ㆍ구를 추출하지
못했습니다」로 멈춘다. 등록신청서에 적힌 주소를 거래처에 넣었다.

```
04516 · 서울특별시 중구 서소문로11길 19 · 배재정동빌딩 B동 10층
```

> **앱 등록에 연락처와 주소가 없다** — 둘 다 뒤에서 손으로 채워야 한다.

## 3-6. 신분증 링크로 받았는데 화면에서 찾지 못했다 — 오류 둘

사람이 신분증 링크로 신분증을 올렸다. 그런데 주문 등록 화면에서 **보이지 않았고**,
공단 팩스도 **보낼 수 없었다.** 두 가지가 겹쳐 있었다.

### 오류 ① 문서 목록에는 있는데 그림칸이 없다

문서 목록(`ALL_DOCS`)에는 들어 있었다.

```
ALL_DOCS: ["0:prescription","10708:test_result","10709:registration_form",
           "-1003:delegation","-1001:consent","-1:signature","-3:patient_id"]
첨부 카드에 보이는 것 : 처방전ㆍ결과지ㆍ등록신청서ㆍ요양비위임장ㆍ위임동의서 (5)
```

까닭은 `renderGenThumbs` 가 **`isGenerated` 인 것만** 그림칸으로 세운 데 있다. 서명ㆍ
신분증(`signDocs`)에는 그 표가 없어 **누를 자리가 없었다.** 뷰어로는 열릴 수 있었지만
사람이 갈 길이 없으니 「첨부파일에 신분증이 없다」로 읽힌다.

> **사람이 못 찾으면 없는 것과 같다.** 서류가 DB 에 있는 것만으로는 시험 통과가 아니다.

**고침** — `signDocs` 세 줄에 `isSign` 을 담고, 그림칸을 `isGenerated || isSign` 으로
그린다. 우리가 만든 서류(자주색)와 받아 둔 것(초록)을 테 색으로 가른다.
문서 수는 `syncDocEmpty` 가 그려진 칸을 다시 세므로 저절로 맞는다. (커밋 `83a58a78`)

### 오류 ② 서류 유형 이름이 「본인 신분증」이라 팩스가 신분증을 찾지 못했다

지시: **「서류 유형이 본인 신분증 => 신분증 이여야 공단 팩스 발송이 가능한, 본인
신분증은 서류 유형에 없음」**

서류 유형(`common_codes.doc_type`)에 있는 이름은 **「신분증」(`id_card`)** 이다.
「본인 신분증」은 어디에도 없는 이름인데, 문서 목록과 팩스 이름표에 그렇게 적혀
있었다. 팩스 창은 `id_card` 갈래로 신분증이 있는지 가린다.

```js
// 팩스 창 — 첨부번호가 있는 것만 「있다」로 센다
const hits = ALL_DOCS.filter(d => d.id > 0 && d.type === req.type);
```

링크로 받은 신분증은 **첨부가 아니라 동의 기록**에 담긴다 — 첨부번호가 없어
`id` 가 음수(`-3`)이고 갈래도 `patient_id` 였다. 그래서 두 조건에 모두 걸리지 않아
**「등록 안 됨 — 문서 카드에서 올리십시오」** 로 서고, 신청 파일이 **3/4** 에 머물렀다.
다 갖췄는데 사람이 팩스를 보낼 수 없는 상태였다.

**고침** (커밋 `04253b74`)

| 자리 | 전 | 후 |
|---|---|---|
| 문서 목록 갈래 | `patient_id` | `id_card` |
| 문서 목록 이름 | 본인 신분증 | **신분증** |
| 링크로 받은 표시 | (없음) | `doc='patient_id'` |
| 팩스 창 | 「등록 안 됨」 | 법정대리인 신분증과 같은 길로 세움 |
| 팩스 이름표 | 본인 신분증 | **신분증** |
| 줄에 적는 출처 | 「동의 첨부」 고정 | 「신분증 링크」/「동의 첨부」 |

싣는 길은 첨부번호가 아니라 `documents[]=patient_id` 다 — 이미 `sendFax` 가 받는다.

### 서버 쪽은 이미 고쳐 두었다

자동 팩스(`NhisFaxAuto`)는 앞서 같은 구멍을 메웠다 — `missing()` 이 첨부만 세어
링크로 받은 신분증을 못 보았고, 그래서 자동 팩스가 **한 번도 나가지 못했다.**

```

받는 팩스 : 02-3275-8350   (중구지사)
팩스 갈래 : redirect · 시험 수신처 0504-134-1393

```

서버는 보낼 수 있는데 **화면이 못 보내게 막고 있던 것**이 오류 ② 였다.

### 고친 뒤 확인 (운영 https://75.2.99.52 · 배포 후)

문서 카드 — **문서 7**, 신분증 그림칸이 초록 테로 섰다.

「팩스 전송」을 눌러 **실제로 보냈다.** 팝빌 포인트가 나갔다.

```
접수번호 : 026093016464500007
받는 곳  : 국민건강보험공단 (중구지사 02-3275-8350)
실수신   : 05041341393   ← fax_mode=redirect · 시험 수신처로 돌아감

실린 것  : 첨부 10709(등록신청서)·10708(결과지) + documents[patient_id] + 생성 요양비위임장
```

한 건 더 있는데, 우리 앱 로그와 nginx 접근 기록에는 그 시각 발송 요청이 없다 —
우리 서버를 거치지 않은 발송이다.

### 웹훅으로 결과를 받았다


웹훅 본문을 그대로 믿지 않고 접수번호만 받아 팝빌에 재조회해 적는다 — 서명이 없는
알림이라 위조할 수 있다. 팝빌 웹훅은 팩스ㆍ문자ㆍ알림톡ㆍ세금계산서ㆍ현금영수증
다섯 갈래가 모두 등록되어 있고 오늘 59건이 들어왔다.

### 오류 ③ 성공한 팩스가 「실패」로 적혔다

| 팝빌 상태 | 팝빌 뜻 | 우리 상수(전) | 우리가 읽던 뜻 |
|---|---|---|---|
| 0 | 접수 | `STATE_WAIT` | 대기 |
| 1 | 변환 중 | `STATE_SENDING` | 전송 중 |
| 2 | 전송 중 | `STATE_OK` | **성공** ✗ |
| 3 | 완료 | `STATE_FAIL` | **실패** ✗ |
| 4 | 취소 | `STATE_CANCEL` | 취소 |

숫자가 같고 뜻이 달라 지금까지 오류로 드러나지 않았다. **성공ㆍ실패는 상태가 아니라
결과코드가 정한다** — 100 이 성공이고, 완료(3)라도 504(잘못된 수신번호)ㆍ505(응답
없음)이면 닿지 않았다.

딸려 있던 문제 넷

1. 발송 이력ㆍ주문 등록ㆍ팩스 발송 화면이 성공한 팩스를 **실패**로 표시
2. **재등록 기한**이 `popbill_state = 2` 를 찾아 한 번도 맞지 않음 → 늘 빈칸
3. 자동 팩스의 「이미 보냄」 잣대가 완료(3)를 실패로 보아 제외 → **같은 팩스를 공단에
   다시 보낼 수 있었다**
4. `scopePending` 이 완료 건을 끝나지 않은 것으로 보아 동기화가 계속 되돌아옴

**고침** (커밋 `bc973cce`) — 상수를 팝빌 값으로 다시 정의하고(`STATE_RECEIVED`ㆍ
`CONVERTING`ㆍ`SENDING`ㆍ`DONE`ㆍ`CANCEL`, 팝빌에 접수조차 안 된 건은 `STATE_NOT_SENT=9`),
판정을 `성공인가()`ㆍ`실패인가()`ㆍ`succeeded()`ㆍ`undelivered()` 한곳에 모았다.
`FaxSyncService` 는 팝빌 상태를 우리 상수와 견주지 않고 그대로 담고, 결과코드는
닿지 못한 수신자의 것을 먼저 남긴다(부분 실패를 성공으로 적지 않게).

기존 자료는 1건뿐이고 이미 팝빌 원값이 담겨 있어 보정이 필요 없었다.

### 오류 ④ 합본 PDF 내려받기가 404

화면은 「PDF 다운로드 (전송 서류 통합본)」을 주는데 열리지 않았다. 운영 서버에
**`public/storage` 연결이 없었다** — 합본은 `storage/app/public/fax/...` 에 저장하고
`/storage/...` 주소로 내려받는 구조다. 공단에 무엇이 나갔는지 확인할 길이 없었다.

```
ln -sfn /opt/ce-admin/storage/app/public /opt/ce-admin/public/storage
chown -h www-data:www-data /opt/ce-admin/public/storage
→ 200 application/pdf 439,078 bytes
```

배포 절차에 이 단계가 없어 다시 사라질 수 있으므로 `deploy.yml` 에 넣었다
(지시 「storage:link 넣기」). `artisan storage:link` 는 쓰지 않는다 — www-data 로 돌면
`public` 에 쓸 권한이 없어 죽고, `set -e` 때문에 배포가 그 자리에서 멈춘다. root 로
돌리면 로그ㆍ캐시가 root 것으로 생겨 뒤가 막힌다. 셸로 만들고, 이미 있으면 손대지 않는다.

## 3-8. 병원ㆍ처방 정보 입력

처방전 이미지에 적힌 대로 넣었다.

| 칸 | 넣은 값 | 저장된 값 |
|---|---|---|
| 병원명 · 요양기관번호 | 서울아산병원 · 11111111 | 그대로 |
| 담당 의사명 · 의사면허번호 | 김의사 · 12345 | 그대로 |
| 전문과목 | (비뇨의학과) → **비뇨기과** | 비뇨기과 |
| 상병 명 · 상병코드 | 신경인성 방광 · N319 | 그대로 |
| 처방전 발행일 · 사용 기간 | 2026-09-30 · 90일 | 그대로 |
| 처방전종료일 | 2026-12-29 | **2026-12-28** |
| 1일 처방 개수 · 총 처방일수 · 총계 | 5 · 90 | 5 · 90 · **450**(자동) |

### 확인이 필요한 셋

**㉠ 처방전종료일이 조용히 바뀐다.** 화면이 「발행일 + 기간 − 1」로 다시 계산한다
(`calcNextRepurchase`, 2026-09-08 확인요청 10쪽의 규칙). **계산은 규칙대로 맞고, 내가 만든
시험 처방전의 날짜가 틀렸다.** 다만 급여 종료일은 다시 계산할 때 알림이 뜨는데
(`onUseStartChanged`) 이 칸은 아무 말 없이 덮인다 — 담당자가 처방전에 적힌 날을 넣어도
하루 다른 값이 저장되고, 화면을 다시 보지 않으면 모른다.

**㉡ 전문과목에 「비뇨의학과」가 없다.** 선택지는 비뇨기과ㆍ재활의학과ㆍ정형외과ㆍ
신경과ㆍ신경외과 다섯이다. 2017년에 「비뇨기과」가 「비뇨의학과」로 바뀌었고 처방전에도
그렇게 적혀 나온다. 원천 데이터에도 `분당연세비뇨의학과` 처럼 새 이름을 쓴 병원이 있다.

**㉢ 병원 마스터가 0건이었다.** `common_codes` 가 비어 있던 것과 같은 갈래다. 조회하면
늘 「검색된 병원이 없습니다」였고, 담당자마다 같은 병원을 새로 등록하게 된다.

요양기관번호는 기관마다 하나이므로 **한 번호에 이름이 여럿인 것은 원천이 틀린 것**이다.
어느 쪽이 맞는지 고를 근거가 없어 **가장 많이 쓰인 번호를 담고, 다툼은 비고에 그대로
적었다.** 지시 「모두 그대로 담는다」에 따라 뒤의 둘도 손대지 않고 담았다.

> **같은 규칙을 쓰는 처방전 이관 명령(`MigratePrescriptionsFromWithworksCommand`)도
> 이 이름들을 처방전에 그대로 적어 두었다.** 처방전 쪽 병원명도 같이 손봐야 한다.

## 3-10. 주문 제품 등록 · 주문 생성 및 연계

### 제품 고르기

「주문 제품」 탭 → 제품명 칸을 눌러 「제품 조회」에서 코드 `28512` 로 찾아 골랐다.

```
SpeediCath CH12 Female 20cm - White
28512 · 보험코드 NBC0121000005 · EA · R-Box 30 · ₩ 2,250
```

같은 이름으로 `M28512`(₩1)도 있다 — 샘플ㆍ브로셔 갈래다. 담당자가 잘못 고르면 금액이
1원이 되므로 코드 앞의 `M` 을 보고 골라야 한다.

### 오류 ⑤ 한 글자씩 치면 「없다」로 나온다

`SpeediCath CH12 Female` 를 **천천히 치면 0건**, 같은 말을 한 번에 넣으면 **2건**이다.
요청이 엇갈려 마지막 글자의 결과가 화면에 서지 않는다. 사람이 빠르게 치면 「없는
제품」으로 읽고 다른 이름을 찾거나 새로 등록하러 간다.

| 넣은 말 | 결과 |
|---|---|
| `SpeediCath CH12 Female` (천천히) | **0건** |
| `SpeediCath CH12 Female` (한 번에) | 2건 |
| `CH12 Female` | 7건 |
| `28512` | 2건 |

### 하루 한도에 막혔다 — 의도된 동작

처방전대로 1일 5개를 넣자 「주문 생성 및 연계」가 멈췄다.

```
⚠️ 하루 한도를 넘었습니다 — 1,012,500원 ÷ 90일 = 11,250원 (한도 9,000원).
   수량 또는 처방일수를 확인하십시오.
```

잣대는 `config('nhis.limits.daily_amount')` = **9,000원** 이다. 2,250원 제품은 하루
**4개**까지다. **저장은 막지 않고**(2026-09-10 확인요청 6쪽) 창고로 보내는 걸음만 막으며,
그때는 안내가 「저장은 됩니다 — 창고로 보내기 전에 확인하십시오」로 달라진다.

> 지시 「1일 4개·총 360개로 고쳐 진행」에 따라 고쳤다. **업로드한 처방전 이미지(1일 5개·
> 총 450개)와 어긋난다** — 내가 만든 시험 서류가 급여 한도를 넘게 적혀 있었다.

탭을 옮길 때 「저장하지 않은 변경사항 — 저장 후 이동 / 저장 없이 이동 / 취소」로 막아 준다.

## 3-11. 토스 결제 — 오류 ⑥ 클라이언트 키와 시크릿 키가 다른 상점의 것 (운영 개시 차단)

링크페이 문자를 받은 사람이 링크를 열어 직접 결제를 눌렀다. 결제창은 열렸고, 결제는
끝났는데 **마지막 승인에서 막혔다.**

```
결제하지 못했습니다
[INVALID_API_KEY] 잘못된 시크릿키 연동 정보 입니다.
주문번호 EUD202609301600381 · 금액 81,000원
```

서버 기록

```
[2026-09-30 17:25:59] [Toss][POST] /v1/payments/confirm
  {"paymentKey":"link_202609301725389AbL3",
   "orderId":"wme2v6i3l5qnubh8kjv3bjzwfx9yhgam2dvph9yx-jr4325s4","amount":81000}
[2026-09-30 17:25:59] [Toss] API 오류 {"http":400,"code":"INVALID_API_KEY"}
[2026-09-30 17:25:59] [결제전송] 승인 실패
```

### 가려낸 과정

| 확인 | 결과 | 뜻 |
|---|---|---|
| 시크릿키로 토스 API 호출 | `404 NOT_FOUND_PAYMENT` | 시크릿키 **자체는 유효**하다 (무효면 `INVALID_API_KEY`) |
| 클라이언트키로 결제창 열림 | paymentKey `link_202609301725389AbL3` 발급 | 클라이언트키 **자체도 유효**하다 |
| 그 paymentKey 를 시크릿키로 조회 | `404 NOT_FOUND_PAYMENT` | 그 결제가 **우리 시크릿키의 상점에 없다** |
| `/v1/payments/orders/{tossOrderId}` 조회 | `404 NOT_FOUND_PAYMENT` | 같다 |

**승인 전 결제도 제 상점에서는 조회된다.** 조회조차 되지 않는다는 것은 결제가 다른
상점에 만들어졌다는 뜻이다 — 즉 **두 열쇠가 서로 다른 상점(MID)의 것**이다.

```
클라이언트 키 : live_ck_Gv6LjeKD8a9wB7pwy5OM8wYxAdXy   (공개 값)
시크릿 키     : live_sk_kYG5…                          (다른 상점)
```

### 고치는 자리

설정 › 서비스 연동 설정 › 토스. 값은 `.env` 가 아니라 **`settings` 표**에 있다
(`group='toss'` · `live_client_key` · `live_secret_key`, 시크릿은 암호화되어 담긴다).
`.env` 에는 시험 키(`test_ck_…`ㆍ`test_sk_…`)만 있고 **읽히지 않는다** — 팝빌과 같다.

토스 개발자센터에서 **클라이언트 키 `live_ck_Gv6Lje…` 가 속한 상점의 시크릿 키**를
받아 넣어야 한다. 두 키는 반드시 같은 상점의 한 쌍이어야 한다.

> **운영 개시를 막는 사안이다.** 지금 상태로는 카드ㆍ가상계좌 어느 쪽도 승인되지 않는다.
> 주문ㆍ위드웍스 연계ㆍ공단 팩스까지는 모두 정상이므로, 이 한 쌍만 맞추면 이어진다.

### 돈이 나갔는가

나가지 않았다. 승인(confirm)이 이루어지지 않았으므로 매입이 일어나지 않는다.
토스 쪽에 승인되지 않은 결제 시도로만 남는다.

토스 열쇠를 바로잡은 뒤(3-11) 문자 링크로 사람이 직접 결제해 **승인까지 끝났다.**

|---|---|

### 오류 ⑦ 결제 뒤 자동 처리가 두 번 돌았다

```
17:40:56  /pay/done 승인 성공 → DepositAutoIssue + PaymentDoneNotice (1회차)
17:40:57  토스 PAYMENT_STATUS_CHANGED 웹훅 → 같은 둘을 다시 실행 (2회차)

17:41:03  알림톡 2통 — 환자가 같은 안내를 두 통 받았다
```

세금계산서는 **팝빌이 문서번호로 막아 준 덕에** 한 장으로 끝났다. 막아 주는 저쪽이
없는 일(거래명세서 생성ㆍ안내 발송)은 그대로 두 번 일어났다.

`PaymentDoneNotice` 의 「한 건에 한 번」 잣대는 발송 이력을 **조회해** 가리는데, 두 길이
같은 초에 돌아 **둘 다 조회 시점에 이력이 없어 둘 다 보냈다**(경쟁 상태).

**고침** (커밋 `e5388242`) — 부르는 자리가 열한 곳이라 밖에서 막으면 반드시 빠뜨린다.
`DepositAutoIssue::run()` 과 `PaymentDoneNotice::send()` **안에서** 주문마다 빗장을
건다. 먼저 든 쪽이 끝난 뒤에 들어가므로 뒤엣것은 「이미 발행됨」ㆍ「이미 안내한 건」을
제대로 보고 지나간다. 중복으로 생긴 거래명세서 뒤엣것(#10712)은 지웠다.

## 3-13. 거래명세서 — 좌우 어긋남과 위드웍스와의 차이 (지시)

> 「거래명세서 틀이 좌우 안맞음, 거래명세서가 운영 위드웍스 거래명세서와 다름」

### 오류 ⑧ 공급받는자ㆍ공급자 상자의 아래가 어긋났다

원본(위드웍스)은 두 표를 **flex** 로 세운다. `align-items:stretch` 가 기본이라 짧은
쪽이 저절로 늘어나 **아래가 늘 같은 줄에서 끝난다.**

dompdf 는 flex 를 모른다. 그래서 우리 쪽은 표 둘을 나란히 두고 **줄 여백 3.1mm 로
높이를 맞춰** 두었는데, 그 값은 「받는 분 주소가 한 줄일 때」 재어 맞춘 것이었다.
이번 건은 주소가 두 줄이라 왼쪽만 11px 길어졌다.

**고침** (커밋 `50499db9`) — **표 하나로 합쳤다.** 한 표 안에서는 두 편이 같은 줄판을
나눠 쓰므로 어긋날 수 없다. 줄 수가 셋ㆍ넷으로 다른 것은 받는 분 주소 칸을 두 줄에
걸치게(rowspan) 하여 맞췄다. 바깥 테두리 0.7mm 는 칸마다 나눠 주고, 가운데 3mm 틈은
테두리도 배경도 없는 칸으로 두었다(원본의 gap).

### 오류 ⑨ 고치자 이름표 칸이 찌그러져 값을 덮었다

칸이 일곱으로 늘자 dompdf 가 auto 배치로 폭을 다시 나눴다. 값 칸의 글이 길면 그쪽으로
폭을 몰아주는 탓에 이름표 칸이 글자보다 좁아져 **「성 명」이 값 칸을 덮고
「성명최연아」로 겹쳐** 나왔다.

**고침** (커밋 `71eafbc1`)

- 폭을 `colgroup` 뿐 아니라 **칸(td)에도** 적는다
- 이름표를 낱자 표 대신 **글자로 두고 줄을 접지 않게** 한다(`white-space:nowrap`).
  낱자 표는 그 폭(15mm)을 dompdf 가 지키지 않아 좁아질 수 있었다. 빈칸 수는 글자 수에
  맞춰(2자 넷ㆍ3자 둘ㆍ4자 하나) 원본의 양끝정렬과 같은 폭이 되게 했다.

## 3-15. 오류 ⑩ PASS 로 본인확인해도 화면이 바뀌지 않았다 (지시)

> 「위임 서명 링크에서 NICE 연동시 문자 인증되는데 PASS 인증이 안됨 원인 분석 후 해결」

### 원인 — NICE 가 아니라 결과를 받는 길

표준창을 팝업으로 열고 결과를 **`window.opener.postMessage` 로만** 받아 왔다.

```js
window.open(out.auth_url, 'nice_delegation', 'width=500,height=620,scrollbars=yes');
// nice-done.blade.php
try { if (window.opener) window.opener.postMessage('nice-done', '*'); } catch (e) {}
```

**PASS 인증은 PASS 앱으로 나갔다 돌아온다.** 모바일에서 그렇게 돌아오면 브라우저가
부모-자식(`opener`) 관계를 잃는 일이 잦다. 그러면 콜백은 제대로 돌아 **서버에는
본인확인이 남는데 화면만 그대로**다 — 사람은 「PASS 는 안 된다」로 읽는다.
문자 인증은 표준창 안에서 끝나 `opener` 가 살아 있어 동작했다.

**서버에는 남는다** — `DelegationSignPublicController::niceCallback` 이
`nice_verified_at` 을 적는다.

### 결정적 증거

```
위임 서명 #3668   본인확인 2026-09-28 11:42:21 (권은선)
                  서명 없음 · 상태 sent
```

인증은 끝났는데 서명으로 넘어가지 못하고 멈춘 건이다.

### 함께 겹쳐 있던 둘

```
[2026-09-30 16:04:03] NICE 콜백 처리 실패 — 본인확인 세션이 만료되었습니다
[2026-09-30 16:04:45] (다시 시도해 성공)
```

- **세션이 10분**이었다(`nice.crypto_ttl_minutes`). PASS 는 앱 전환ㆍ설치 안내까지
  있어 빠듯하다.
- **배포가 `optimize:clear` 로 응용 캐시를 통째로 지웠다.** 그 안에 `cache:clear` 가
  들어 있다 — 표준창을 오가는 사이에 배포가 돌면 복호화 열쇠가 사라진다.

오전의 `[NICE] 허용되지 않은 IP 접근(3.37.111.215)` 는 그 뒤 풀렸다 — 지금은 토큰이
정상 발급된다(그래서 문자 인증은 됐다).

### 고친 것 (커밋 `5d76707d`)

| 자리 | 고침 |
|---|---|
| 서명 화면 둘 | **스스로 묻는다** — `GET /{token}/nice/status` 를 3초마다, 그리고 앱에서 돌아와 화면이 다시 보이는 순간(`visibilitychange`ㆍ`focus`) 곧바로 |
| 알림 | 빠른 길로 남기되, **화면을 바꾸는 자리는 한 곳**으로 모음 |
| 돌아온 창 | 부모를 못 찾으면 「이 창을 닫고 서명 화면으로 돌아가 주십시오 · 본인확인은 정상으로 처리되었습니다」 |
| 세션 | 10분 → **20분** |
| 배포 | `config`ㆍ`route`ㆍ`view`ㆍ`event` 만 비움 (응용 캐시 보존) |

돌려주는 것은 **「끝났는가」 하나뿐**이고, 링크의 토큰을 가진 사람만 자기 건을 묻는다 —
이름ㆍ생년월일은 담지 않는다.

### 운영 확인

```
GET /delegation/{본인확인 있는 토큰}/nice/status   200  {"verified":true}
GET /consent/{본인확인 있는 토큰}/nice/status      200  {"verified":true}
GET /delegation/{본인확인 없는 토큰}/nice/status   200  {"verified":false}
GET /delegation/{없는 토큰}/nice/status            404

```

**남은 확인** — 사람이 PASS 로 실제 인증해 화면이 「확인됨」으로 바뀌는지.

## 3-16. PASS 본인확인 재시험과 서명 완료

고친 뒤(3-15) 새 링크를 보내 사람이 PASS 로 다시 인증했다.

### 1차 — 고치기 전 코드로 (동의 #6)

```
18:37:06  POST /nice/start   → 131바이트 (실제 인증주소)
18:37:09  status → verified:false
18:37:12  status → verified:false
18:37:14  callback?web_transaction_id=NmNmOWMwYWIt…
18:37:27  status → verified:true
```

**「즉시 인증되는 것 아니냐」는 물음을 받았다.** 확인 결과 실제 인증이 맞았다 —
누른 지 **8초**, 시뮬레이션 로그 0건, 시뮬레이션이 쓰지 않는 칸(생년월일 19940406ㆍ
휴대폰 01042061393ㆍDI)까지 채워졌다. PASS 앱이 로그인·생체인증 상태면 그 정도다.

> **다만 그 물음 덕에 허점이 드러났다.** 상태 조회가 「이 건이 **언젠가** 인증된 적
> 있는가」를 돌려주어, **이미 인증된 건에서 다시 누르면 아무것도 하지 않고 곧바로
> 「인증됨」**이 된다. 사람은 통과하는 화면을 보고 인증이 진짜 됐는지 의심하게 된다.

**고침** (커밋 `03273c1e`) — `niceStart` 가 시작 시각을 주고 화면이 `since` 로 되돌려
보낸다. 서버는 **그 뒤에 들어온 인증만** 「됐다」로 답한다. 시각은 서버가 준 것만 쓴다
(폰 시계는 제각각). 시계 오차 몫 5초.

운영 확인

```
since 없이   → verified:true    (옛 방식)
since = 지금 → verified:false   ← 이번 시도만 센다
since = 어제 → verified:true
```

## 3-17. 오류 ⑪ 증빙 첨부가 두 장씩 생겼다 (지시)

> 「첨부파일 중복 생성 방지」

결제 뒤 자동 처리가 두 번 돈 자국이 첨부에도 남아 있었다.

```
17:40:59  카드매출전표 #10713 · #10714   ← 같은 초에 두 장
17:40:59  거래명세서   #10711 · #10712   ← (거래명세서는 3-13 에서 이미 정리)
```

까닭은 만드는 자리마다 **「먼저 조회해 보고 없으면 만든다」**로 막은 데 있다. 두 길이
같은 순간에 부르면 둘 다 조회에서 아무것도 못 보고 둘 다 만든다.

`DepositAutoIssue` 에 빗장을 걸었지만 그것만으로는 부족하다 — 부르는 자리가 여럿이고
(ClaimBundle · ReturnDocsReissue · 출고 웹훅 · 정산 화면) 새로 생길 수도 있다.

### 고침 — 표에서 막는다 (커밋 `8328e50b`)

처방전 사진처럼 **여러 장이 정상인 갈래**가 있어 `(prescription_id, doc_type)` 전체에
유일 잣대를 걸 수는 없다. 한 장뿐이어야 하는 갈래일 때만 값이 서고 나머지는 NULL 인
생성 칸을 두고 그 칸으로 건다 — **MySQL 은 NULL 끼리를 겹침으로 보지 않는다.**

```sql
single_doc_type  VARCHAR(50) GENERATED ALWAYS AS (
  CASE WHEN doc_type IN ('card_sales','trade_statement','tax_invoice_form',
                         'cash_receipt_form','medical_aid_claim')
       THEN doc_type END) STORED
UNIQUE KEY uk_attach_single_doc (prescription_id, single_doc_type)
```

겹침을 만난 쪽은 **오류로 올리지 않고 먼저 만든 줄을 그대로 쓴다** — 결제가 끝난
뒤의 일이라 화면에 오류를 띄우면 사람은 결제가 잘못된 줄 안다. 그때 이미 써 둔
파일은 주인이 없으므로 지운다.

### 운영에서 실제로 시험

| 시험 | 결과 |
|---|---|

### APK 1.3.5 배포 상태

```
/opt/ce-admin/public/apk/   ce-admin-1.3.5.apk 하나만 (59,162,486 bytes)
받기 : 1.3.3 → 404 · 1.3.5 → 200
설정 : latest_version 1.3.5 · min_version 1.3.2 · apk_url …/ce-admin-1.3.5.apk
앱 응답 : GET /api/app/version → latest 1.3.5 · download_url …1.3.5.apk
```

APK 가 운영 서버를 바라보는 것도 확인했다 — `75.2.99.52` 3회 · `/api` 8회 ·
`ceadmin.co.kr` 0회. 원본과 SHA-256 일치(`6329ff03…`).

### NICE CI — 계약 문제이고 코드는 이미 준비돼 있다

저장소의 규격서(`nice_openapi.json`) 「인증 결과 목록」에 답이 있다.

| 항목 | 설명 |
|---|---|
| `ci` | (공통) CI |
| `ci2` | (공통) CI2 (추후 필요시 전달됨) |
| `di` | (공통) DI |

> 리턴 되는 결과 데이터의 경우, **NICE 평가정보와 계약된 값만 제공되며, 그렇지 않은
> 경우 항목 자체가 제공되지 않습니다.** 리턴 데이터 항목 추가 및 변경이 필요한 경우,
> NICE평가정보 계약 혹은 관리 담당자에게 문의 바랍니다.

우리 코드는 `$r['ci']` 를 그대로 읽어 `nice_ci` 에 담는다(두 화면 모두). 칸도 이미
있다 — **NICE 가 보내 주기 시작하면 코드 수정 없이 저장된다.**

NICE 담당자에게 요청할 것

```
client_id : NI3bdf…  (통합인증 IDO/INTC)
요청      : 인증 결과 리턴 항목에 CI 추가
현재      : di 는 오는데 ci 는 항목 자체가 오지 않음
```

지금 `nice_ci` 를 읽어 쓰는 코드는 없어 당장 막히는 곳은 없다. 사람을 하나로 묶는
열쇠로 필요해질 때 막힌다.

### 규격서에서 함께 확인된 것 — PASS 는 별도 코드가 아니다

`svc_types` 는 **`M` 휴대폰 · `F` 금융인증서 · `U` 공동인증서 · `I` 아이핀** 넷뿐이고,
**PASS 는 `M`(휴대폰) 안에 들어 있다.** 3-15 의 PASS 문제가 인증 수단 설정 탓이
아니었음이 규격으로도 확인된다.

### 세금계산서 양식 — 공급받는자 칸이 텅 비었다 (결함)

붙은 양식의 공급받는자 쪽 **등록번호ㆍ상호ㆍ성명ㆍ업태ㆍ종목이 모두 비어 있고**
사업장 주소만 찍혔다. 공급자 쪽과 금액(55,227 + 5,523 = 60,750)은 맞다.

주문 표에는 값이 멀쩡히 있다 — `tax_invoice_biz_name=최연아`,
`tax_invoice_ceo_name=최연아`, `tax_invoice_biz_no=940406-2******`.

#### 까닭 — 빗장은 걸었는데 표에서 다시 읽지 않았다

```
20:28:26  세금계산서 발행 성공 TI20260930000003 → 주문 표에 기록
20:28:27  [TaxInvoice] 발행 실패 {"order":3,"error":"[-11001038] 동일한 공급자 문서번호가 사용 중입니다."}
20:28:28  세금계산서 양식 첨부 #10721 생성
```

결제가 끝나면 두 길이 이 자리를 부른다 — 결제 화면의 승인과 토스 웹훅이다. 어제
`Cache::lock('deposit-auto-issue:…')` 으로 **겹쳐 도는 것은** 막았다. 그런데 뒤에 든
쪽이 손에 쥔 `Order` 는 **요청이 시작될 때 읽은 것**이라, 앞선 쪽이 적어 놓은
`tax_invoice_status='issued'` 가 그 안에 없다. 그래서

1. `taxInvoice()` 의 「이미 발행됨」 관문이 열린 채 지나갔고
2. 같은 문서번호로 다시 내다 팝빌에 막혔고(`-11001038` — 이중 신고는 면했다)
3. 실패했으니 「신고가 막혀도 종이는 남긴다」 길로 빠져
4. **상호ㆍ등록번호가 아직 없는 그 낡은 주문으로** 양식을 그려 붙였다

주소만 찍힌 것도 같은 까닭이다 — `TaxInvoiceForm::parties()` 는 등록번호가 비면
개인 건으로 보고 환자 주소로 물러난다.

#### 고친 것

`DepositAutoIssue::돌기()` 와 `PaymentDoneNotice::보내기()` 첫머리에서 빗장을 얻은
뒤 `$order->refresh()` 로 **표에서 다시 읽는다.** 뒤에 든 쪽이 앞선 쪽의 결과를 보므로
「이미 발행됨」에서 제대로 멈춘다.

발행이 성공한 건의 세금계산서는 서류 관리에 이미 제대로 들어 있다
(`prescription_documents` #14 · 20:28:26 · `세금계산서_최연아_EUD202609302000191.pdf`).
잘못 그려진 첨부 #10721 은 시험 이력이므로 지우지 않는다.

**CASE 3** — 위임장 대신 요양비 지급청구서(「시군구청에 내는 서류」).

무통장만) · 세금계산서 건너뜀.

## 3. 오류 — ⑤를 「가장 급하다」고 과하게 말했다

기초(지자체) 건에 **자동 팩스가 공단으로 나간다**고 보고했다. 팩스가 나간다고 단정하기
전에 **서류 관문을 확인하지 않았다.**

`NhisFaxAuto::REQUIRED` 는 네 서류를 모두 요구하고 그 가운데 **요양비위임장**이 있다.
기초는 `위임장받나 = false` 라 위임장을 만들지 않고, `delegationDoc()` 의 대체 경로
(같은 환자의 지난 위임장)도 끌어올 것이 없다.

```

fax_histories 0줄
```

**즉 지금 기초 건에서 자동 팩스가 나갈 수 있는 건은 0건이다.** 스위치는 켜져 있고
(`nhis_fax_on_consent`ㆍ`on_id_card` true · `fax_mode` live) 사람이 누르는 것도 아니지만,
서류 관문이 먼저 막는다.

**바로잡음** — 「팩스가 나간다」가 아니라 「나가지 못한다」다. 다만 우연히 다른 칸이
막은 것이고 지자체라서 막은 것은 아니다.

## 4. 남는 실제 불편 — 채울 수 없는 서류를 요구한다

기초 건은 `needsDelegation = true` 라 서명을 받고, 서명이 끝나면 `NhisFaxAuto::attempt`
가 돌아 `tell()` 로 담당자 채팅방에 이렇게 쌓인다.

```

```

요양비위임장은 기초 건에 만들어지지 않으므로 **담당자가 채울 방법이 없다.** 서명 완료
때ㆍ신분증 도착 때마다 반복된다. 원인은 `NhisFaxAuto` 가 `claim_agency` 를 한 번도 읽지
않는 것이다(0회).

담당자가 위임장 파일을 **첨부로** 올리면(`prescription_attachments.doc_type='delegation'`)
관문이 충족되어 그때는 공단 지사로 나간다 — 사람의 행동이 필요한 경로다.

**지시: 「지자체는 자동 팩스 수동 팩스 모두 사용안하는데 수정해야하나요?」 → 고치지

## 6. 배포에 php-fpm reload 가 꼭 필요한가 — 설정을 읽어 확인

**필요 없다.** 운영 FPM 이 물고 있는 값(`php -c /etc/php/8.3/fpm/php.ini` 로 확인):

```

opcache.validate_timestamps    '1'   ← 파일 시각을 다시 본다
opcache.revalidate_freq        '2'   ← 2초마다
opcache.preload                ''    ← 안 쓴다
opcache.file_update_protection '2'
```

`php.ini`·`conf.d`·pool 어디에도 opcache 를 덮는 줄이 없어 PHP 기본값 그대로다.
코드만 바뀌는 배포는 **2초 안에 저절로 갈린다.**

| 바뀐 것 | reload 필요? |
|---|---|
| PHP 코드·blade | 아니오 |
| `.env`·설정값 | 아니오 — `config:clear` 로 된다(배포 스크립트가 이미 함) |
| 마이그레이션 | 아니오 |
| `php.ini`·conf.d·FPM pool | **예** |
| `opcache.preload` 를 쓰거나 `validate_timestamps=0` 으로 바꿀 때 | **예** |

### 502 의 까닭

`php-fpm.conf:82` 의 `;process_control_timeout = 0` — 주석 처리, 기본값 0 이다.
마스터가 `SIGUSR2`(reload)를 받으면 워커에게 종료 신호를 보내고 이 시간만큼
기다린 뒤 남은 워커를 강제로 죽이는데, **0 은 기다리지 않는다**. 그래서

`/broadcasting/auth` 세 건이 502 로 끊겼다. 여기에 `pm.max_children = 5` 가
겹친다 — 동시에 다섯 요청뿐이라 워커가 한꺼번에 갈리면 밀림이 크다.

### 고친 것 (2026-10-01 08:44 UTC)

```

```

백업은 `php-fpm.conf.bak-20261001`. `php-fpm8.3 -t` 통과.

**reload 는 돌리지 않았다.** 업무 중(KST 17:42)이었고, 서명 동의 폴링·토스
웹훅·환자 등록이 돌고 있었다. 돌릴 까닭도 없다 — **다음 배포의 reload 가

graceful 해진다.

## 1. SR 답변 창에 빈 입력칸이 쌓인다

### 드러난 모습

「답변」 항목에 **빈 입력칸**이 있고, 그 아래 입력칸에 담긴 답변이 보인다.
위 칸에 글을 적어도 저장되지 않는다 — 저장은 `#srxAnswer` 의 것을 읽는다.

### 어떻게 재현했나

추측하지 않고 운영 화면을 열어 DOM 을 쟀다(보기만 했다).

| 한 일 | `.ce-quill` 안 |
|---|---|
| 한 번 열기 | 도구막대 1 · 편집기 1 — **정상** |
| 두 번째 열기 | 도구막대 2 · 편집기 2 |
| 세 번째 열기 | 도구막대 3 · 편집기 3 |

늘어난 쪽은 `DIV.ql-toolbar ql-snow ql-container` — **도구막대인데 편집기 그릇도
된 것**이다. 즉 Quill 이 **앞서 만든 도구막대를 자리 삼아** 또 섰다.

`ceQuill.make` 를 감싸 인자를 찍어 자리를 특정했다.

```
받은것: "ql-toolbar ql-snow"
스택:   at Object.열기 [as open] (sr:3656) → NodeList.forEach → sr:3657
```

### 까닭

`srxPop.open()` 이 창을 열 때마다 이렇게 돌았다.

```js
el.querySelectorAll('.ce-quill > div').forEach(자리 => ceQuill.make(자리, …));
```

Quill 은 세워지면서 **도구막대를 같은 자리 안에** 끼워 넣는다. 그래서 두 번째
열기부터 그 도구막대까지 함께 집혀 편집기로 섰다.

`ceQuill` 자체는 멀쩡했다 — 따로 재현판을 띄워 네 갈래(한 번 열기 · 닫았다 열기 ·
거의 동시에 두 번 · `__quill` 을 지운 뒤)를 모두 돌려 보았고 전부 정상이었다.
부르는 쪽의 선택자가 문제였다.

### 고침

두 곳을 고쳤다.

```js
// ① 부르는 쪽 — Quill 이 붙이는 이름표를 빼고 고른다
el.querySelectorAll('.ce-quill > div:not(.ql-toolbar):not(.ql-container)')

// ② 받는 쪽 — 도구막대를 받으면 그 자리에서 거절한다(ceQuill.make)
if (el.classList.contains('ql-toolbar')) return null;
```

①만 고치면 새로 쓰는 화면에서 또 빠뜨린다. ②를 함께 둔 까닭이다.

### 내가 처음 잘못 짚은 것

담긴 HTML 이 깨진 줄 알고 원문부터 봤다 — `<p>` 넷이 모두 닫힌 멀쩡한 글이었다.
그 다음에는 「편집기가 두 겹으로 섰다」고 짐작했는데, 짐작으로 고치지 않고 재현해
보니 겹친 것이 아니라 **도구막대가 그릇이 된 것**이었다. 재현 전에 고쳤으면
엉뚱한 자리를 건드렸다.

브라우저 캐시가 깨져(`ERR_CACHE_READ_FAILURE`) CDN 이 하나도 안 받아지는 바람에
첫 측정에서 「Quill 이 아예 안 섰다」로 읽혔다. 그것은 내 환경 탓이었고, 주소에
값을 붙여 캐시를 비켜 간 뒤 제대로 쟀다.

### 고침

`Setting` 줄을 바로 고쳐 `'1'` 로 되돌리고 활동 기록에 남겼다. 나머지 토스

설정값이라 배포 없이 곧바로 먹으며, **이미 나가 있는 링크에도 적용된다** —
김순태 님 링크를 열어 카드ㆍ가상계좌 두 갈래가 다시 서는 것을 확인했다.

### 되짚을 것

이 함정은 **기억에 적어 두고도 또 밟았다**(2026-10-01 에 한 번 적었다). 적어
두는 것만으로는 막히지 않는다. 설정 화면을 거쳐 한 칸만 바꿀 때는 **저장 직후

**① `mark()` 가 메모를 지웠다.**

```php
'memo' => $request->input('memo'),   // 안 보내면 null 로 덮는다
```

**② `mark()` 에 권한 검사가 없었다.** 화면을 볼 수 있는 사람이면 누구나 상태를
바꿀 수 있었다. `abort_unless(perm('error-logs','update'), 403)` 을 세웠다.

### 다시 그릴 때 코드를 어디서 찾는가

`wwGrid` 의 renderer 는 `getData()` 가 떠 준 **사본**을 받는다. 그래서 `row.state_key`

코드를 되찾는다(`코드찾기[딱.textContent.trim()]`).

딱지에 `<i>` 를 덧붙여도 `textContent` 는 글만 돌려주므로 `trim()` 하나로 족하다.

### #13 은 우리 코드로 짚지 못했다

`Uncaught SyntaxError: Unexpected end of input` 1건. 찾은 것은 이렇다.

- 그 화면은 **10-02 00:59:32(UTC)** 에 온전히 받았다 — nginx 기록 200ㆍ510,300바이트.
  오류는 **01:17:51**, 즉 **18분 뒤**다. 처음 받은 글이 끊긴 것이 아니다.
- 그 시각 그 화면을 다시 부른 기록이 없고, 5xx 도 없다.
- 오류 자리가 `…:1:20` 이다. 문서의 인라인 스크립트라면 **문서 안의 실제 줄번호**가
  찍힌다(10-02 11:26 에 내가 낸 것은 `4191:24` 였다). `1:20` 은 **따로 만들어진
  스크립트**를 가리킨다.
- 그런데 `resources/views` 를 통틀어 글을 코드로 돌리는 자리(`new Function`ㆍ`eval`ㆍ
  글을 넘기는 `setTimeout`)가 **하나도 없고**, 이 화면에는 `<script>` 를 다시 만드는
  자리도 없다.

그래서 **우리 코드에서 날 수 있는 길을 찾지 못했다.** 확장 프로그램이 끼워 넣은
스크립트일 수 있으나(수집기는 `chrome-extension://` 로 **시작하는 것만** 거른다.
확장이 문서 안에 끼워 넣으면 주소가 우리 것으로 찍혀 걸러지지 않는다) **단정하지
않는다.** 한 번 났고 자취에 발자국이 없어 더 짚을 것이 없다.

④ 를 고쳤으므로 **또 나면 「미확인」으로 되살아난다.** 그 자리에서 다시 본다.
