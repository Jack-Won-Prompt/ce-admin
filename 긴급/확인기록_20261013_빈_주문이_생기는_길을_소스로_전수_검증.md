# 빈 주문이 생기는 길을 소스로 전수 검증했다 — 한 군데가 아직 뚫려 있었다

- 날짜 : 2026-10-13
- 지시 : 「빈주문 그냥 생성되는것 수정한게 앞으로 안생기게 수정이 잘 되었는지 소스 레벨로 다시 확인 정밀 검증」
- 결과 : **뚫린 자리가 하나 더 있었다.** 막고 운영에서 되돌리는 거래로 전수 확인했다.
- 올린 것 : `080d6382`

## 주문이 만들어지는 자리는 셋뿐이다

`app/` 전체에서 `Order` 를 만드는 자리를 모두 찾았다(씨앗 파일 제외).

| 자리 | 무엇 | 문턱 |
|---|---|---|
| `OrderController.php:898` | 「주문 생성 및 연계」 | 제품ㆍ유형ㆍ청구전략ㆍ위임 서명ㆍ동의ㆍ재구매 창 — 여섯 |
| `PrescriptionController.php:4220` | 추가 주문 | 원 주문이 있어야 하고 처방 총계를 넘을 수 없다 |
| `OrderSync.php` | 저장ㆍ서명 완료ㆍ검수 승인이 쓰는 자리 | **여기가 문제였다** |

앞의 둘은 담당자가 단추를 눌러야 지나는 길이고 문턱이 단단하다. 빈 주문이 난 것은 셋째다.

## 무엇이 뚫려 있었나

`OrderSync` 에는 함수가 둘이다.

- `seed()` — 없으면 만들기만 한다. **다섯 문턱이 여기 안에 있었다.**
- `ensure()` — 없으면 만들고, 있으면 값을 맞춘다. **문턱이 없었다.**

`ensure()` 를 바로 부르는 자리가 둘 있었다.

```
ConsentController        서명 완료 → ensure        (2026-10-13 아침에 고침)
PrescriptionController   검수 승인 → ensure        ← 아직 뚫려 있었다
```

`approve()` 의 주석에는 「유형이나 거래처가 아직이면 `OrderSync::ensure` 가 세우지
않는다」고 적혀 있었는데 **사실이 아니었다.** `ensure` 에는 그런 조건이 없다.

### 운영에서 되돌리는 거래로 확인했다

고치기 전, 주문을 만들어 보고 곧바로 `rollBack` 했다.

```
검수 pending · 유형 있음 · 거래처 있음   ensure → 주문 생성 ✗   seed → null ✓
위임동의 껍데기                          ensure → 주문 생성 ✗   seed → null ✓
위드웍스 구매확정ㆍ취소                  ensure → null ✓        seed → null ✓
갖춘 건                                  ensure → 주문 생성 ✓   seed → 주문 생성 ✓

되돌린 뒤 주문 수 그대로 · 열려 있는 거래 0
```

`ensure` 가 문턱 없이 만든다는 것이 그대로 드러났다.

## 어떻게 고쳤나 — 부르는 자리가 아니라 **만드는 자리**에 둔다

호출하는 자리마다 막는 방식은 **세 번 샜다** — 2026-09-22(저장), 2026-10-02(유형 선택),
2026-10-13(서명 완료ㆍ검수 승인). 길이 늘어날 때마다 같은 일이 되풀이된다.

그래서 문턱을 `OrderSync::만들수있는가()` 한 곳으로 옮기고, **`ensure()` 가 주문을 새로
만들기 전에 반드시 그것을 지나게** 했다.

```php
public static function 만들수있는가(Prescription $p): bool
{
    // 빈 초안 · 상담만 · 위드웍스 마감 · 유형 · 검수 승인 · 거래처  — 여섯
}

public static function ensure(Prescription $p): ?Order
{
    $order = $p->order()->first();

    if (! $order && ! self::만들수있는가($p)) {
        return null;          // 만들 때만 막는다
    }
    …                          // 이미 선 주문은 그대로 값을 맞춘다
}

public static function seed(Prescription $p): ?Order
{
    if ($p->order()->exists()) {
        return null;          // seed 와 ensure 가 갈리는 자리는 이것뿐이다
    }
    return self::ensure($p);
}
```

`seed()` 에서 문턱을 한 번 더 보지 않게 했다 — `상담만인가()` 하나가 관계를 세 번 묻는데
이 자리는 처방전이 저장될 때마다 지나간다. 두 벌 돌 일이 아니다.

`ensureOrder()`(PrescriptionController)는 지금 부르는 곳이 없다. 지우지 않고 그 사실과
「다시 이어 써도 빈 주문이 나지 않는다」를 적어 두었다.

## 고친 뒤 전수 검증 (운영 · 되돌리는 거래)

### 하나 — 지금 남아 있는 건으로

```
검수가 안 끝났다            ensure → null ✓   seed → null ✓
위임동의 껍데기             ensure → null ✓   seed → null ✓
위드웍스 구매확정ㆍ취소     ensure → null ✓   seed → null ✓
빈 초안                     ensure → null ✓   seed → null ✓
상담만 적어 두었다          ensure → null ✓   seed → null ✓
갖춘 건                     ensure → 생성 ✓   seed → 생성 ✓
이미 선 주문                ensure → 맞췄다 ✓
```

### 둘 — 남아 있는 건이 없는 두 모양은 거래 안에서 만들어 시험했다

갖춘 처방전(WW-93029)을 바탕으로 한 칸씩 무너뜨려 보았다.

```
유형을 비웠다                 → null ✓
유형을 빈 글자로 두었다       → null ✓
거래처를 떼었다               → null ✓
검수를 pending 으로 되돌렸다  → null ✓
빈 초안으로 바꿨다            → null ✓
위드웍스 구매확정으로 바꿨다  → null ✓
위드웍스 취소로 바꿨다        → null ✓
손대지 않았다 (갖춘 건)       → 주문 생성 ✓
```

### 셋 — 값 맞추기가 막히지 않는지

문턱이 값 맞추기까지 막으면, 자격이 바뀌어 본인부담이 달라진 주문에 옛 셈이 남는다.

```
[WW-ADD0068090] 검수를 pending 으로 되돌리고 유형도 비운 뒤 ensure
   → 주문 EUD202610010907331 을 그대로 맞췄다 ✓
   → 그 사이 새 주문이 생기지 않았다 ✓
```

### 되돌려졌는가

```

열려 있는 거래 0 ✓
```

## 남는 길은 둘뿐이고 둘 다 담당자가 눌러야 한다

이제 주문이 새로 만들어지는 길은 셋이고, 모두 문턱을 지난다.

1. `OrderSync` — 여섯 문턱(만들수있는가)
2. 「주문 생성 및 연계」 — 여섯 문턱
3. 추가 주문 — 원 주문이 있어야 한다

어느 길로 `OrderSync::ensure` 를 부르더라도 빈 주문이 나지 않는다.

## 내가 틀렸던 것

아침에 위드웍스 조건만 `ensure` 에 넣고 「막았다」고 보고했다. 그 조건은 위드웍스 건에만
맞는 것이었고, 유형ㆍ거래처ㆍ검수ㆍ빈 초안ㆍ상담만은 여전히 `seed` 안에만 있었다.
`approve()` 가 `ensure` 를 바로 부르므로 그 다섯은 그대로 비어 있었다 — 소스의 주석이
「ensure 가 세우지 않는다」고 적어 둔 것을 그대로 믿은 것이 잘못이다. 주석이 아니라
`ensure` 의 몸통을 읽었어야 했다.
