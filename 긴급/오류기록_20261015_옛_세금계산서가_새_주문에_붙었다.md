# 옛 세금계산서 세 줄이 엉뚱한 주문에 붙어 있다 (2026-10-15)

## 어떻게 드러났나

「주문이 이유 없이 생성되었는지」를 보다가, 품목도 창고도 없는 껍데기 주문 178건 중
**한 건만 삭제가 막히는 것**을 발견했다. 막은 말은 「세금계산서가 발행된 주문은 삭제할
수 없습니다」였는데, 그 주문의 `orders.tax_invoice_status` 는 `not_issued` 였고 발행
번호도 금액도 없었다.

삭제 잣대는 그 칸을 보지 않는다. `app/Models/Order.php:587` 은 `popbill_taxinvoices`
표에 그 주문 id 로 된 줄이 있는지만 본다. 그 줄을 열어 보니 **다른 사람의, 두 달 전
계산서**였다.

```
주문 EUD202610011206181 · (E)김주환A · 만든때 2026-10-01 12:06
  popbill_taxinvoices #49
     mgt_key            TI20260824000034
     write_date         20260824          ← 주문이 생기기 38일 전
     invoicee_corp_name 한희성             ← 주문의 환자가 아니다
     total_amount       3,499,200
     state_code         600 (발행취소)
```

## 왜 붙었나

관리번호 규칙은 **접두사 + 발행일(Ymd) + 주문 id 여섯 자리**다
(`app/Support/PopbillLink.php`). `TI20260824000034` 의 끝 여섯 자리는 `000034` 이므로
주문 **#34** 로 읽힌다.

문제는 8월에 발행할 때의 주문 #34 와 지금의 주문 #34 가 **다른 주문**이라는 것이다.
그 사이에 시험 자료를 비우는 명령(`ResetBusinessData`ㆍ`ResetForRetest`ㆍ
`PurgeTestDataCommand`)이 `orders` 를 비웠고, 자동 번호가 처음부터 다시 매겨져 id 가
되쓰였다. 10월 1일에 새로 선 주문들이 8월에 쓰던 id 를 물려받았다.

`fromMgtKey()` 는 「그 id 의 주문이 **있는지**」만 확인한다 —

```php
return $id > 0 && Order::whereKey($id)->exists() ? $id : null;
```

있기는 있다. 다른 주문이지만.

## 어디에 몇 건인가

잣대를 짐작이 아니라 시각으로 세웠다 — **주문이 생기기 전에 발행된 것은 그 주문의 것일
수 없다.** 운영에서 이어진 줄 전부를 견주었다.

```
세금계산서  이어진 줄 369건 중 어긋남 3건
   TI20260825000033 · 발행 20260825 · 이희영 · 3,499,200원 · 600
      → EUD202610011204151 ((E)김서영) 생성 20261001
   TI20260824000034 · 발행 20260824 · 한희성 · 3,499,200원 · 600
      → EUD202610011206181 ((E)김주환A) 생성 20261001
   TI20260813000010 · 발행 20260813 · 정하준 ·    39,450원 · 600
      → EUD202610010927221 ((E)이승원) 생성 20261001
현금영수증  이어진 줄 210건 중 어긋남 0건
```

**세 줄 모두 상태 600(발행취소)다.** 국세청에 살아 있는 신고가 엉뚱한 환자에게 붙은
것은 아니다. 현금영수증은 팝빌이 주문번호를 그대로 돌려주어 관리번호를 뜯지 않으므로
한 건도 어긋나지 않았다.

## 무엇이 잘못 보이나

1. 전자세금계산서 화면에서 그 세 줄의 주문번호ㆍ환자가 **엉뚱한 사람으로** 보인다.
2. 그 주문 세 건은 **삭제가 막힌다** — 품목도 결제도 없는 껍데기인데 지울 수 없다.
3. 주문 상세에서 발행 자취를 그 표로 읽는 자리가 있으면 남의 금액이 섞인다.

## 손으로 비우면 남아 있나 — 남는다

처음에는 「다음 동기화가 다시 채운다」고 적었다. 소스를 다시 읽어 바로잡는다.

세금계산서 목록 화면은 팝빌에서 그 기간을 통째로 받지만, **이미 있는 줄에는
`state_code`ㆍ`state_dt`ㆍ`is_final`ㆍ`synced_at` 넷만 다시 적는다**
(`app/Http/Controllers/Popbill/TaxinvoiceController.php:160`). `order_id` 는 줄을
**새로 만들 때만** 적힌다. 그러니 비워 두면 그대로 남는다.

바꾸어 말하면, 코드를 고치지 않고 비우기만 하면 그 줄이 지워졌다 다시 서는 날
되돌아온다. 고치는 것이 먼저다.

## 고친 자리

`PopbillLink::fromMgtKey()` 가 id 의 존재만 보지 않고 **그 주문이 발행일에 이미
있었는지**까지 본다. 관리번호의 날짜 여덟 자리를 함께 뽑아 쓴다.

```php
private const MGT_KEY = '/^(?:TI|CRC|CR)(\d{8})(\d{6})/';
...
$생긴때 = Order::withTrashed()->whereKey($id)->value('created_at');
return Carbon::parse($생긴때)->format('Ymd') <= $발행일 ? $id : null;
```

지워진 주문도 함께 본다. 발행 기록은 주문을 지워도 남아야 하므로, 지운 주문을 없는
것으로 보면 멀쩡히 이어져 있던 건이 제 자리를 잃는다.

## 남은 일 — 세 줄의 연결을 비우는 것

운영 자료를 고치는 일이라 이 자리에서는 막혔다(권한). 사람이 열어 주면

```
popbill_taxinvoices #48ㆍ#49ㆍ#50 의 order_id 를 null 로
```

비운다. 발행 기록(관리번호ㆍ국세청 승인번호ㆍ금액)은 손대지 않는다 — 국세청에 이미
간 것이라 우리 쪽 사정으로 없앨 수 없다. 끊어만 둔다.

비운 뒤에는 그 주문 세 건의 삭제가 열린다.
