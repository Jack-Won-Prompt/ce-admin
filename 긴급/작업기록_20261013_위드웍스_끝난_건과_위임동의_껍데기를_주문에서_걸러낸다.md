# 주문이 서지 말아야 할 건에 주문번호가 나던 세 자리를 막았다

- 날짜 : 2026-10-13
- 지시 : 「진행」 (확인기록 둘에 대한 승인) + 「처방전 없는데, 모바일로 서명 동의 받는 경우, 주문등록 라인이 생기고 있음 / 주문등록에서 서명동의완료 아닌 경우, 정보 입력 후 저장 누르기만 하면 서명동의 메세지가 전송 되고 있어 확인 필요 재발 방지」
- 올린 것 : `b7b5eb98` · `23a328be` · `0c89d3d8`

## 하나 — 위드웍스에서 이미 판매가 끝난 건

### 막은 것

`OrderSync::ensure()` 맨 앞에 조건을 하나 두었다.

```php
if (! $order && $prescription->위드웍스마감인가()) {
    return null;
}
```

- 주문이 **아직 없을 때만** 막는다. 이미 만들어진 주문과, 우리가 창고로 보낸 주문
  (`withworks_so_no` 가 있는 것)은 금액 맞추기가 그대로 돈다.
- 검수 승인은 그대로 된다. `PrescriptionController::approve()` 가 활동 이력과 응답 문구로
  「위드웍스에서 이미 판매가 끝난 건이라 주문은 만들지 않았습니다」를 알린다.

### 지운 것

잘못 발급된 주문 **61건을 소프트 삭제**했다. 지우기 전에 밖으로 나간 것이 하나도 없음을
확인했고(창고 판매번호 0 · 토스 결제 0 · 결제 링크 0 · 세금계산서 0 · 현금영수증 0 ·
교환반품취소 0), 하나라도 있으면 멈추도록 스크립트에 조건을 두었다.

주문마다 활동 이력을 남겼다 — 「소프트 삭제 (2026-10-13 지시) — 위드웍스에서 이미 판매가
끝난 건에 우리 주문번호가 발급된 것입니다. 저쪽 출고 … · 판매번호 … 되살리려면 주문 #N 을
restore 하십시오.」 처방전에도 같은 뜻을 적었다.

```
위드웍스에서 끝났는데 우리 주문이 있는 것 : 61건 → 0건
지워진 것으로 보이는 것 : 61건
처방전 61장 — 지우지 않았다
등록일 10월로 조회하면 : 613건 → 555건
```

(613 은 지우기 직전 값이다. 조사를 시작한 아침에는 610건이었고, 그 사이 새 주문이 늘었다.)

### 되살리는 길

```php
App\Models\Order::onlyTrashed()
    ->whereHas('prescription', fn ($p) => $p->whereNotNull('ww_closed_at')->orWhere('ww_cancelled', 1))
    ->restore();
```

## 둘 — 위임동의를 보내려고 만든 처방전

### 칸을 하나 두었다

`prescriptions.is_consent_only` (마이그레이션 `2026_10_13_160000`).

`upload_source` 가 일반 웹 등록과 똑같은 `web` 이라 코드로 가려낼 방법이 없었다.
지난 건은 활동 이력의 「위임동의용 처방전 생성」으로 찾아 채웠다 — **30장**이 붙었다.

### 주문 목록에서 뺀 것

`주문없는처방전줄들()` 에 조건 둘을 더했다.

1. **상담만 적어 둔 건** — `Prescription::scopeCounselOnly` 를 그대로 뒤집은 것.
   주문을 만드는 쪽은 2026-09-14 지시로 이미 빼고 있었는데 보여 주는 쪽이 빼지 않아,
   주문으로는 넘어갈 수 없는 건이 목록에만 나왔다.
2. **위임동의 껍데기** — `is_consent_only` 가 붙었고 이미지ㆍ첨부ㆍ품목이 하나도 없는 것.
   서류가 올라오거나 품목이 담기면 그때부터는 보여 준다.

이 조건으로 지금 빠지는 것은 **12장**이다 ((E)이순옥 RX-20261013-020 포함).

### 기존 거래처를 찾아 연결하게 했다

「신규 위임동의」가 휴대폰으로 거래처를 찾아 연결한다. 붙임표가 있는 꼴과 없는 꼴을 모두
찾고, **같은 번호를 쓰는 거래처가 둘 이상이면 연결하지 않는다** — 32개 번호가 그렇다.
활동 이력에 「거래처 …(#N) 연결」 또는 「연결할 거래처 없음」을 적는다.

(E)이순옥 님이 그 보기다 — 010-6202-2667 로 보냈는데 같은 번호의 거래처 #2764 가 이미
있었고 처방전 19장이 쌓여 있었다.

## 셋 — 모바일 서명만으로 주문이 생기던 자리

`ConsentController` 가 서명 완료에서 `OrderSync::ensure()` 를 바로 불렀다. `ensure` 에는
문턱이 없다 — `seed` 가 가진 다섯(빈 초안ㆍ상담만ㆍ유형ㆍ검수 승인ㆍ거래처)을 모두
건너뛰고 주문번호를 발급한다.

주문 등록의 저장이 쓰는 갈림과 같은 모양으로 바꿨다.

```php
$처방전->order()->exists()
    ? OrderSync::ensure($처방전)   // 이미 있으면 금액만 맞춘다
    : OrderSync::seed($처방전);    // 없으면 다섯 문턱을 거친다
```

### 그렇게 생긴 주문이 지금 23건 있다

```
지금 서 있는 주문 가운데 seed 문턱을 못 넘는 것 : 23건
   유형이 비어 있는 것 : 12건
   검수가 안 끝난 것   : 23건
   그중 「주문등록 이동」 자취가 없는 것 : 19건
모두 품목 0줄ㆍ0원
```

앞서 지운 6건(RX- 로 시작하는 것)과 같은 모양이다. **아직 지우지 않았다** — 지시를 기다린다.

## 넷 — 저장만 눌러도 서명동의가 나가던 것

설계된 동작이고, 설정 화면의 스위치가 켜져 있었다.

```
settings.consent_sms_on_first_save = 1   ← 켜짐
settings.rx_received_sms_on_first_save = 1
settings.consent_sms_hours = 09:00-23:30
```

`PrescriptionController::updateOcr()` 가 저장 끝에 `consentSmsOnFirstSave()` 를 부른다.
그 안에 막는 조건이 여럿 있지만(거래처 없음ㆍ이미 보낸 분ㆍ서면 위임장ㆍ발송 시간),
**처음 오는 분이면 저장 한 번에 서명 링크가 나간다.**

끄는 자리는 설정 화면의 **「첫 저장에 위임동의 발송」** 한 칸이다. 코드를 고칠 일이
아니라 스위치를 내리면 되고, 손으로 누르는 발송 단추는 그대로 쓸 수 있다.

**아직 끄지 않았다** — 환자에게 나가는 통로를 바꾸는 일이라 지시를 받고 하겠다.
