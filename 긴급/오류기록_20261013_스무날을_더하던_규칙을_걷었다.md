# 다음 재구매 가능일에 스무 날을 더하던 규칙을 걷었다

- 날짜 : 2026-10-13
- 물음 : 「사용시작일 + 총 처방일수 = 다음 재구매 가능일이고 급여종료일 + 1일인데,
  맞는 환자도 있고 다르게 보이는 환자도 있어서 확인」 → 「스무 날이 붙는 건은 없어야
  하지 않나요?」
- 고친 것 : `e915bd6e` → `7e3fe7b4`

## 전제가 한 장도 성립하지 않았다

「Five/Six(110days)」 건에 스무 날을 더하던 규칙이 있었다. 더하는 까닭은 **「90일
처방이지만 110일분을 받아 간다」**는 것이었다.

| 잣대 | 수 |
|---|---|
| 스무 날이 붙어 있던 건 | 112장 |
| 그중 총계 = 1일 개수 × 총처방일수 (**처방일수만큼만** 받음) | **112장** |
| 그중 110일분(1일개수 × 110)을 받는 건 | **0장** |
| 운영 전체에서 110일분을 받아 간 처방전 | **0장** |
| 총 처방일수가 110인 처방전 | **0장** |

보기 — `1일 6개 · 일수 90 · 총계 540`. 110일분이면 660이어야 한다.

## 깃발도 어긋나 있었다

SR #103 의 요청은 「Five/Six**(110days)** 정보 있으면 +20」이다. 그런데 그 칸이
이관분 73,754건에 **날짜**를 담고 있어 못 쓴다는 까닭으로, 2026-10-07 에 깃발을
「Five/Six」 **선택 칸(05ㆍ06)** 으로 바꿨다. 그 둘은 다른 것이다.

- `five_program` 05ㆍ06 은 1일 개수와도 맞지 않는다 — 05 인데 1일 6개가 8,403장,
  06 인데 1일 6개가 9,436장
- 「Five/Six(110days)」 칸은 **우리가 올린 처방전 564장 가운데 값이 있는 것이 0장**이다

## 걷었다 — 자리가 **셋**이었다

```
다음 재구매 가능일 = 사용 개시일 + 총 처방일수   (= 급여 종료일 다음 날)
```

| 자리 | |
|---|---|
| `App\Support\BenefitDates::apply()` | 걷음 |
| 주문 등록 화면의 `calc다음재구매()` | 걷음 |
| **`App\Models\Prescription` 의 `saving` 훅** | **처음에 못 찾아 빠뜨림** |

앞의 둘만 걷고 112장을 다시 세었더니 **값이 하나도 바뀌지 않았다.** `apply()` 는 참을
돌려주는데 날짜가 그대로였다. 되짚어 보니 모델의 저장 훅이 저장할 때마다 다시 세면서
+20 으로 덮어쓰고 있었다 — **그 자리가 마지막 말을 한다.** 셋을 다 걷어야 했다.

110일분을 받아 가는 거래가 실제로 생기면 그때 조건을 다시 정한다 — 없는 거래에 맞춰
날짜를 미루면 **그만큼 환자가 못 산다.**

## 이미 저장된 112장을 다시 셌다

`BenefitDates::apply()` 를 그대로 불렀다 — 셈하는 자리는 한 곳이어야 한다. 바뀐 것은
다음 재구매 가능일 하나이고 급여 종료일은 그대로다(돌린 뒤 하나씩 확인했다).

## 재어 본 것 (운영, 돌린 뒤)

| 잣대 | 결과 |
|---|---|
| 급여 종료일 = 사용개시일 + 총처방일수 − 1 | **250/250 맞음 · 틀림 0** |
| 다음 재구매 = 사용개시일 + 총처방일수 | **250/250 맞음 · 틀림 0** |
| 스무 날이 붙는 건 | **0장** |
| (E)이건우 · RX-20261001-014 | 급여종료 2026-12-29 · 다음 재구매 **2026-12-30** |

알려 주신 그대로다.

## 내가 놓친 것

- **같은 규칙이 세 곳에 흩어져 있는 것을 처음에 다 찾지 못했다.** 둘만 고치고 「다시
  셌다」고 할 뻔했다 — 돌린 뒤 값을 다시 읽어 보았기에 드러났다. 고친 뒤에는 늘 값을
  되읽는다.
- 검증 스크립트가 **옛 규칙을 잣대로 쓰고 있어** 바로잡은 자료를 「틀림 112장」이라
  적었다. 자료가 아니라 잣대가 낡은 것이었다 — 규칙을 바꾸면 검증하는 쪽도 함께 고친다.
