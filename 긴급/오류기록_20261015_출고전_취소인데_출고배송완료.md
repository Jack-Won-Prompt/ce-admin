# 출고 전 취소로 접수했는데 출고ㆍ배송이 완료되었다 (2026-10-15 확인요청)

## 신고 내용

(E)이정현A 건은 **출고 전 취소**로 접수했는데

- 증빙이 (+)로 발행되어 있고
- 송장이 붙어 **배송완료**되었으며
- 위드웍스 판매주문은 취소로 보이지 않고
- 취소 관련 (−) 증빙도 없다

## 원인 ① — 판매주문이 취소되지 않은 까닭

접수 시 창고에 무엇을 보낼지는 **송장ㆍ출고번호 유무**로 정한다.

```php
// app/Services/WithworksReturns.php
private function isPreShipCancel(OrderReturn $return, Order $order): bool
{
    return !$order->withworks_ship_no && !$order->withworks_tracking_no;
}
```

10-13 09:46 접수 시점에 `withworks_ship_no = SH2610120475` 가 이미 있었다. 결제 완료
직후(10-12 17:25) 창고가 출고 줄을 세웠기 때문이다. 따라서 **출고 후**로 판단해
`cancelOrigin()`(원 판매주문 취소)이 아니라 `storeReturn()`(반품주문 등록)을 실행했다.

창고에 실제로 등록된 것.

```
반품주문 RT2610130002 · 유형 1504 · 상태 02(등록) · 10-13 09:46:33
   remark : [CE-ADMIN 반품] (cancel) 기타 — 10.12 병원입원으로
```

**원 판매주문 S2610120389 는 95(확정) 그대로**였고, 예정대로 출고되어 배송까지 완료됐다.

## 원인 ② — 화면은 「출고 전 취소」라고 표시한 까닭

갈래 판정은 **사람이 고른 유형만** 본다. 실제 출고 여부를 보지 않는다.

```php
// app/Models/OrderReturn.php
return $this->subtype === self::SUB_REFUND_ONLY
    ? self::SC_REFUND_ONLY
    : self::SC_CANCEL_PRESHIP;
```

`type=cancel`ㆍ`subtype=before_ship` 이므로 화면에는 계속 「출고 전 취소」로 선다.
창고로 나간 것은 반품주문인데 화면은 취소라고 말한다 — **두 판정이 서로 다른 기준을
쓰고 있고, 어긋났을 때 아무도 알려 주지 않는다.**

접수 직후 담당자가 본 문구는 다음과 같다.

```
접수했습니다. 접수번호 RN202610130002 — 위드웍스에 전달했습니다.
```

판매주문을 취소하지 못했다는 말은 어디에도 없다.

## 원인 ③ — (−) 증빙이 없는 까닭

반품 건이 **접수 단계에 머물러 있다.**

```
RN202610130002 · 상태 received(접수) · 승인 - · 환불 - · 환불금액 81,000원
```

(−) 증빙과 결제 취소는 **반품 승인** 이후 단계에서 실행된다. 승인이 되지 않았으므로
하나도 실행되지 않았다.

```
세금계산서 TI20261012000576 · 상태 304(국세청 신고완료) · 취소 안 됨
결제 CARD 81,000원 · DONE · 취소금액 0원
```

반대로 증빙은 (+)쪽으로 더 늘었다. 10-13 출고가 확인되면서 자동 발행이 한 번 더 돌았다.

```
10-13 17:48  입금 확인 자동 발행(출고 확인) : 거래명세서 · 카드매출전표
10-13 17:48  입금 확인 자동 발행(출고 웹훅) : 거래명세서 · 카드매출전표
```

## 검토가 필요한 사항

**업무 처리**
물건이 이미 고객에게 전달되었으므로 「출고 전 취소」가 아니라 **반품** 절차로 진행해야
한다. 창고에는 이미 반품주문이 등록되어 있어 수거는 가능하다.

**시스템 수정안**

1. **접수 시 어긋남을 알린다.** 유형은 「출고 전 취소」인데 출고번호가 이미 있으면,
   판매주문을 취소하지 않고 반품주문을 세웠다는 사실을 접수 결과 화면에 명시한다.
   지금은 「위드웍스에 전달했습니다」로만 끝나 담당자가 취소된 줄 안다.
2. **갈래 판정을 실제 출고 여부와 맞춘다.** `scenario()` 가 출고 여부를 함께 보게 하면
   화면 표기와 단계 흐름이 실제 처리와 일치한다. 다만 기존 접수 건의 갈래가 바뀌므로
   영향 범위 확인이 필요하다.
3. **취소 접수된 주문에 증빙 자동 발행을 계속할지 검토.** 10-13 출고 확인 시 취소 접수
   상태였음에도 증빙이 추가 발행되었다.

읽기만 했다. 코드도 자료도 수정하지 않았다.

## 추가 확인 (2026-10-15 · 「출고 판단은 위드웍스 출고 완료가 아닌가요?」)

지적이 맞다. 판단 기준이 틀렸다.

```php
// 고치기 전
private function isPreShipCancel(OrderReturn $return, Order $order): bool
{
    return !$order->withworks_ship_no && !$order->withworks_tracking_no;
}
```

`withworks_ship_no` 는 창고가 **출고 줄을 세우는 순간** 생긴다. 판매주문 확정 직후이며,
그때 물건은 아직 창고에 있다. (E)이정현A 건의 시각을 보면 분명하다.

```
10-12 17:25:34  판매주문 확정 → 출고 줄 SH2610120475 생성 · 출고 상태 02(신규)
10-13 09:46:33  취소 접수                              ← 이때도 02(신규)
10-13 17:47:24  출고 완료
```

접수 시점의 출고 상태는 **02(신규)** 였다. 취소할 수 있는 건이었는데 출고번호가 있다는
이유로 「출고 후」로 갈렸다.

운영 전체에서 출고 전 취소로 접수된 건은 이 한 건뿐이고, **원 판매주문이 취소된 적은
한 번도 없다.**

### 고친 기준

```php
private function isPreShipCancel(OrderReturn $return, Order $order): bool
{
    if ($order->isShipped()) {
        return false;
    }

    if (in_array((string) $order->withworks_ship_status, WithworksSync::SHIPPED, true)) {
        return false;
    }

    return blank($order->withworks_tracking_no) && blank($order->tracking_number);
}
```

보는 것은 셋이다 — **출고 완료 상태(95 출고완료ㆍ98 오더종결)**, 우리 쪽 출고일,
송장번호. 하나라도 있으면 나간 것이다. 할당ㆍ피킹까지 간 건은 아직 「출고 전」으로 본다.

### 거절 대비

할당ㆍ피킹이 걸린 건은 창고가 취소를 거절할 수 있다. 그때 그대로 멈추면 반품 주문도
서지 않아 수거할 길이 없어진다. 취소가 막히면 **반품 주문으로 되돌아가고**, 그 사실을
접수 화면에 붉은 줄로 남긴다.

```
판매주문을 취소하지 못해 반품 주문으로 등록했습니다 — (창고가 돌려준 말)
창고에 원 판매주문 취소를 직접 요청해 주십시오.
```

여태는 반품 주문으로 나가도 「위드웍스에 전달했습니다」로만 끝나 담당자가 취소가 간
줄 알았다. 그 자리도 함께 고쳤다.
