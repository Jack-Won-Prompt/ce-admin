# 주문 등록에서 저장만 눌러도 위임동의 알림톡이 나갔다 — 437통

- 날짜 : 2026-10-13
- 지시 : 「주문등록에서 서명동의완료 아닌 경우, 정보 입력 후 저장 누르기만 하면 서명동의 메세지가 전송 되고 있어 확인 필요 재발 방지」 → 「첫 저장에 위임동의 발송 끄고, 그렇게 생성건 확인」
- 처리 : 설정 한 칸을 껐다. 코드는 고치지 않았다.

## 무엇이 일어났나

`PrescriptionController::updateOcr()` 가 저장 끝에서 두 가지를 잇달아 부른다.

```php
$rxSms      = $this->rxReceivedSmsOnFirstSave($prescription);   // 5063줄
$consentSms = $this->consentSmsOnFirstSave($prescription);      // 5064줄
```

`consentSmsOnFirstSave()` 안에는 막는 조건이 여럿 있다 — 거래처가 없거나, 이미 보낸
분이거나, 서면 위임장을 받아 두었거나, 발송 시간(09:00-23:30) 밖이면 보내지 않는다.
그런데 **처음 오는 분이면 저장 한 번에 서명 링크가 환자에게 나간다.** 담당자는 정보를
입력하고 저장을 눌렀을 뿐이다.

이것은 결함이 아니라 설계된 동작이고, 설정 화면의 스위치가 켜져 있었다.

## 껐다

`settings.consent_sms_on_first_save` 를 **1 → 0** 으로 바꿨다.

설정 화면의 묶음 저장은 한 칸을 저장하며 다른 스위치를 끈 적이 있어, 화면을 쓰지 않고
그 한 칸만 바꾸고 앞뒤로 표 전체를 적어 견주었다.

```
끄기 앞 : settings 90칸 · consent_sms_on_first_save = 1
끄기 뒤 : settings 90칸 · consent_sms_on_first_save = 0
함께 바뀐 칸 : 없음
config(order.consent_sms_on_first_save) = false  ← 실제로 꺼진 채 읽힌다
```

`rx_received_sms_on_first_save`(처방전 접수 안내)는 **그대로 켜 두었다** — 지시가
위임동의에 대한 것이고, 접수 안내는 환자에게 「접수되었습니다」를 알리는 다른 통이다.

이제 서명 링크는 담당자가 **단추를 눌러야** 나간다. 손으로 누르는 발송과 배지 안의
재발송은 그대로 쓸 수 있다. 다시 켜려면 설정 화면의 「첫 저장에 위임동의 발송」이다.

## 그 뒤로 생긴 주문 23건

저장 → 자동 발송 → 환자 서명 → `ConsentController` 가 주문 생성, 이 흐름이었다.
서명 쪽은 오늘 `0c89d3d8` 로 막았다(`ensure` 대신 `seed` 의 문턱을 거친다).

이미 생긴 23건은 그대로 남아 있다.

```
주문을 세울 문턱을 못 넘는데 서 있는 주문 : 23건
   그중 저장이 보낸 위임동의에서 비롯한 것 : 9건
   유형이 비어 있는 것 12 · 검수가 안 끝난 것 23

밖으로 나간 것 : 창고 0 · 토스 0 · 결제 링크 0 · 세금계산서 0 · 현금영수증 0 ·
                교환반품취소 0 · 품목이 담긴 것 0 · 받을 돈이 있는 것 0
```

모두 품목 0줄ㆍ0원이다. 앞서 지운 6건과 같은 모양이다. **아직 지우지 않았다.**

## 내가 틀렸던 것

저장이 보낸 것을 처음에 **27줄**이라 보고했다. 「위임동의 발송」 자취의 **바로 앞 줄**이
「주문 등록 저장」인 것만 셌기 때문이다.

그런데 저장은 접수 안내를 **먼저** 보내고(5063줄) 위임동의를 보낸다(5064줄). 그래서
사이에 「처방전 접수 안내 발송 → …」 줄이 끼어 410줄을 놓쳤다.

잣대를 「같은 처방전ㆍ같은 사람ㆍ앞 20초 안에 주문 등록 저장이 있었나」로 넓혀 다시 세니
**437줄**이다. 두 수를 나란히 돌려 견주고 나서야 알았다 — 한 가지 잣대만 돌렸으면
스물일곱 건으로 보고하고 넘어갔을 것이다.
