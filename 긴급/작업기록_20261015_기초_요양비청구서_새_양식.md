# 기초(의료급여) 요양비 지급청구서를 새 양식으로 바꿨다

- 날짜 : 2026-10-15
- 지시 : 운영 담당자 — 「기초(의료급여) 요양비청구서 변경되었음. 기존 양식으로 제출하려
  보니 변경 양식으로 제출 필요하다 하여, 10/1부터 기초건에 대해 모두 반영하고 이후
  변경된 양식으로 생성」
- 받은 것 : `기초 청구서/기초(의료급여) 요양비청구서.pdf`

## 무엇이 달라졌나 — **내용은 같고 담긴 모양이 다르다**

```
옛 : 가로 A4 한 쪽 (297 × 210mm)   resources/pdf/medical_aid_claim_form.pdf
새 : 세로 A4 두 쪽 (210 × 297mm)   resources/pdf/medical_aid_claim_form_2023.pdf
     서식은 1쪽 위쪽에 가로로 앉고, 2쪽은 작성방법이다(내지 않는다)
```

개정 표기는 둘 다 `<개정 2023. 9. 27.>` 로 같고 칸 구성도 같다. **줄 간격이 아래로
갈수록 더 벌어져 옛 좌표를 비례로 옮길 수 없었다** — 세로 쪽에 맞춰 다시 조판된 것이다.

그래서 원본 위에 **10mm 격자와 2mm 눈금을 얹어** 한 칸씩 눈으로 읽어 다시 잡았다.
시험 값을 넣어 그리고 어긋난 자리를 고치기를 여섯 번 되풀이했다.

## 서식이 달라 함께 고친 것 둘

| | 옛 양식 | 새 양식 | 한 일 |
|---|---|---|---|
| ③ 진료 구분 | 외래 칸이 비어 있어 우리가 `V` 를 찍었다 | **`외래[V]` 가 이미 인쇄되어 있다** | 그 자리를 뺐다(또 찍으면 겹친다) |
| 진료받은 사람과의 관계 | 「본인」이 인쇄되어 있었다 | **인쇄되어 있지 않다** | 우리가 적는다 |

## 긴 상병명이 옆 칸을 침범하던 것

상병명은 길이가 제각이다. 운영 65건 가운데 **서른여덟이 열네 자를 넘고**, 가장 긴 것은
스물두 자다(「달리 분류되지 않은 이완성 신경병성 방광」). 그대로 찍으면 옆의 회색
「상병코드」 칸을 덮는다.

칸 폭(`w`)을 적어 둔 칸은 **그 폭에 들어갈 때까지 글자를 줄인다.** 잘라 버리지 않는다 —
관청에 내는 서류라 말이 반토막 나면 읽히지 않는다. 성명ㆍ보장기관ㆍ기관명에도 폭을
적어 두었다.

## 서명 자리는 **DB 가 설정 파일을 덮는다**

`MedicalAidClaimSetting::applyToConfig()` 가 설정 화면에 담아 둔 값으로 config 를 덮는다.
운영에는 옛 양식 기준 서명 자리(`168, 164.5, 20`)가 담겨 있어, 설정 파일만 고치면
그대로 무시된다. **DB 도 새 자리로 바꿨다**(`151, 200.5, 16`).

시험 서버에는 거기에 더해 **칸 좌표 21개가 담겨 있었다.** 옛 양식 기준이라 새 서식에서는
쓸모가 없어 비웠다. 운영에는 담긴 것이 없었다.

## 다시 그린 것

```
10/1 이후 기초(의료급여) 건 : 65건
   이미 청구서를 만들어 둔 것 : 50건 → **모두 다시 그렸다** (탈 0건)
   아직 만들어지지 않은 것    : 15건 → 그대로 둔다
```

아직 없는 건은 **미리 만들지 않는다.** 금액이 정해지기 전에 만들면 0원짜리가 서류함에
쌓인다 — 입금이 확인될 때 `DepositAutoIssue` 가 금액이 든 것으로 그린다.

`attach(…, true)` 가 옛 줄과 파일을 걷고 새로 만든다. 두 벌이 남으면 청구 묶음이
옛것을 집을 수 있다.

### 확인

쪽 크기로 가렸다 — 새 양식은 세로, 옛 양식은 가로다.

```
새 양식(세로) 50건 · 옛 양식(가로) 0건 · 읽지 못한 것 0건
```

운영 자료로 두 건을 그려 눈으로도 보았다(저장하지 않았다).

```
(E)장홍진   성명ㆍ주민번호ㆍ기관명ㆍ기호ㆍ처방전 발행일ㆍ지급일수ㆍ개수
            청구일 2026년 10월 15일 · 청구인 · 전화번호 · 본인 — 모두 제자리
(E)박정태B  상병명 스물두 자가 회색 칸을 넘지 않고 들어갔다
```

진료 시작 「일」이 원본의 구분점 위에 앉아 「14」가 「1·4」로 읽히던 것도 밀었다.

## 서식과 **무관한** 것 둘 — 자료 쪽 문제다

이번 일로 드러났지만 양식을 바꿔도 달라지지 않는다. **옛 양식에서도 같았다** —
값을 만드는 코드는 손대지 않았다.

### ㈎ 보장기관이 **65건 모두** 비어 나간다

```php
'insurer_name' => $rx?->billingOffice?->office_name,
```

처방전에 청구지사가 지정되어 있지 않다. 지금까지 낸 서류도 그 칸이 비어 있었다.
관청이 그대로 받아 왔다면 둘 수 있고, 채워야 한다면 처방전에 청구지사를 지정하는
일이 먼저다.

### ㈏ 구입금액이 **0원**인 건이 18건

본인부담도 공단부담도 0이다. 같은 18건이 **상병명ㆍ진료기간도 비어** 있어 처방전
정보가 아직 안 찬 건으로 보인다. 코드 주석에 「금액이 0 인 청구서는 공단ㆍ지자체가
그 자리에서 되돌려 보낸다」고 적혀 있다.

이 가운데 청구서가 이미 만들어진 건은 새 양식으로 다시 그려졌지만 **금액은 여전히
0이다.** 입금이 확인되면 `DepositAutoIssue` 가 금액이 든 것으로 다시 그린다.

## ⑥ 상병코드는 **적지 않는다** (2026-10-15 지시)

그 칸은 바탕이 회색이고, 서식 머리에 「바탕색이 어두운 난은 청구인이 적지 않습니다」
라고 적혀 있다 — 관청이 심사해 채우는 칸이다. **여태 적고 있었다.**

자리를 두지 않으면 그리지 않는다. 값을 만드는 자리에서도 함께 걷었다 — 쓰지 않는 값을
남기면 다음 사람이 어느 쪽이 도는지 헤맨다.

고친 뒤 **50건을 한 번 더 다시 그렸다.** 그 전에 그린 것에는 상병코드가 찍혀 있었다.

```
다시 그린 청구서 50건
   상병코드가 아직 찍힌 것 : 0건   ← 그 건의 상병코드 글자가 PDF 안에 있는지로 가렸다
   옛 양식(가로)이 남은 것 : 0건
```

가장 긴 상병명 건으로 눈으로도 보았다 — 회색 「상병코드」 칸이 비어 있고, 스물두 자
상병명이 그 칸을 넘지 않는다.

## 뒷손질 — 설정 한계ㆍ미리보기ㆍ실제 구매 값 (2026-10-15 저녁)

### ㈎ 설정 화면에서 고친 자리가 **조용히 잘렸다**

담당자가 「설정을 바꿔도 정보 위치가 변경되지 않는다」고 알렸다.

설정은 제대로 담기고 쓰이고 있었다 — 바꾼 값으로 한 장 그려 확인했다. 문제는
**한계값이 옛 양식 기준**이었다는 것이다.

```
옛 양식 가로 A4 297 × 210  → x 최대 297 · y 최대 210
새 양식 세로 A4 210 × 297  → x 최대 210 · y 최대 297
```

맺음줄(청구인ㆍ전화번호ㆍ관계)은 y 196~213 에 있다. **y 가 210 에서 막혀** 그 아래를
가리키는 값이 조용히 210 으로 잘렸다 — 관계 칸이 212.8 로 들어가야 하는데 DB 에
210 으로 담겨 있었다. 담당자에게는 「바꿔도 그대로다」로 보인다.

모델 상수와 화면의 min·max, 안내 글을 새 양식에 맞췄다(`ebd99fc1`).

### ㈏ 설정 화면에 **미리보기**를 붙였다

자리를 고치고 나면 종이에 어떻게 앉는지 바로 보아야 한다. 여태는 고친 뒤 실제 건을
다시 만들어야 알 수 있었고, **이미 만들어 둔 청구서는 설정을 바꿔도 그대로**라
「고쳐도 그대로다」로 읽혔다.

```
설정 저장 │ 미리보기 ← 새 창
```

같은 폼을 그대로 보내므로 **저장하지 않아도** 지금 칸에 적힌 자리로 그려진다. 새 창으로
여는 것은, 이 창에서 열면 고치던 값이 날아가 한 자리 볼 때마다 처음부터 다시 적어야
하기 때문이다.

**실제 환자 자료를 쓰지 않는다** — 미리보기는 화면에 띄우는 것이라 거기에 남의
주민번호가 실릴 까닭이 없다. 대신 칸마다 **긴 보기 값**(스물두 자 상병명 따위)을 넣어
칸을 넘치는지까지 보인다. 서명은 받아 둔 그림이 없으므로 자리를 네모로 보인다.

**그리는 자리는 하나로 모았다**(`그리기`). 실제 발행과 미리보기가 따로 그리면
미리보기에서 맞춰 둔 자리가 종이에서는 다르게 앉는다.

### ㈐ ⑤ 진료기간과 ⑩ 개수를 **실제 구매 것**으로

담당자가 종이에 표시해 알렸다.

| 칸 | 여태 | 이제 |
|---|---|---|
| ⑤ 진료기간 | 거래명세서 발행일(주문 확정일) | **실제 구매한 날**(처방전의 구매일) |
| ⑩ 개수 | 처방전 총계(`total_count`) | **실제로 산 수량**(주문 품목 수량 합) |

개수는 실제로 틀려 있었다 — 처방 총계 **540** 개인데 이번 주문은 **360** 개인 건에
540 이 찍혔다. 처방에 적힌 수는 이번에 산 수가 아니다. 나누어 사면 갈린다.

진료기간은 2026-10-12 에 거래명세서 발행일을 쓰게 했었다(구매일이 대개 비어 진료기간이
통째로 공란이 되었기 때문이다). 그 까닭은 여전해서 **구매일을 먼저 보고 없을 때만**
물러난다.

### 다시 그리고 전수로 확인했다

```
10/1 이후 기초 건 66건 · 청구서가 있는 51건을 다시 그렸다 (탈 0건)

   옛 양식(가로)이 남은 것   0건
   상병코드가 찍힌 것        0건
   개수가 실제와 다른 것     0건
   진료기간이 빈 것          3건
```

빈 3건은 **구매일도 거래명세서 발행일도 없는** 건이다.

```
EUD202610021055311 (E)유택환 · EUD202610131133091 (E)박선미A · EUD202610131501531 (E)오옥경
   모두 상태 pending · 품목 0줄 · 본인부담 0원 · 창고 번호 없음
```

**아직 주문이 서지 않은 건**이다 — 품목도 금액도 없다. 앞서 적은 「구입금액이 0원인
18건」과 같은 자리다. 서식의 문제가 아니라 자료가 아직 차지 않은 것이므로 그대로 둔다.
입금이 확인될 때 `DepositAutoIssue` 가 금액이 든 것으로 다시 그린다.
