### 까닭 (서버에서 읽음)

`PrescriptionController@list` 의 `doc_rx` 가 **첨부만** 보았다.

```php
'doc_rx' => $rx->attachments->contains('doc_type','prescription') ? 'O' : '—',
```

그런데 그 건에 처방전 그림이 아직 없으면 올린 첫 장은 **`image_path`(본 그림)** 로


**칸이 사실상 반대로 읽혔다.** 「장수만으로는 무엇이 비었는지 알 수 없어」 세운 칸인데,

### 까닭 (코드에서 읽음)

`ReuploadRequestService::알리기()` 가 이렇게 되어 있었다.

```php
if (! $받는이->fcm_token) {
    $요청->update(['fcm_error' => '앱 알림 토큰이 없습니다(앱 로그인 필요).']);
    return;                       // ← 이력도 남기지 않고 끝

```

그런데 `FcmHelper::send` 는 **실패한 것도 이력에 남긴다** — 「알림이 안 왔다」고 할 때
짚을 근거가 되라고 그렇게 두었고, 앱의 알림 이력 화면도 「이 알림은 기기로 전달되지
못했습니다」를 그리도록 되어 있다. **토큰이 없는 경우만 그 앞에서 끊겨 있었다.**

모바일 **웹**으로 쓰는 사람은 브라우저라 토큰이 아예 없다. 그러니 재업로드 요청이
영영 닿지 않는다 — 무엇을 다시 올려 달라고 했는지 볼 자리가 통째로 없다.

같은 자리가 셋이었다: 자료 재요청 · 서류 보탬 · 처방전 등록 취소.

```
결제ㆍ증빙  그대로    ← 바뀐 것이 없으니 올바르다
```

### 왜 잣대가 걸리지 않았나 — 그 뒤에 더 큰 것이 있었다

빈 정정을 막는 잣대는 「품목이 같고 **주소가 그대로**면 멈춘다」다. 그 주소 비교가
언제나 거짓이었다. 화면을 다시 읽으면

```
도로명 주소 칸 ← shipping_address      (기본 + 상세를 합친 값)
상세 주소 칸   ← shipping_address_detail (상세)
```

가 들어가고, 정정할 때 다시 `기본 + ' ' + 상세` 로 만들어 보낸다. **그래서 누를
때마다 상세가 한 벌씩 늘어난다.** 한 번 누른 것으로 이렇게 되었다.

```
전: 서울특별시 강남구 테헤란로 152 강남파이낸스센터 17층
후: 서울특별시 강남구 테헤란로 152 강남파이낸스센터 17층 강남파이낸스센터 17층
```

활동 이력이 그 자리를 못박는다 — `22:42:43 updated || old=…17층  attributes=…17층 17층`.
**창고가 읽는 바로 그 칸이다.**

### 고친 것

규칙을 `Order::기본주소()` 한 곳에 두고 두 자리가 그것을 읽게 했다.

| 자리 | 전 | 후 |
|---|---|---|
| 주문 화면 「도로명 주소」 칸 | 합친 값 | `기본주소()` — 상세를 뗀 값 |
| `WithworksLink::배송지()` | 합친 값 | 같은 `기본주소()` |

`65446d90` 에서 창고 쪽에만 박아 두었던 같은 셈을 이 하나로 모았다 — 두 곳이 따로
떼면 한쪽만 고쳐진다. 떼고 남는 것이 없으면 합친 것을 그대로 준다(상세만 적힌 주문).

**배포 전에 주문 화면을 실제 길로 렌더해 200 을 확인했다** — 1회차에 운영 500 을 낸
그 규칙대로. 어긋난 이 건의 주소도 한 벌로 되돌렸다.

내일 최종 시험 전에 **지시와 소스가 다른 자리 여덟**을 먼저 올린다. ⚠️ 표시한 넷은

## ⚠️ 1) 항목 12 — 결제 완료일을 창고로 보내지 않는다. 저쪽에 받을 칸이 없다

`WithworksConfirm::confirm` 이 `so_confirm` 으로 보내는 것은 **둘뿐**이다.

```php
$보낼것 = ['so_no' => $soNo];
if ($order->statement_date) { $보낼것['statement_date'] = …; }
```

위드웍스 쪽(`CeAdminController::soConfirm`)의 검증도 그 둘만 받는다.

```php
'so_no'          => 'required|string|max:50',
'statement_date' => 'nullable|date_format:Y-m-d',
```

`statement_date` 는 **거래명세서 발행일**이고, 입금 확인 자리에서 굳으므로 결제일과
사실상 같은 날이 된다. 그러나 **이름이 다르고 시각이 없으며, 「결제일」 칸이 저쪽에
아예 없다.**

→ 항목 12 를 글자대로 채우려면 **위드웍스 저장소를 함께 고쳐야 한다**(칸 추가).
우리 쪽만으로는 안 된다. 지금 상태로 둘 것인지, 저쪽 칸을 늘릴 것인지 정해 주셔야 한다.

## ⚠️ 2) 항목 14ㆍ19 — 「바뀐 것이 없는 정정」을 3회차에 막아 두었다

지시는 이렇다.

> 14. 주문 정정에서 **금액 변경이 없으면** 기존 판매주문 삭제되고 신규 판매주문이 등록 및 확정되는지?
> 19. 주문 정정시 **금액 변경과 주소 변경이 없을 때** 거래명세서는 새로 생성되는지?

그런데 3회차에서 **아무것도 바뀌지 않은 정정이 창고 판매주문을 헛되이 갈아 치우는 것**을
결함으로 보고 막았다(`4b5e2b7d`).

```
빈 정정 → 「바뀐 것이 없어 정정하지 않았습니다 — 제품ㆍ수량ㆍ배송지를 먼저 고쳐 주십시오.」
```

**19번은 이 잣대와 정면으로 부딪힌다.** 14번은 부딪히지 않는다 — 「금액 변경 없음 +
**주소 변경 있음**」은 막지 않고 정상 정정되어 판매주문이 갈린다(3회차 확인).

→ 셋 가운데 하나를 골라 주셔야 한다.
  ㉮ 지금처럼 **완전히 같은 정정만** 막는다(19번은 「주소나 제품이 하나라도 달라야 한다」로 읽는다)
  ㉯ 막는 것을 **걷는다** — 누를 때마다 판매주문이 갈리고 거래명세서가 새로 난다
  ㉰ 막되 **「거래명세서만 새로 내기」** 단추를 따로 둔다

## ⚠️ 3) 항목 11 — 카드 결제 건에 현금영수증 「발행 대기」가 선다 (이중 신고 위험)

입금일 때만** 나간다 — 카드결제는 카드매출전표가 증빙이다.」 CASE 1(카드)에서

## ⚠️ 4) 항목 5 — 위임 서명은 **처방전 단위**다. 사람 단위가 아니다

`DelegationGate::signed()` 는 **이 처방전의** 동의만 본다.

```php

    ->where('status','agreed')->whereNotNull('signature_data')->exists();
```

단추 상태(`CONSENT_STATUS`)도 `$prescription->consents()` 다. 그래서

* 같은 처방전에서 서명을 받으면 단추가 「서명 동의」 → **「서명확인」**으로 바뀐다 ✅ (4ㆍ5회차 확인)

  서명을 다시 받아야 주문이 선다

되어 있는 **사람**에게」라는 말과는 다르다 — 어느 쪽을 뜻하셨는지 확인이 필요하다.

```php
{
```

**「처방전 조회」가 한 건도 찾지 못했다** — 남이 올린 건에 서류를 보태는 길이 통째로

```
name=[(E)강태민]   birth_date=NULL   masked=760315-1******

「(E)강태민」 이름만    → 1건
```

* **이름** — `where('name', $이름)` 정확히 일치였다. 주문 등록을 거치면 「(E)강태민」이

지시: **「서먕은 한번 받으면 5년간 재사용하지 않나요? 최초 서명하고 5년산 재사용하지
않나요? => 소스 확인 후 보고」**

### 0. 결론

**지시가 맞고 내가 틀렸다.** 5년 재사용은 이미 소스 여러 곳에 들어 있다.
다만 **앞문(DelegationGate) 하나만 처방전 단위**로 서 있어, 5년 위임기간이 적혀 있는
사람에게도 새 건마다 서명을 다시 받게 하고 있었다.

바로 앞 항목에 내가 적은 「위임 서명은 처방전마다 받는 것이 맞다」는 **근거 없는 판단**이었다.
762fb69c 로 붙인 안내 문구(「이 건은 따로 받습니다」)도 그 잘못된 전제 위에 서 있다.

| # | 결함 | 커밋 | 무엇이 문제였나 |

**③④는 같은 갈래다** — 화면을 여는 동안 값이 바뀌는 것(주문 유무ㆍ유형)을 서버가

markup 을 늘 그린 뒤 그 값을 이미 지켜보는 화면 함수에서 함께 여닫는다.

## 이번 시험에서 내가 잘못 본 것 둘 (바로잡음)

1. **「저장이 멈췄다」** — 사실이 아니었다. 「동의 확인」 창이 확인을 기다리고 있었고,
   누르니 그 자리에서 저장됐다. 내가 `saveOCR()` 을 코드로 불러 창을 보지 못했다.
2. **업로드 확인창 문구가 붙어 나온다** — 사실이 아니었다. 원본에 줄바꿈이 있고
   대화창이 `\n` 을 `<br>` 로 바꾼다. 접근성 텍스트가 붙여 보인 것이다.

**교훈**: 문구는 접근성 텍스트가 아니라 **화면 갈무리로** 판단한다. 조작은 앱 함수를
부르지 말고 **실제 클릭ㆍ입력**으로 한다 — 그래야 사람이 겪는 것을 본다.
