## 6. 오류와 그 해결 — 하나도 빼지 않고

### 6.1 없는 메서드를 부르고 있었다

`$거래처->주민번호담기($w->resident_no)` — `Patient` 에 그런 메서드가 없다. 돌렸으면
첫 줄에서 멈췄다. 실제 길은 `resident_no` 씌우개(`setResidentNoAttribute`)로,
값을 주면 암호문ㆍ해시ㆍ가린 값을 갈라 담고 `rrn_purpose` 까지 적는다.
→ `$거래처->resident_no = …; $거래처->save();`

### 6.2 지울 목록에서 지운 표시가 된 줄이 빠졌다

모델로 고르니 `deleted_at` 이 찍힌 줄이 걸러졌다 — 처방전 **36줄**ㆍ주문 **14줄**.
그대로 지웠으면 그 줄에 딸린 품목ㆍ결제ㆍ서류가 주인 없이 남았다. 밖으로 나간 자취를
세는 자리도 같은 까닭으로 적게 세어졌다(세금계산서 45→46, 위드웍스 74→77).
→ 모델이 아니라 표를 바로 읽는다.

### 6.3 지우면 팝빌 문서번호와 토스 결제열쇠가 함께 사라진다

토스가 아직 쥐고 있는 돈이 2,948,100원인데 열쇠를 잃으면 취소할 길이 없다.
→ 지우기 **앞에** 열쇠를 JSON 으로 적어 둔다. 세어 보이기만 할 때도 적는다.

### 6.4 딸린 파일이 하나도 지워지지 않았다

첨부 줄을 먼저 지운 뒤에 길을 읽으려 했다 → 「딸린 파일 0개」로 보고되고
파일 **527개(77MB)** 가 주인 없이 서버에 남았다.
→ 길을 지우기 앞에서 모은다. 첨부의 덧그리기 원본과 서류함도 함께 모은다.
→ 이미 남은 것은 `--orphan-files` 로 치운다. 폴더째 지우지 않고 파일마다 표와 견준다.

**여기서 또 걸렸다** — `ubuntu` 로 돌리니 522개 가운데 **1개만** 지워졌다.
하위 폴더가 `drwxr-sr-x www-data:www-data` 라 그룹 쓰기 권한이 없다.
→ `sudo -u www-data php artisan test-data:purge --orphan-files --force` 로 521개 지움.

### 6.5 「남는 이력」을 지운 뒤에 세어 13줄만 보였다

외래키가 번호를 비운(`SET NULL`) 다음이라 아무것도 잡히지 않았다. 「남깁니다」라고
표를 보여 주면서 문자 619줄이 어떻게 되었는지 사람이 알 수 없었다.
→ 앞에서 센다. `CASCADE` 로 딸려 지워지는 표(`local_claim_dispatches`ㆍ`nhis_fax_logs`)는
「남깁니다」가 아니라 「딸려 지워집니다」로 갈라 적는다.

### 6.6 되돌리는 길을 거짓으로 적었다

「되돌리려면 `test-data:purge --batch=ww-20260929`」 — 그 명령은 기본으로 `test` 딱지만
본다. 옮겨 온 줄은 `migration` 딱지라 그대로 치면 「지울 것이 없습니다」가 나온다.
되돌릴 수 있다고 믿고 12,604명을 옮겼다가 되돌리지 못하는 것이 가장 나쁘다.
→ `--origin` 을 둔다(고를 수 있는 것은 `test`ㆍ`migration` 둘뿐, `live` 는 멈춘다).
안내도 실제로 통하는 한 줄로 바꿨다.

### 6.7 거래처 관리 화면이 500 오류를 냈다 ★

옮긴 직후 `/patients` 가 열리지 않았다. `laravel.log` 에는 아무것도 없었다 —
치명 오류라 nginx 기록에만 남았다:

```
PHP Fatal error: Allowed memory size of 134217728 bytes exhausted
  in .../Illuminate/Database/Eloquent/Concerns/HasAttributes.php on line 785
  while reading response header from upstream, request: "GET /patients HTTP/1.1"
```

`$query->get()` 이 관계까지 딸려 모델 12,604개를 세우다 메모리 128MB 를 넘겼다.
시험 자료 90명일 때는 드러나지 않던 자리다.
→ 한 번에 그리는 줄을 **500**으로 묶는다(처방전 작업 대기 목록과 같은 잣대).
→ 총 줄 수는 상한을 걸기 **앞에서** 센다. 500줄만 그리면서 「총 500건」이라고 적으면
   12,104명이 없는 것처럼 읽힌다.
→ 상한에 걸렸음을 화면에 적는다 — 적지 않으면 찾는 사람이 목록에 없으니
   없는 줄 알고 새로 등록해 버린다.

### 6.8 나이는 나오는데 생년월일 칸이 비었다

나이는 가린 주민번호에서 세지만(`Patient::age` 가 되돌아간다) 생년월일 칸은
`birth_date` 만 읽는다. 더 나쁜 것은 **「생년」으로 찾는 거르개**가
`whereYear('birth_date')` 라, 채우지 않으면 12,604명 가운데 한 명도 찾히지 않는다.
사업부도 비어 있었다 — 비우면 저장할 때 이름 앞에 `(E)` 가 붙지 않아 위드웍스와
같은 사람을 다른 이름으로 읽는다.
→ `care_type = 'IC'` · 생년월일 · 성별을 가린 주민번호에서 읽어 채운다(복호화 없음).
→ 다시 옮겨 12,604건 덧씀. 생년월일 11,452 · 성별 11,454.

### 6.9 미성년 건의 「본인 서명」이 누구 글씨인지 알 수 없었다

만 7세(#4236 조은빈) 건의 본인 서명 칸에 보호자(이미진) 글씨가 서 있었다.
서명 화면이 미성년이면 법정대리인 서명 하나를 두 자리에 싣기 때문이다 —
종이에도 「위임인이 미성년자인 경우, 본 전자서명은 위임인과 법정대리인 각각의
서명란에 동일하게 적용됩니다」라고 적혀 있다. 그 말이 거래처 화면에는 없어
일곱 살 아이가 제 손으로 쓴 것처럼 읽혔다.
→ 「본인 서명 — 미성년이라 법정대리인이 대신 했습니다」로 적는다.

### 6.10 세어 보이기에서 셈이 0 으로 나왔다 (두 번)

주민번호ㆍ생년월일ㆍ성별을 **담는 자리**에서 세고 있어, `--force` 없이 돌리면
0 으로 나왔다. 몇 명분이 채워지는지 미리 알 수 없다.
→ 세는 자리를 담는 자리보다 앞으로 옮겼다.

### 6.11 「지역 청구 발송」을 「남깁니다」에 적었다

`local_claim_dispatches` 는 `CASCADE` 라 실제로는 딸려 지워진다. 남는다고 적어 놓고
3줄이 조용히 사라졌다. → 6.5 에서 함께 고쳤다.

| 팝빌 세금계산서 | 72 | **25건** | **47건** — 국세청 신고완료(304), 팝빌이 취소를 거부 |
| 팝빌 현금영수증 | 9 | **0건** | **9건 + 내가 만든 취소전표 3장** |
| 토스 승인 | 35 (우리 표) | — | **1건 37,500원** — 나머지 30건은 토스에 없었음 |

### 8.1 토스가 쥐고 있던 돈은 2,948,100원이 아니라 37,500원이었다

우리 표에 적힌 승인 31건 가운데 **30건이 `NOT_FOUND_PAYMENT`** 였습니다.
시험 승인(`/pay/{token}/simulate`)은 장부에만 적는 것이라 결제열쇠가 `TEST_…` 로
서고 토스에는 그런 결제가 없습니다. 앞서 보고한 2,948,100원은 **우리 표 기준**이었고
토스가 실제로 쥔 돈이 아니었습니다.

실제로 살아 있는 것은 가상계좌 한 건 `tlink20260927112446LPyP3` · 37,500원입니다.
가상계좌는 **돌려줄 계좌**가 있어야 무릅니다(`INVALID_REFUND_ACCOUNT_NUMBER`).
주문을 지운 뒤라 고객 계좌를 알 수 없어 짐작해 넣지 않았습니다 —
`--refund-account=은행코드:계좌번호:예금주` 로 사람이 줄 수 있게 두었습니다.

### 8.2 내가 만든 해 — 취소현금영수증 세 장

현금영수증도 세금계산서처럼 「지워 보고 안 되면 취소한다」로 만들었는데, 팝빌이
이렇게 답했습니다 —

| 코드 | 뜻 |
|---|---|
| `-14002007` | 삭제 가능한 상태가 아닙니다 — **국세청에 신고된 현금영수증은 삭제 자체가 안 된다** |
| `-14001065` | 이미 취소전표가 딸린 건에 또 취소를 발행하려 해서 |
| `-14001041` | 취소전표 자체는 다시 취소할 수 없다 |

그 길로 가다 **취소전표 세 장(`XCR…`)이 새로 발행되었고 그것도 지울 수 없어**
주인 없는 문서가 오히려 늘었습니다. 명령을 고쳐 더 이상 지우려 들지 않게 했고,
무엇을 할 수 있는지 줄마다 적어 보이게 했습니다. 현금영수증에서 취소는
「없애기」가 아니라 「전표를 한 장 더 남기기」입니다.

### 8.3 「86건 지움」이 거짓이었다 — 판매주문은 한 주문번호에 여럿 있다

첫 판은 「지움 86건 · 못함 0건」으로 끝났는데, 창고에 물어보니 **21건이 남아**
있었습니다(취소 18 · **확정 3**). 정정이 옛 판매주문을 취소하고 새것을 세우므로
(`so_cancel` → `so_store`) 한 주문번호에 판매주문이 여럿 서고, `so_delete` 는
하나씩만 지웁니다. 다시 돌리니 또 16건이 남았습니다.

남지 않을 때까지 되풀이하도록 고쳤고, **6바퀴**에 끝났습니다 — 지금 0건입니다.

### 8.4 보여 주기가 파일만 읽어 치운 뒤에도 같은 숫자를 냈다

열쇠 파일은 지우던 그때를 찍어 둔 것입니다. 86건을 지우고 다시 돌려도
「아직 쥐고 있는 것 31건 2,948,100원」이 그대로 나와 아무 일도 안 된 것처럼
읽혔습니다. 보여 주기일 때 **토스와 창고에 직접 물어보도록** 고쳤습니다.

### 8.5 위드웍스가 「지웠다」와 「원래 없다」를 같은 답으로 준다

`success: true` 와 함께 「주문을 찾을 수 없거나 이미 삭제되었습니다」가 옵니다.
그것을 「지움」으로 세면 이번에 지운 것처럼 읽혀 셈이 어긋납니다 —
「이미 없음」으로 갈라 세게 고쳤습니다.
