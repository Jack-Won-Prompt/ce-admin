## 3. 옮겨 온 위임 서명을 서명으로 인정한다

`DelegationGate` 가 우리 동의 줄(`prescription_consents`)만 보고 있어, 위드웍스에서
위임장에 서명한 사람도 「서명 없음」이었다.

| 무엇 | 몇 |
|---|---|
| 옮겨 온 위임 서명 | 204줄 |
| 위임 동의 + 서명 그림이 있는 것 | **204줄 전부** |
| 그 사람들의 처방전에서 문이 열리나 | **200/200장** |

위임장을 그리는 자리ㆍ서명 그림을 내려 주는 자리ㆍ문서 목록이 모두 동의 줄에서 넉 칸만
읽으므로(`status`ㆍ`signature_data`ㆍ`patient_name`ㆍ`responded_at`), 옮겨 온 서명을 **담기지
않는 동의 줄 꼴로 감싸** 건넸다. `exists = false` 라 실수로 저장되지 않는다
(`prescription_consents` 0줄 그대로 확인).

**서명 그림이 없으면 받지 않는다** — 받아 주면 위임장이 빈 서명란으로 공단에 나간다.

배지와 「서명확인」 창도 이 처방전의 동의 줄만 보고 있었다. `statusCheck` 가 동의 줄이
없을 때 `reused_sign`(어디서 온 서명ㆍ서명일ㆍ기한ㆍ이름ㆍ서명 그림)을 함께 주도록 고쳤다.
`exists` 는 그대로 false 다 — 이 처방전에 동의 줄이 없는 것은 사실이라 속이지 않는다.

시험서버에서 브라우저로 확인 : 배지에 「✓ 서명 동의 완료 · 운영 데이터의 서명 ·
2026-09-28 서명 — 2031-09-27 까지」, 「서명확인」을 누르면 서명 그림(41,898자)이 그대로 뜬다.

### 3-1. 오류 — 붙여 쓴 Blade 지시어가 화면을 500 으로 죽였다

```
syntax error, unexpected token "endif", expecting end of file
```

`@endif@if(...)` 처럼 지시어를 붙여 쓰면 Blade 가 뒤엣것을 **글자로 본다** — 앞이 낱말
글자(`f`)라 지시어를 찾는 `\B@` 가 어긋난다. `@if` 는 글자로 남고 그 짝인 `@endif` 만
컴파일되어 `endif` 가 하나 더 생겼다.

**앞으로 blade 를 고치면 올리기 전에 컴파일해 잰다** —

```php
$c = new Illuminate\View\Compilers\BladeCompiler(new Filesystem(), sys_get_temp_dir());
file_put_contents($t, $c->compileString(file_get_contents($blade)));
shell_exec('php -l ' . escapeshellarg($t));
```

없는 정보를 짐작으로 채우지 않는다 — 담당자가 미리보기로 보고 찍은 것만 쌓는다

**처방전 그림(첫 장)도 바꾼다.** 처방전이 아닌 것으로 바꾸면 첨부로 내려가고 처방전 칸이
빈다. 거꾸로 첨부를 「처방전」으로 바꾸는데 칸이 비어 있으면 그 칸으로 올라간다.
파일은 옮기지 않고 **가리키는 자리만** 바뀐다.

우리가 만든 서류(거래명세서ㆍ세금계산서…)는 바꿀 수 없다 — 유형이 곧 그 서류의 정체다.

## 6. SSO 로 들어온 사람이 대시보드만 보이던 것

권한은 역할이 아니라 **권한 그룹**이 정한다 —

```php
$group = $user->permissionGroup;
if (!$group) { return $page === 'dashboard' && $action === 'view'; }
```

그런데 SSO 는 사람을 만들 때 `role` 만 넣고 `permission_group_id` 는 넣지 않았다. 게다가
운영에는 **권한 그룹이 0개**였고 여덟 명 모두 그룹이 비어 있었다(`admin` 은 위에서
통과하므로 관리자만 멀쩡해 보였다).

`sso.web.jit_permission_group` 을 두고 기본값 `'full'` — 전권 그룹에 넣고, 없으면 만든다.
JIT 는 처음 들어올 때만 도므로 **로그인할 때도 그룹이 비어 있으면 채운다**. 이미 그룹이
있는 사람은 건드리지 않는다.

운영에서 「전체 권한」 그룹(#1)을 만들고 여덟 명 전부에 붙였다 — `krdk@coloplast.com` 으로
재니 dashboard · patients · prescriptions · orders · finance · settings 모두 **보임**.

**운영 키는 시험서버 DB 에 있었다** — `toss.live_*`ㆍ`popbill.live_*`ㆍ`nice_settings`.
APP_KEY 가 서버마다 달라 암호문은 그대로 못 옮기므로 평문으로 읽어 다시 암호화했다.

### 7-1. 잘못 본 것 — NICE 자격이 「없다」고 했다

`.env` 와 `config/services.php` 만 보고 없다고 했는데 **`nice_settings` 표에 있었다.**
운영에는 `client_secret` 암호문이 있었지만 **풀면 0자**(다른 APP_KEY 로 만든 값)였고
`product_id`ㆍ`standard_url` 이 비어 있었다.

### 7-2. NICE — IP 만 막혀 있었다

두 서버에서 나란히 불러 갈랐다 —

| 서버 | 나가는 IP | 결과 |
|---|---|---|
| 시험 | `3.34.53.36` | ✅ 접근토큰 받음 |
| 운영 | `3.37.111.215` | ❌ `[1007] 허용되지 않은 IP 접근` |

다섯 칸(`client_id`ㆍ`client_secret`ㆍ`product_id`ㆍ`api_base`ㆍ`standard_url`)의 **sha1 이
모두 같음**을 확인했다 — 변수는 IP 하나뿐.

**나가는 IP 는 `3.37.111.215`** 다(checkipㆍipifyㆍifconfigㆍicanhazip 네 곳 일치).
`75.2.99.52` 는 Global Accelerator 라 **들어오는 쪽 전용**이고 이 서버에 붙어 있지도 않다
(`ip route get` 도 `src 10.10.1.82` → NAT → `3.37.111.215`).

공식 가이드(`auth-guide.niceid.co.kr`)와 대조하니 엔드포인트ㆍ**Base64Url** 인코딩ㆍ
본문 칸ㆍ`client_id` 꼴(`NI` 로 시작)이 모두 우리 구현과 같았다. 가이드가 「이용기관 서버의
**Outbound IP** 를 NICE 담당자에게 전달하여 권한 등록」이라 적어 둔 그대로다.

중간에 받은 키 `05169ec0-…`(UUID 꼴)는 `NI` 로 시작하지 않았고 실제로 부르니
`1006 ClientID 권한 없음` 이었다 — 다른 앱이라 **담지 않았다**.

### 7-3. 위드웍스 — `CEADMIN_WEBHOOK_SECRET` 만으로는 안 된다

저쪽 `.env` 의 `CEADMIN_WEBHOOK_SECRET` 은 우리가 가진 48자와 **글자까지 같다**. 다만 그것은
**저쪽 → 우리 콜백**용이다. 우리가 저쪽을 부르는 `api/v1/ce-admin/*` 는 `auth:api`(Passport)
그룹 안에 있어 토큰이 필요하다.

**토큰 없이 부르면 HTTP 200 인데 몸이 `{"error":"Not Login","code":"403"}` 다** — 200 만 보고
된다고 읽으면 안 된다.

토큰은 `POST /api/v1/auth/login` 이 내준다(`WithWorksAuth` 개인 접근토큰). 처음에는 저장소에
적힌 사람 계정(`JHW` · user 1826)으로 받았다가, 지시로 **전용 계정 `CEADMIN`(user 159163)**
으로 바꿨다. 담기 전에 그 토큰으로 읽어 보고 주인이 159163 인지 확인한 뒤에 갈아 끼웠다.

  (`String.fromEnvironment('API_BASE_URL')`, 기본값이 시험서버).
- `flutter build apk --release --flavor prod --dart-define=API_BASE_URL=https://75.2.99.52/api`

  Flutter 가 Dart 산출물을 캐시에서 재사용했다(Gradle 7.5초). **`flutter clean` 뒤에

### 8-1. `storage:link` 는 만들지 않았다

`public/storage` 링크가 없어 `/storage/...` 가 404 인데 **그대로 두었다.** 그 링크를 만들면
`storage/app/public` 아래가 통째로 열리고, 거기에는 옮긴 **처방전 사진 11,296장(8.8GB)** 이
들어 있다. APK 한 장만 `public/apk/` 에 두었다.

| 칸 | 값 |
|---|---|
| `mobile.apk_url` | `https://75.2.99.52/apk/ce-admin-1.3.3.apk` |
| `mobile.latest_version` | `1.3.3` |
| `mobile.min_version` | `1.3.2` |

`min_version` 을 1.3.3 으로 올리면 지금 1.3.2 를 쓰는 사람이 그 자리에서 막힌다.

### 8-2. 인증서 — 자동 갱신은 살아 있다

`75.2.99.52` 는 Let's Encrypt **IP SAN** 인증서(`preferred_profile = shortlived`, 10-05 만료).
`certbot` 이 `/etc/letsencrypt/renewal/75.2.99.52.conf` 로 관리하고

### 9-1. 토스 웹훅이 없는 결제에 500 을 돌려주던 것

것이고 그 뜻은 그대로 둔다.

그런데 **없는 결제는 몇 번을 물어도 없다.** 그것까지 500 이면 토스가 끝없이 다시 보낸다.
토스 개발자센터의 「웹훅 테스트 발송」이 바로 그 꼴(가짜 paymentKey)이라, 연동을 확인하려고

`TossClient` 는 `[코드] 메시지` 꼴로 던지고 예외 코드에 HTTP 상태를 담으므로,
**404ㆍ401 과 `NOT_FOUND_PAYMENT`ㆍ`UNAUTHORIZED_KEY`ㆍ`INVALID_API_KEY` 는 200 으로 접고**
그 밖(연결 끊김ㆍ저쪽 5xx)은 그대로 500 이다. 고친 뒤 같은 요청에 **200** 이 돌아왔다.

위 두 번째ㆍ세 번째 시험이 답이다 —

- 다섯 자리에 **서로 다른 값**은 넣을 수 있다(통과).
- 사이의 「/」 는 승인된 글자라 **지울 수 없다**(지우면 실패).

그런데 처방전 48,490장 가운데 품목이 딱 다섯 줄인 것은 **2장**뿐이다.

| 품목 줄 | 장 | 몫 |
|---|---|---|
| 1줄 | 42,709 | 88.1% |
| 2줄 | 5,419 | 11.2% |
| 3줄 | 330 | 0.7% |
| 4줄 | 30 | 0.1% |
| 5줄 | **2** | 0.0% |

나머지는 빈 자리가 「,  , 개/」 꼴로 환자에게 그대로 보인다.
**템플릿을 「1. 주문사항: #{주문사항}」 꼴로 고쳐 다시 승인**받아야 한다 —
변수 하나면 우리가 품목 수에 맞춰 지어 넣는다.

### 사람이 받았다 — 확인 완료 (2026-09-30)

시험 폰(01057990084)에 **「[콜로플라스트] 주소 안내」** 와 **「[콜로플라스트] 구매 내용
안내」** 두 통이 **도착한 것을 사람이 확인**했다. 팝빌의 `successCnt` 만이 아니라
받는 쪽 화면까지 닿은 것을 보았다.

이로써 알림톡 길이 처음부터 끝까지 선다 —

```
메시지 유형(승인 본문 그대로)
  → 변수 채우기(못 채우면 멈춘다)
  → KakaoReceiver(우리가 둔 것)
  → 팝빌 SendATS · 발신 1588-7866
  → 카카오 채널 @coloplast콜로플라스트
```

세 번째 통(남는 자리를 지운 것)이 실패한 것도 그대로 확인됐다 — 승인된 글자는
지울 수 없다는 뜻이고, 「구매 내용 안내」의 재승인이 필요한 근거다.

**시험 이력은 지우지 않는다** — 접수번호 세 개(`…62200016`ㆍ`…73100004`ㆍ`…81900006`)는

## 15. 재등록 기한과 토스 웹훅 (2026-09-30 지시)

### 재등록 기한 = 최초 등록신청서 팩스 전송일 + 2년

`Prescription::재등록기한()` 으로 두었다. 「재등록 신청 안내」(`026090001920`) 의
`#{날짜}` 가 이 값을 쓴다.

- **처방전이 아니라 사람으로 센다** — 한 사람이 처방전을 여러 장 내는데 등록은 사람
  단위로 한 번이다. 이 처방전만 보면 두 번째 처방전부터 기한이 뒤로 밀린다.
- **전송완료(`popbill_state` 2)만 센다** — 실패한 팩스는 공단에 닿지 않았다.
- 보낸 적이 없으면 `null` 이고, 그러면 알림톡이 막힌다.

**지금은 모든 환자가 `null` 이다** — 운영의 `fax_histories` 가 0건이다(새로 뜬 서버).
등록신청서 팩스가 나가기 시작하면 그때부터 채워진다.

**이관 환자는 그래도 비어 있을 것이다** — 최초 등록이 위드웍스에서 일어났기 때문이다.
저쪽에서 그 날짜를 담은 칸을 **확정하지 못했다.** 날짜로 보이는 것은 있으나 모두
2년이 아니다 —

| 칸 | 건수 | 보기 | 사이 |
|---|---|---|---|
| `udf42` → `udf43` (처방전 거울) | 65,767 / 42,646 | 2023-10-05 → 2028-10-04 | **정확히 5년** |
| `udf12` → `udf20` (거래처 거울) | 4,653 / 6,777 | 2026-09-28 → 2031-09-28 | 5년으로 보임 |

**짐작해 쓰지 않았다.** 이관 환자의 재등록 기한이 필요하면 저쪽 칸을 먼저 확정해야 한다.

### 토스 `PAYMENT_STATUS_CHANGED` — 등록은 됐으나 아직 한 건도 오지 않았다

nginx 로그의 `POST /toss/webhook` 은 **7건 모두 내 `curl` 시험**이다. 토스가 보낸 것은
아직 없다. 실제 결제가 일어나거나 콘솔의 **「테스트 발송」** 을 눌러야 들어온다.

**웹훅 주소가 카카오톡에 붙여진 자취가 있다** — `kakaotalk-scrap` 이 네 번 `GET` 으로
긁어 갔다(405 로 막혔다). 주소에 열쇠가 박혀 있으므로, 그 대화방 밖으로 새어 나갔다고
볼 여지가 있으면 **열쇠를 새로 짓고 토스ㆍ팝빌에 다시 등록**하는 편이 낫다
(`WebhookKeys::새로짓기`).

### 알림톡 전송결과 웹훅도 선다

세 통 모두 팝빌이 결과를 돌려주었고 접수번호가 그대로 맞는다 —

| 웹훅 | 접수번호 | result | 뜻 |
|---|---|---|---|
| #51 | `026093011462200016` | **100** | 성공 |
| #52 | `026093011473100004` | **100** | 성공 |
| #53 | `026093011481900006` | **630** | 카카오톡 내용과 템플릿이 일치하지 않음 · **미과금** |

630 이 「남는 자리를 지우면 안 된다」를 팝빌 코드로 확인해 준다. 미과금이라 포인트도
성공한 두 통만 깎였다(7,936 → 7,920 = 8점 × 2).

## 16. 알림톡을 링크 두 자리에 물리고, 도메인을 IP 로 되돌렸다 (2026-09-30)

### 알리고 길은 한 번도 선 적이 없었다

`MessageSender` 의 알림톡은 알리고를 탔는데 `KAKAO_API_KEY`ㆍ`KAKAO_SENDER_KEY` 가 빈
채라 `isConfigured()` 가 늘 거짓이었다 — 메시지 유형에서 알림톡을 켜 두어도 한 통도
나가지 않았다. 팝빌로 옮겼다.

알림톡은 **승인 본문으로만** 나가므로 부르는 쪽이 건네는 문자 글을 쓸 수 없다(그대로
보내면 630 으로 되돌아온다). `sendBulk` 에 값들을 받아 본문은 유형에서 읽고 변수만
채운다. `#{이름}` 은 사람마다 달라 수신자별로 따로 짓는다.

### 물린 자리

| 자리 | 코드 | 이제 나가는 채널 |
|---|---|---|
| 신분증 제출 링크 | `id_card_request` ← `026090001916` | **알림톡 + 문자** |
| 위임장 서명 링크 | `delegation_sign` ← `026090001915` | **알림톡 + 문자** |

한쪽이 못 나가도 다른 쪽은 살리고, 둘 다 못 나갔을 때만 실패로 본다.
`kakao:sync-templates` 가 이 코드를 되돌리지 않도록 **이미 있는 줄의 코드는 건드리지
않게** 고쳤다 — 되돌리면 그 자리가 조용히 문자만 나가는 상태로 돌아간다.

### 서류명 고르개 · 미리보기

「서류등록 안내」의 `#{서류명}` 고르개를 알림톡 팝오버에 두었다(첨부 유형과 같은 목록).
승인 문구가 그 변수를 쓸 때만 뜬다.

**미리보기가 이제 실제로 나갈 글 그대로를 보여 준다.** 예전에는 코드에 박아 둔 글 세 벌뿐
이어서 새 유형 13개 전부가 「미리보기 없음」이었다 — 담당자는 무엇이 나갈지 보지 못한 채
눌러야 했다. 못 채운 값이 있으면 빨간 줄로 알리고 **보내기 단추를 잠근다.**

값 채우는 자리는 한 곳(`알림톡값들`)으로 모았다 — 두 벌로 두면 화면에서 본 것과 환자가
받는 것이 갈린다.

### 시험 — 새 길로 세 통 더

| 접수번호 | 무엇 | result |
|---|---|---|
| `026093012115000004` | 위임장 서명 안내 · `MessageSender` 알림톡 | **100** |
| `026093012123700001` | 신분증 제출 안내 · `MessageSender` 알림톡 | **100** |

나가는데 내역은 부르는 쪽이 준 글을 적고 있었다. 이제 지어진 글을 적는다(311자).
커밋 `caab4d27`.

### 도메인 — `mycolo.co.kr` 을 걷고 IP 로 되돌렸다

## 17. 자동 알림 정리 · 알림톡 우선 · 문구 일치 (2026-09-30 지시)

### 자동으로 나가는 알림 여섯

사람이 누르지 않고 저절로 나가는 자리다.

| 언제 | 부르는 곳 | 코드 | 알림톡 |
|---|---|---|---|
| 결제가 끝나면 | 토스 웹훅ㆍ가상계좌 입금ㆍ결제완료 화면 | `payment_done` | **`026090001850` 이음** |
| 창고가 출고하면 | 위드웍스 웹훅ㆍ동기화 | `shipping_started` | **`026090001918` 이음** |
| 주문을 취소하면 | `OrderCancelService` | `order_cancelled` | 승인 문구 없음 |
| 교환·반품 접수 | 반품 상세(저절로) | `return_received` | 승인 문구 없음 |
| 환불 완료 / 환불 없음 | 반품 상세(저절로) | `return_refunded`ㆍ`return_refunded_none` | 승인 문구 없음 |
| 추가 입금 필요 | 금액조정 단계(저절로) | `return_extra_payment` | 승인 문구 없음 |

사람이 눌러 보내는 것 — 결제 링크 셋ㆍ위임장 서명ㆍ신분증ㆍ최종 승인 요청ㆍ주문 등록
화면의 수동 알림톡.

### 발송 방식을 한 곳으로 모았다

여태 **일곱 자리**가 제가끔 `보낼채널들` 을 돌며 결과를 모았다. 방식을 바꾸려면 일곱 곳을
모두 고쳐야 했고, 한 곳이라도 빠지면 그 자리만 조용히 두 통을 보낸다.

`MessageTemplate::채널마다` 한 곳으로 모았다. 기본은 **알림톡 우선 · 실패 시 문자**다.

**2026-09-19 의 「모두 보냄」을 되돌리는 것**임을 적어 둔다 — 그때는 「알림톡이 성공하면
거기서 멈춰 둘 다 켜 두어도 한쪽만 나간다」가 까닭이었다. 이번에는 같은 말을 두 통 받는
쪽이 더 번거롭다고 본다. **설정 › 서비스 연동 설정 › 카카오 알림톡 › 발송 방식**에서
「모두 보냄」을 다시 고를 수 있다(`kakao.send_policy`).

문자만 나가던 자동 알림 셋(결제 완료ㆍ주문 취소ㆍ출고)도 이 길을 타게 했다. 알림톡
유형이 그 코드로 서 있지 않으면 예전처럼 문자만 나간다.

### 문자 문구를 승인 문구 그대로 맞췄다

| 코드 | 전 | 후 |
|---|---|---|
| `payment_done` | 73자 | **134자** (승인 문구) |
| `shipping_started` | 58자 | **151자** (승인 문구) |

**옛 글은 여기 남긴다** — 되돌리려면 그대로 쓰면 된다.

```
payment_done      [콜로플라스트] #{고객명}님, 결제가 정상 처리되었습니다.
                  주문번호: #{주문번호}
                  결제 금액: #{결제금액}원 (#{결제수단})

shipping_started  [콜로플라스트] #{고객명}님, 제품이 발송되었습니다.
                  주문번호: #{주문번호}
                  운송장: #{운송장번호}
```

**줄어든 것이 있다 — 지시대로 맞추었으나 짚어 둔다.**

- **결제 완료 문자에 금액과 주문번호가 없어졌다.** 승인 문구에 그 변수가 아예 없다.
- **출고 문자에 주문번호가 없어지고 택배사가 `CJ택배` 로 굳었다.** 승인 문구가 그렇다.
- 둘 다 길어져 **LMS** 로 나간다(한글 45자를 넘으면 SMS 가 아니다).

되살리려면 팝빌 템플릿에 `#{주문번호}`ㆍ`#{결제금액}` 을 넣어 **재승인**받아야 한다.

### 변수 이름이 둘이 되었다

승인 문구는 `#{이름}`ㆍ`#{송장번호}` 를, 우리는 `#{고객명}`ㆍ`#{운송장번호}` 를 쓴다.
승인 문구는 한 글자도 고칠 수 없으므로 **우리 쪽이 둘 다 본다**.

배송 안내의 「운송장이 없으면 그 줄을 뺀다」도 두 이름을 모두 찾게 했다 — 한 이름만 보면
「-운송장번호:」 뒤가 빈 채로 나간다.

### 지어지는 글 확인 (운영)
